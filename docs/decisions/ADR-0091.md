# ADR-0091: The Lite Edition Takes Its Own Identity Before 1.0

**Status:** Accepted -- built 2026-10-01 (W2-05, W3-03)
**Date:** 2026-10-01
**Answers:** the deferral in [ADR-0074](ADR-0074.md)
**Amends:** [ADR-0032](ADR-0032.md) (the application id)

## Context

ADR-0032 chose `io.github.dboles99.BachelorPadPlus` as the application id,
and the Windows registration wrote ProgIDs `BachelorPadPlus.<ext>` and a key
`HKCU\Software\BachelorPad+`. ADR-0074 renamed the product to *BachelorPad+
Lite* and left all three alone, saying so: *"the full BachelorPad+ would want
that same identifier, and two products sharing an `APP_ID` is a collision
waiting for whoever installs both. It is written down here so that it is
asked before the full version ships."*

1.0 is the point after which it cannot be asked cheaply. Before it, the only
registries holding the old names are this project's own test machines; after
it, every installed copy holds them, and a rename means migrating each one.
Two more facts arrived with the release:

- **Flathub requires an `io.github` id to name the repository it is built
  from.** `io.github.dboles99.BachelorPadPlus` names a repository that does
  not exist; `io.github.dboles99.bachelorpluslite` names this one.
- **The guard admitted the full product's territory.** `key_objection`
  allowed any key beginning `Software\BachelorPad+` and any ProgID beginning
  `BachelorPadPlus` -- harmless while that product did not exist, and the kind
  of prefix that stops being harmless without anybody noticing.

## Decision

**The Lite edition gets names of its own, and the old ones become the full
product's.** Approved by Daniel on 2026-10-01, including the renamed file.

| | 0.9.5 | 1.0 |
| --- | --- | --- |
| `APP_ID` | `io.github.dboles99.BachelorPadPlus` | `io.github.dboles99.bachelorpluslite` |
| Window icon | `io.github.dboles99.BachelorPadPlus.png` | `io.github.dboles99.bachelorpluslite.png` |
| ProgID prefix | `BachelorPadPlus` | `BachelorPadPlusLite` |
| Software key | `HKCU\Software\BachelorPad+` | `HKCU\Software\BachelorPad+ Lite` |
| `APP_DIR` (your data) | `bachelorpad` | unchanged -- nothing of yours moves |

`key_objection` now admits exactly the new key and the new prefix, so the old
names read as another application's -- which, from now on, they are.

**The registration gets an undo.** The installation page had promised one and
nothing produced it. Every Windows plan now carries a second `.reg`,
`<app id>-remove.reg`, written beside the first. It deletes the product's own
ProgID and software keys outright, and takes single *values* out of the
shared keys (`OpenWithProgids`, `RegisteredApplications`) -- never the keys,
which belong to every application that has registered a file type. **It is
the one place the 0.9.5 names may appear**, as constants named `LEGACY_*`,
because the full product has never shipped and so nothing but an earlier
build of this one can have written them. A test walks every key it names and
accepts only what is ours or was.

**Both scripts are written as UTF-16LE with a byte-order mark.** The
`Version 5.00` header declares a Unicode file, and `regedit` reads a UTF-8
one through the system code page, so an executable under a folder with an `é`
in its name was registered at a path that does not exist.
`Artefact::bytes` decides the encoding in one place.

**The window says which application it is** (W3-03).
`slint::set_xdg_app_id(APP_ID)` before the window is created, so a Wayland or
X11 dock matches the window to the `.desktop` file this product writes and
draws its icon. Unset, winit named the window after the executable,
`bachelorpad`, which matched no `.desktop` file at all.

## What building it found

**The test `DISPLAY_NAME`'s doc comment named had never existed.**
`every_place_the_product_names_itself_must_read_display_name` was cited from
the commit that wrote the comment, and `git log -S` finds no other commit
mentioning it. Meanwhile four registration messages said "BachelorPad+" -- the
full product's name -- in the Lite edition's dialogs. That is trap 3 inside
the comment written about trap 4, and it is the third time ADR-0074's lesson
has been relearned.

`tests/integration/tests/the_product_names_itself_through_one_constant.rs`
now reads every string literal in shipped Rust and Slint source and fails on
any that names the product outside the constants allowed to; the registry
constants that must be literals are pinned to `DISPLAY_NAME` by a test of
their own. Run against the code before this change, it names all six sites
the change fixed -- watched.

## What it costs

- **A machine that applied the 0.9.5 registration keeps the old entries until
  the removal script runs.** They still point at wherever the old executable
  was. The tutorial says to run it; nothing runs it for anybody (ADR-0070).
- **`APP_ID` now carries ADR-0032's compatibility promise for real**, from
  the first release anybody outside this project installs.

## Verification

- `bp-platform`: the full product's names are refused; the registry
  constants agree with `DISPLAY_NAME`; the removal script deletes our keys and
  only our values, and every key it names is ours or was; both scripts are
  UTF-16 with a BOM and an `é` survives as itself.
- The name guard above, failing against the previous code.
- **Not seen in a dock or in regedit.** Both need a person at a desktop: the
  manual pass applies the registration, checks Explorer's Open With, runs the
  removal script, and on Linux checks the window groups under the launcher.
