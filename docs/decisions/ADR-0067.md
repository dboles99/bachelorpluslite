# ADR-0067: There Is No Installer, And An Unsigned One Would Be Worse Than None

**Status:** Accepted
**Date:** 2026-08-30
**Closes:** `project/WORK_QUEUE.md`'s P5
**Amends:** [ADR-0054](ADR-0054.md)
**Depends on:** [ADR-0055](ADR-0055.md), [ADR-0012](ADR-0012.md)

## Context

P5 asked for *"an installer, or a decision that there is not one"*, and noted
it only became askable once an archive existed. `scripts/New-Release.ps1`
produces both today: a `.zip` for Windows and a `.tar.gz` for Linux, each
carrying the executable, the `bpad` short spelling, both licences, a manifest
naming the target, and checksums.

The candidates were MSI, winget, or nothing.

## Decision

**There is no installer. The archive is the delivery mechanism.**

### An unsigned installer is a worse product than no installer

[ADR-0055](ADR-0055.md) deferred code signing and refused self-signing
outright. That decision governs this one, and it is not a small
inconvenience — it is the argument:

- **An unsigned MSI is treated far more harshly than an unsigned executable.**
  SmartScreen's reputation check applies to both, but an installer *asks for
  elevation*, which is precisely the moment a user should be most suspicious
  of something unsigned. The product would be teaching the habit
  [ADR-0055](ADR-0055.md) refused self-signing to avoid.
- **A zip the user extracts themselves involves no elevation and no trust
  decision.** They can see exactly what they got before running it.

So the ordering matters: an installer is not blocked on effort, it is blocked
on a signature, and until D15 is revisited the answer would be the same
however much work went into it.

### winget is not available, for a reason that has nothing to do with quality

`microsoft/winget-pkgs` requires a manifest submitted by pull request with a
**publicly reachable, stable installer URL**. This repository is private and
there are no published release artefacts. That is a fact about distribution,
not about packaging, and no amount of MSI work changes it.

> **Amended 2026-09-25 ([ADR-0086](ADR-0086.md)).** Both halves of this have
> gone: the repository has been public since 2026-09-10, and winget accepts a
> portable ZIP (`InstallerType: zip`, `NestedInstallerType: portable`), so it
> needs no installer at all. winget is a 1.0 distribution task now. The
> decision against an installer stands.

### An installer would have almost nothing to do

This is the part worth writing down, because it is the part that would
otherwise be rediscovered:

| What an installer usually does | What it would do here |
| --- | --- |
| Copy the program somewhere | Copy **one** self-contained executable |
| Create a Start Menu shortcut | The only genuine gain, and small |
| Provide an uninstaller | Delete a folder |
| Add a short-spelling alias | **Already done** — `bpad.cmd` on Windows and a symlink on Linux ship *in the archives* (P4) |
| Register file types | **Forbidden** as an install step |

That last row is the strongest of them. [ADR-0012](ADR-0012.md) decided that
this product never seizes a file association: File ▸ Set as Default Editor
*reports* first, asks for consent, and on Windows hands the user a `.reg` to
read and apply themselves. **An installer that registered file types would
contradict ADR-0012; one that did not would be copying a single file.**

**ADR-0054 is amended.** It kept the `bpad` short spelling as "something an
installer creates rather than something the product does". P4 built it into
the release staging instead, and this ADR removes the last reason that
sentence gave for wanting an installer at all.

## What would change the answer

Written down so the question can be re-asked from evidence rather than from
appetite:

1. **A code-signing certificate** (D15 revisited) **and** a public release
   URL. Both, not either: signing makes an installer defensible, and a public
   URL makes winget possible. With those, winget is the cheapest good answer
   and MSI still probably is not.
2. **Something that must live outside the program's own directory.** A shell
   extension, a service, a per-machine registry key nothing else writes.
   Today there is nothing: the profile directories are created on demand by
   `bp-config`, and the `.reg` handoff is the user's to apply.

Neither is close. The second is *further* away than it was — this session
removed encryption, signing keys, an audit log and a metadata inspector, all
of which were candidates for state an installer might have wanted to place.

## Consequences

**The release scripts are already the whole story and need no change.** That
is the useful outcome: this ADR is a decision that costs nothing to implement,
which is what P5 was queued to establish.

**P2 is unblocked and its shape is now fixed.** The icon question was waiting
on this, because an installer is the usual place an icon gets placed into an
icon theme. With no installer, an icon must travel **inside the archive** and
be referenced from where it lands — which turns out to remove P2's dependency
problem rather than create one. That is [ADR-0068](ADR-0068.md).

**A Start Menu entry is the one thing genuinely lost**, and it is worth naming
rather than pretending otherwise. A user who wants one makes a shortcut. That
is a real if minor cost of this decision, accepted knowingly.

## The lesson

> **"Or a decision that there is not one" is the more valuable half of a
> queue item, and it is the half that gets skipped.**

P5 was written with both halves in it, deliberately, and the second half was
the right one. What made it decidable was not new information about
installers — it was that two *other* decisions had already constrained it:
ADR-0055 refused an unsigned trust gesture, and ADR-0012 refused a silent
association. Together they leave an installer with one Start Menu shortcut to
justify itself.

**A decision is often already made by the decisions around it**, and the work
is noticing rather than choosing.
