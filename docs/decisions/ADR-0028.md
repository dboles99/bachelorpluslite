# ADR-0028: Redaction

**Status:** Accepted
**Date:** 2026-08-19

## Context

specs.md section 15 asks for redaction and a metadata inspector; section 24
names "metadata leakage" as a threat category of its own. Neither existed.

The failure that has embarrassed governments, law firms and newspapers is
always the same one: a "redaction" that covers text the reader can select,
copy, or recover by deleting a layer. So `redact` returns a new `String` with
the named text gone out of it. Nothing in `bp-redaction` draws a black
rectangle, sets a background colour, applies a style or attaches an
annotation. There is nothing to peel off because there is nothing underneath.

Finding is a different job from destroying, so spans are a parameter.
`bp-secrets` finds credentials, `inspect` finds identifying metadata, and the
user finds the rest by selecting it. This crate deliberately does not depend
on `bp-secrets`: it would gain nothing, would bind two release cycles
together, and a redaction engine that can only destroy what one particular
scanner recognises is one the user cannot point at their own name.

## Decision

### Overlapping *and adjacent* spans merge

The three available answers are reject, apply in sequence, and merge.

**Rejecting fails at the worst moment** — the moment two rules agree there is
something to remove. Two scanners both spotting the same key, or a user
selecting text a scanner already flagged, is the normal case and not an
error.

**Applying in sequence is where the classic bug lives**: the first
replacement moves every later offset, and the second redaction lands
somewhere else. That failure destroys the wrong text and reports success.

So spans are sorted, widened, merged, and applied in one pass. All offsets
are resolved against the original before a single byte is copied, which is
precisely why overlapping spans cannot shift each other. The cost is linear
in the text plus `n log n` in the number of spans, with no re-scanning.

Merging *adjacency* as well as overlap is the part that is easy to skip and
buys the most: it makes the output independent of how the caller happened to
split its findings. Splitting a span at any interior point gives byte-identical
output, and that is a pinned test. The caller's arbitrary decision about where
one finding ends and the next begins must not be visible in the document.

Order does not matter, because spans are sorted first. Labels of merged spans
are all kept, in first-seen order and without duplicates, because dropping
all but one would misdescribe the redaction inside the document itself.

### A span past the end is an error, not a clamp

A span reaching past the text proves the offsets were measured against
different text — nearly always because the text changed after the spans were
computed. That does not make one span suspect; it makes **every** span in the
set suspect. Clamping it would redact a range nobody named while reporting
success, which is worse than any error message.

An inverted span is an error for the same reason: `end < start` cannot be
honoured in any way that is not a guess. Nothing is redacted when either
fires — a partial redaction reported as a failure is the worst of both.

An empty span is ignored rather than refused. It names no text, so there is
nothing to destroy and nothing to announce. It is dropped *before* widening,
so a zero-width position inside a multi-byte character cannot grow into the
destruction of a character nobody named. That also protects `verify`: every
string contains the empty string, so a single empty range in a plan would
make verification report a survivor for ever.

### A span splitting a character widens outwards, and says so

Spans are byte ranges, because that is the only unit in which a caller can
name a boundary Rust will refuse to slice at — and refusing to slice there is
a panic in the user's face. A caller computing offsets from a parser, a
search or a scanner already has bytes; converting to characters first would
be a second place for an off-by-one to live.

Widening is outwards, never inwards: the direction that destroys more,
because leaving a fragment of what was named is the failure that matters.
`Applied::widened` reports it, because more was destroyed than the caller
asked for. Harmless in itself — the extra is the remainder of a character the
span cut in half — but it is also the symptom of a caller computing offsets
in the wrong unit, and that is worth surfacing.

### Three replacement modes, and each discloses something different

* **`Remove`** closes the gap. The document reads as if the words were never
  written. Right when the redaction should not be visible at all — a key
  pasted into a note by accident, a paragraph the author decided against — and
  wrong when the reader is entitled to know something was withheld, because it
  hides the withholding as well as the text.
* **`Mask { fill, width }`** replaces with a run of one character. Right where
  the document's shape matters, or where a visible bar is the convention the
  reader expects. `fill` is written verbatim: a newline or a control character
  here will damage the document's structure and this crate will not stop you.
* **`Placeholder`** writes `[REDACTED]`, or `[REDACTED: label]` when the
  merged span carries labels. Right for a document read by someone who needs
  to know a redaction happened, and often what kind. The cost is exactly that:
  `[REDACTED: AWS key]` tells the reader an AWS key was there, which the empty
  gap of `Remove` does not give away.

`MaskWidth` is the sharpest of these. `Fixed(n)` tells the reader that
something was here and nothing else. **`MatchOriginal` discloses the length of
what was removed.** For a name that is nearly nothing; for a password, a PIN,
or a short answer from a fixed set of options it is most of the secret.
`Fixed(0)` is legal and leaves no mark at all — `Remove` with extra steps —
allowed so a caller computing a width from a setting need not special-case
zero, and worth knowing about. Masking counts characters, not bytes, so an
accented letter or an ideograph costs one mask character rather than two or
three.

A `Span`'s `label` says what kind of thing was here — "AWS key", "client
name" — and must never be the text itself, because `Placeholder` writes it
into the document and a label carrying the secret puts the secret back. The
type cannot enforce that; the caller can, by passing the name of the rule that
matched rather than what it matched.

### `verify` proves one narrow thing, and the "cannot" list is longer

`verify` takes the same original and spans given to `redact`, plus the text it
returned, and re-derives what was removed rather than taking it as an
argument — so no caller has to hold the secret in a variable in order to check
for it.

**What a clean result proves.** That the exact byte sequence occupying each
redacted span in the original does not occur anywhere in the output. For a
credential, a name or an address — text meant to be matched literally — that
is the question worth asking, and it catches the whole family of real
failures: a mask written over the top without deleting, a replacement applied
at a stale offset, a copy of the value elsewhere in the same document, a mode
that turned out to be a no-op.

**What it does not prove.**

* **Not that the information is gone.** Only literal bytes are searched for.
  The same secret base64-encoded, percent-encoded, in another case, split
  across a line break, or described in a sentence is invisible to the check.
* **Not that a survivor is a failure.** If the same text also appears
  somewhere the caller did not name — the key pasted twice, a name in the
  title as well as the body — it is reported as surviving even though every
  named span was destroyed. That is the correct alarm to raise, but it is a
  reason to look, not a verdict.
* **Not that the spans were the right spans.** A caller that named the wrong
  bytes gets a clean verification of a redaction that removed the wrong text.
  Nothing here can know what should have been removed.
* **Nothing about the file.** The original document, earlier versions, the
  recovery journal (ADR-0022), revision history, the undo stack, the
  clipboard, backups and every copy already sent are outside this string and
  all still hold the original.

Each of those limits is pinned as a test — a second copy reported as
surviving, a base64 re-encoding passing clean — specifically so they cannot
quietly become claims the crate does not support. `Verification::is_clean` is
documented as a necessary condition for a good redaction and not a sufficient
one, and a caller reporting it as "the secret is gone" has overstated it.

### Metadata inspection reports what it cannot see

`inspect` reads a `&str` and nothing else. A finding is a position and a
classification, never a value, on the argument `bp-secrets` makes about its
own `Finding`: a struct carrying the matched text would become a new place a
person's name and address live, and the caller has the document in front of
it. The offsets are bytes so `MetadataFinding::span` hands straight to
`redact`, because a conversion step between inspection and destruction is
where an off-by-one turns into a redaction of the wrong words.

The heavier metadata — a `.docx` author field, a PDF producer string, EXIF
GPS coordinates — needs a ZIP reader, an XML parser or an image parser, and
no dependency is added for any of them. `Container::hidden` reports that
boundary per format instead of hiding it: an inspector that quietly said "no
metadata found" about a `.docx` would be worse than no inspector, because the
user would believe it. It returns a slice rather than an `Option` so that
"nothing hidden" and "we did not look" cannot be the same value.
`Container::PlainText` returns empty, and says explicitly that the filesystem
entry around the file — modification times, ownership, extended attributes,
alternate data streams — is the shell's to handle and not this crate's.

## Consequences

- **What this crate cannot destroy must not be described as destroying.** It
  rewrites one string. A shell that redacts a buffer and saves over the
  original has dealt with exactly one of the places the text still lives.
  Telling the user "redacted" without telling them that is the same lie the
  black rectangle tells, and it is the shell's obligation, not this crate's.
- `Applied` deliberately holds no removed text, and `Verification` reports
  survivors as indices rather than strings. Both are records a caller may log
  or show in a panel, and a report quoting the secret it failed to remove is a
  leak wearing the clothes of a safety feature.
- `Applied` carries both original and output ranges, so a caller can map a
  highlight from one to the other without re-deriving anything. Both are on
  character boundaries.
- `PLACEHOLDER` is public so a caller can find previous redactions — to count
  them, to refuse to sign a document that still contains one, or to warn
  before publishing. A labelled redaction keeps the same prefix inside the
  same brackets, so `text.contains("[REDACTED")` finds both forms.
- The crate is pure: no clock, no IO, no configuration, no randomness. The
  same text and the same spans give the same output on every machine, which is
  what makes a redaction something a second person can check.
- `MetadataKind` is `#[non_exhaustive]` and `Exposure` is ordered, so the list
  can grow without breaking the shell and `>= Exposure::Identifying` is a
  filter a caller can write and mean. Anything automatic should demand the top
  tier: automatically deleting a timestamp out of somebody's notes is a bug
  they will not forgive.
