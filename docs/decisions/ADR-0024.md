# ADR-0024: The Audit Log

**Status:** Accepted
**Date:** 2026-08-19

## Context

specs.md section 15 lists "security audit history" beside encryption,
signatures and redaction, and ADR-0011 names *audit events* among the
artefacts a document's security policy propagates to. Neither half existed:
not the vocabulary of security-relevant events, and not the file they are
written to.

An audit log is a new place secrets live, and that is the whole hazard.
`bp-secrets` already refuses to carry the matched text of a finding on that
argument; here it has more force, because a finding is transient and a log is
on disk for ever. Every logger that ever leaked started from the same prose
promise not to record anything sensitive.

The second problem is that the log is itself a derived artefact. A
Maximum-profile document whose audit trail is a plaintext file saying "unlock
failed for document 7 at 14:02" has disclosed exactly the pattern the profile
existed to hide — when the document is touched, how often, and that somebody
is guessing at it.

## Decision

### A record is `Copy`, which is a constraint and not a convenience

A `Copy` type cannot own a `String`, a `Vec<u8>`, a `PathBuf` or a
`Box<str>`; it therefore cannot hold any text or bytes acquired at run time.
`Record`, `Event`, `DocumentId`, `ProfileLabel` and `SealFailed` are held to
it by an explicit assertion rather than by their derives alone, because a
`#[derive]` is easy to delete while chasing a compile error and the deletion
would look like a fix.

So putting a passphrase, a filename, a matched secret or a redacted span on
an audit line is not a review comment somebody might miss on a busy
afternoon. It is a build failure.

What `Copy` still permits is `&'static str` — text fixed when the code was
written — and that is the intended residue. It is why `SealFailed` carries
its reason as one: error messages are the classic route by which the thing
that failed ends up in a log file. Nothing a document contains becomes
`&'static str` by accident. A property test over the serialised form catches
whatever slips past the type.

Every `Event` payload is consequently a count, a flag or a closed enum.
`SecretScanFinished` carries how many secrets were found and not one
character of any of them; `RedactionApplied` carries `bytes_removed` and not
the removed text, which — being the text somebody chose to destroy — is the
most sensitive content this product ever handles. `SignatureVerified` carries
`valid` as a flag rather than splitting into two variants, so a caller cannot
record that a check happened without recording its answer.

### A document is a `u64`, and there is no conversion from a path

`DocumentId` wraps a number and nothing else. The obvious design is a
`PathBuf`, and the obvious design is the leak: a log naming
`Divorce settlement.bpadx` has disclosed what the user keeps, which is most
of what a strict profile was protecting. A `u64` cannot hold a filename, so
the file physically cannot say one — "opened Passwords.bpadx" is not a line
this crate can be made to write.

The session holds the mapping from id to document and resolves it for the UI,
exactly as `bp-history` keys checkpoints. A caller wanting ids to survive
into a later session derives one from a digest of the path
(`bp_crypto::stable_name`): a stable number, still not a name.

Deliberately no `From<&Path>`. An ergonomic conversion would put a path one
keystroke away from the log, and one keystroke is the whole distance the type
exists to keep.

### The destination resolves from two axes that already exist

No new `Policy` axis was invented for the log. Two of ADR-0020's seven
already answer the two questions it actually asks:

* **May anything at all be recorded about this document?** That is
  `metadata`, whose subject is what the machine writes down *about* a
  document rather than in it. ADR-0019 refused to store an extracted title on
  precisely this ground, and an audit trail is the same kind of object: a
  durable local record of a document's existence and use.
* **May a derived artefact sit on disk in clear?** That is `recovery`, the
  axis already governing the other file this product writes beside a
  document. A profile unwilling to leave an unencrypted journal is not
  willing to leave an unencrypted audit trail.

`Destination` is the three answers those produce — `PlaintextFile`, `Sealed`,
`SessionOnly` — ordered permissive-first like every `bp-security` axis, so
"tightening a profile never loosens the log" stays a comparison rather than a
table. As a table: Standard writes a plaintext file, Private writes a sealed
one, Confidential and Maximum write nothing. `Recovery::Disabled` with
metadata still permitted lands on `Sealed` rather than `PlaintextFile`,
because a profile that has switched off plaintext recovery has already stated
its view of plaintext artefacts.

Sealing goes through a `Sealer` trait rather than a dependency on
`bp-crypto`, for the reason ADR-0020 gives about `bp-security`: this crate
decides *that* a line must be sealed and something else performs it. The
implementation the shell supplies wraps the document's `.bpadx` envelope, so
an audit log is readable by exactly the people who can read the document it
describes — the correct access rule, arrived at for free.

### A policy that cannot be honoured writes nothing

A profile demanding a sealed log with no key available gets no log and a
notice, never a plaintext one. That is ADR-0020 in as many words: a security
control that quietly weakens itself is worse than an absent one, because the
user has been told it is on.

Both refusals are `Appended::NotWritten` rather than an error, because a
profile doing what it was set to do is not a failure. Only the second carries
a notice; a message for every suppressed event would train the user to
dismiss the ones that matter.

### Append-only is enforced where a process can, and the gap is named

Enforced here:

* the type offers exactly one mutation, `append`, and reading; there is no
  operation that edits, removes or truncates an entry;
* every write opens the file in append mode and never seeks or truncates,
  and writes each record as one line-plus-newline in a single call, so a
  second process appending concurrently interleaves whole entries rather than
  shredding one;
* every entry is numbered, and `open` refuses a file whose numbers are not
  the unbroken run 1, 2, 3, ..., so deleting or reordering any line but the
  last is detected and reported as tampering;
* every entry is flushed to the device before `append` returns, because an
  audit line still in the page cache when the machine loses power is exactly
  the line about the thing that went wrong.

**Not enforced, and no pretence otherwise.** A process with write access can
truncate the tail, or rewrite the whole file with consistent numbering, and
nothing inside this crate can tell. Detecting that needs a per-entry
authentication chain keyed by something the editor does not hold — a signing
key, or an append-only store the user's own account cannot rewrite. A sealed
log gets part of the way for free, since each line is authenticated by the
document's envelope and so cannot be *altered* undetectably, only removed.

Deliberately no home-rolled hash chain. specs.md section 15 forbids custom
cryptography, and a chain that looks like tamper-evidence but is not is worse
than the honest gap.

## Consequences

- Sequence numbers order the log; timestamps do not. A clock can be set
  backwards, and a log that trusted one could be reordered by changing the
  system time. Timestamps are whole seconds with the UTC offset kept, so a
  line written at 14:02 local still reads as 14:02 after the user travels.
- `Record` has no public constructor. A shell able to supply its own sequence
  number is a shell able to forge the order of history, which is the one
  thing an append-only log is for.
- Callers must pass `security.policy_under(privacy)`. A caller resolving a
  document's own policy directly is a caller Privacy Mode does not reach.
- `Event` is not `#[non_exhaustive]`, deliberately. The shell should be made
  to decide how to show a new security event; a `_` arm rendering one as
  nothing is worse than a compile error.
- A `ProfileLabel` records which profile, never the seven axes behind it.
  Writing the whole `Policy` on every line would make the log a copy of the
  security model rather than a history of decisions, and would drift the
  moment an eighth axis appeared.
- Errors name the line number and never quote the line. A log is read when
  something has already gone wrong, and an error that quotes the offending
  entry copies its contents into a terminal, a bug report or a screenshot.
- The clock is a parameter; nothing here reads the time. That is what makes
  ordering and wording settled by tests rather than by waiting.
- A file holding both plaintext and sealed lines is normal — a document whose
  profile was tightened has exactly that — and is read as such. Sealed lines
  are not silently skipped when no key is given, because a history that
  quietly showed only the readable half would hide the interesting part.
