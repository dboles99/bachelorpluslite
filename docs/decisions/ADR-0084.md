# ADR-0084: Questions Are Asked In The Window, And A Question Nobody Answered Keeps The Work

**Status:** Accepted -- built 2026-09-25 (W1-02)
**Date:** 2026-09-25
**Answers:** D22
**Amends:** [ADR-0057](ADR-0057.md) (names the one program this product can start)

## Context

Every Yes/No, Yes/No/Cancel and OK prompt in `bp-ui` is an
`rfd::MessageDialog`: the recovery prompt at startup, *save changes?* on
close, *changed on disk*, Replace All, Set as Default Editor, and the
information box. On Windows those are native. On Linux, rfd 0.17.2 draws
**none of them itself** -- it runs `zenity`:

```
grep -n 'zenity::question\|zenity::message' rfd-0.17.2/src/backend/xdg_desktop_portal.rs
```

and when `zenity` is not installed, rfd logs the error and **returns
`Cancel`** (lines 313--316 and 333--336 of the same file). Two defects follow,
and neither shows itself:

- **The recovery journal is deleted.** `lib.rs` restores on `Yes` and treats
  everything else as a decision to decline, and calls
  `journal.discard_all()`. So on a Linux desktop without `zenity` -- KDE
  often, any minimal install -- the unsaved work of a crash is thrown away at
  the next launch, by the feature that exists to keep it, with no prompt
  having been shown.
- **A window with unsaved work cannot be closed.** The close handler keeps the
  window on anything but `Yes` or `No`, which is correct for a real Cancel and
  means the close button silently does nothing when there is no dialog.

And [ADR-0057](ADR-0057.md) says this product executes nothing. Starting
`zenity` is executing something. Nothing recorded it.

## Decision

**1. Every message dialog is drawn by Slint, on both platforms.** One code
path, one look, and a dialog the Xvfb harness can drive -- which a `zenity`
window it did not start is not. `rfd` stays for the file pickers, where the
native dialog is the one users expect and a Slint replacement would be a
file manager.

**2. A question nobody answered keeps the work.** Wherever a prompt guards
something that cannot be recovered, only an explicit answer destroys it. The
recovery prompt discards the journal on **No** and on nothing else; a
dismissed, failed or absent dialog keeps it and asks again next launch. That
rule is extracted into a function that takes the answer and returns
keep-or-discard, so it has a unit test rather than a comment.

**3. The file pickers' `zenity` fallback is named, not removed.** rfd tries
the XDG desktop portal first and runs `zenity` only when no portal answers:

```
grep -n 'Using zenity fallback' rfd-0.17.2/src/backend/xdg_desktop_portal.rs
```

If that fails too, the picker returns nothing, which the product already
treats as a dismissed dialog -- so the failure costs a file dialog, never data.
**This is the one program the product can start, it is a dependency's
fallback rather than the product's choice, and ADR-0057 now says so.** A
headline claim with an unrecorded exception is trap 3; one with a recorded
exception is merely less absolute.

## What it costs

The dialogs stop looking native on Windows. That is a real regression in
polish and is accepted: one tested path is worth more than two looks, one of
which deletes work when a package is missing.

## Built

`ui/message_dialog.slint` draws the question; `src/dialog.rs` owns the
wording, a queue that puts one question on screen at a time, and the three
functions that turn an answer into an action -- `recovery`, `unsaved` and
`confirmed` -- each of which returns the destructive outcome for exactly one
input, the explicit button, and is tested for it. An answer the dialog reports
that nobody expected is read as Cancel. Every `rfd::MessageDialog` is gone;
the file pickers remain.

**A question can no longer block, so everything after one moved into a
continuation.** Slint has no nested event loop. Save, close tab, close window,
reload, Save All, Replace All and default-editor registration each ask and
hand over the rest of their work; the window's close request is answered
"stay" at once and hidden by the last answer. R011's trap 7 now says so, because
code written on the line after `ask` runs while the question is still on
screen.

**The dialog sits outside the shortcut `FocusScope`.** Shortcuts are matched
from the window down to the focused element, so inside it Ctrl+W would have
closed the tab behind the question. It claims every key, and `focus-editor`
defers to it, because `dispatch` calls that after every menu row -- the rows
that open a dialog included.

### What building it found

**The journal could not keep anything, whatever the dialog did.** Checkpoints
were files named by document id, and document ids restart at 1 in every run.
The checkpoint pass discards the journal of every *clean* document, and every
launch opens a clean Untitled as document 1 -- so within five seconds of
starting, a run deleted the previous run's `1.json`. `rfd` hid this by
blocking before any timer ran. A dialog that does not block let the timer run
while the question waited, and "a question nobody answered keeps the work"
would have been false in the first run that tried it.

So `bp_history::Journal` now writes under a session tag -- time, process id
and a per-process counter, because a process id alone is reused by a later
run (trap 5) -- and a run discards only its own files. `left_behind` is what
other runs left, including bare `N.json` files from builds before this one;
`forget` removes exactly the entries that were offered, not "all", because by
the time an answer arrives the run may have checkpoints of its own. That also
closes the half of W1-03 where two running instances deleted each other's
checkpoints. **The other half stays open**: a second instance started while
the first is running is offered the first one's live work to recover.

**A restore forgets the old entry only once this run holds the work.** The
first version forgot it straight after re-checkpointing, and review of the
pull request pointed out that `checkpoint_all` swallows a failed write -- and a
profile can refuse a journal outright -- so a full disk would have left the
restored work with no copy at all. The entries now wait in
`AppState::superseded` until a checkpoint pass holds every unsaved document,
by writing it or because it has been saved. A test pins it, and fails against
the version that forgot at once.

Two smaller defects came with it:

- **Closing a tab with Don't Save left its checkpoint on disk**, so the next
  launch offered to recover what had been deliberately thrown away. `close`
  now discards it, and so does Don't Save when the window closes.
- **A restore sat beside an empty Untitled.** The startup blank is now closed
  after a restore the same way the command line closes it.

### Verification

- `dialog.rs`: nine tests, among them that an unknown answer is never a
  Decline, that Cancel keeps last session's work and leaves a document open,
  and that overwriting a changed file is never the default.
- `bp-history`: five new tests, four of which fail against the old id-only
  file naming -- watched failing first.
- **`scripts/drive-recovery-xvfb.sh`**, on a machine without `zenity`: crash
  with unsaved work, then relaunch and leave the question unanswered for two
  checkpoint passes, then Escape, then Restore, then Discard, checking the
  journal on disk after each. It passes on both surfaces. **Against the build
  before this change it fails at the second step**: one relaunch, one
  unanswered question, and the work is gone.
- Driven by hand under Xvfb, on both surfaces: with the unsaved-changes
  question up, `Q Q Ctrl+S Ctrl+W Backspace Delete` changed nothing; Escape
  returned the caret; Don't Save closed the tab and wrote nothing. A window
  close request (`WM_DELETE_WINDOW`, as a window manager's button sends)
  with two unsaved documents stayed open on Escape, then asked about each in
  turn, saved the first and discarded the second, and exited. An info box
  opened by clicking a menu row -- R011 trap 9's race -- held the caret, and
  typing after Escape landed in the document.

### Conceded

- **The dialogs no longer look native on Windows**, which was accepted above.
  With it goes one convenience: a Windows message box's text can be copied
  with Ctrl+C, and this body cannot be selected. Help ▸ Report a Problem
  already puts the diagnostics on the clipboard, which is what copying was
  mostly for.
- **Windows was not driven.** It is the same Slint code on both platforms,
  and hosted CI builds it; the manual pass should still close a window with
  unsaved work there once.
- Keyboard Shortcuts is aligned with spaces in a proportional font, as it was
  in the native box. Cosmetic, and left.
