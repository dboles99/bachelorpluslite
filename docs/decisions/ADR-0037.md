# ADR-0037: Phase 9 Is A Related-Notes Panel And Duplicate Detection

**Status:** Accepted
**Date:** 2026-08-21

## Context

ADR-0019 built `bp-storage` and deliberately stopped at the schema: SQLite,
append-only migrations, metadata never content, and nothing wired in,
because "recording something before deciding what it is for is how a
metadata store becomes a liability." That was the right call at the time --
schema v1 covers documents, tags and the join between them, and the crate's
own module documentation already names the target questions it was built
toward: "which notes are related, which are near-duplicates, what is tagged
what." What stayed open was which of those the product actually ships, and
what a user sees for it. 721 lines and 21 tests have had no answer to react
to since.

## Decision

**Phase 9 is both a related-notes panel and duplicate detection**, built on
the schema ADR-0019 already shipped.

- **A related-notes panel** surfaces other documents in the store connected
  to the one open now -- by shared tags at first, since that join already
  exists in schema v1; a similarity measure beyond exact tag overlap is later
  work, not a blocker on shipping the panel with what the schema already
  gives it.
- **Duplicate detection** flags when a document being saved is a near-match
  for something already recorded, at save time rather than as a standing
  background scan -- consistent with `record_document` already running on
  the save path under ADR-0020's policy gate, so duplicate detection extends
  a check that already happens rather than adding a new one.

Both read from the one store; neither needs its own schema. They ship
together because a related-notes panel with no way to notice the note it is
about to become a near-duplicate of is half the feature ADR-0019's own
module documentation was written toward.

## Consequences

- D3 leaves `project/DECISIONS_NEEDED.md`.
- **Not yet implemented.** This closes the product question ADR-0019 left
  open; the wiring, the UI, and any schema addition a similarity measure
  beyond tag overlap needs are phase 9's own work, not recorded as done here.
- `bp-organize`, named as blocked on this in the roadmap, is unblocked by
  this decision but still needs its own design pass for how the two features
  are presented -- a panel, a menu, a status-bar affordance -- which this ADR
  does not settle.
- `record_document`'s existing policy gate (ADR-0020: `PathOnly` drops the
  title, `Disabled` records nothing) governs both features identically,
  because both read the same rows that gate already protects. Nothing about
  the security half changes.
