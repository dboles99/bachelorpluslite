# ADR-0038: Notebook Mode Is A Lightweight, One-Cell-At-A-Time Utility

**Status:** Accepted
**Date:** 2026-08-21

## Context

`bp-notebook` (3,627 lines, 59 tests) is deliberately only half of specs.md
section 12's ask: a cell model and Jupyter interchange, with no interpreter,
process, channel or thread anywhere in it. ADR-0025 already settled the
format questions and, alongside them, the security rule that constrains
everything downstream -- a cell can only run behind a [`UserGesture`] that no
parsed file, no default and no clone can produce.

What ADR-0025 left open, because it is a different question, is what running
a notebook *looks like* to the person doing it: a full always-on notebook
surface with live outputs and a persistent kernel session, or something
smaller. That was phase 12's own open item, and it has stayed open since the
crate shipped -- 59 tests behind an interaction model nobody had described.

**Execution itself is not built.** The crate's own module documentation names
`bp-execution` as the crate that would run a cell, and no such crate exists in
this workspace yet. This ADR settles the shape of the view; it does not claim
the engine behind it is ready to build against.

## Decision

**Notebook mode is a lighter utility: cells run one at a time, on request,
not a persistent live session.** A user opens a `.ipynb` document as a
sequence of cells rather than a rope, selects a cell, and asks for it to run
-- each ask its own `UserGesture`, per ADR-0025's rule -- and sees that one
cell's result. There is no standing kernel process the view keeps alive
between cells, no "run all" that fires a sequence of gestures from one click,
and no live variable inspector watching a session change underneath the
document.

This is a narrower product than a Jupyter client, on purpose. It answers "let
me check what this cell does" rather than "give me an interactive computing
session," and the narrower shape is also the one `bp-notebook`'s own security
posture already points at: a run that starts, finishes and stops is a run
whose gesture-per-cell rule reads naturally, where a persistent session would
have to answer harder questions about what "one gesture" authorises across an
open-ended sequence of later cells.

## Consequences

- Phase 12 has a described shape for the first time; `project/WORK_QUEUE.md`
  and `project/NEXT_SESSION.md` can list it as blocked on the execution engine
  rather than blocked on a decision.
- **`bp-execution` (or an equivalently-scoped crate) has to exist before any
  of this can run a real cell.** That crate does not exist yet, is not scoped
  by this ADR, and is real, separate, likely substantial work -- process
  spawning, a kernel protocol per supported language, and its own security
  review given it is the thing `bp-notebook`'s gesture rule was written to
  constrain.
- A view can be built and tested against `bp-notebook` alone before
  `bp-execution` exists -- the cell sequence, selection and layout do not need
  a real kernel to render or to test -- so the view and the engine are
  parallel-safe work once both are scoped, not a strict sequence.
- "Run all" and a persistent session are not ruled out forever; they are
  ruled out of the first shape. Revisiting either is a decision to make
  explicitly, the same as this one was, not a feature that accretes because
  nothing said no.
