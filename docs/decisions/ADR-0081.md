# ADR-0081: Two Of The Three Slint Blockers Were Never Blocked

**Status:** Accepted
**Date:** 2026-09-25
**Amends:** [ADR-0048](ADR-0048.md) (the answer to D14)
**Related:** [ADR-0018](ADR-0018.md), [ADR-0030](ADR-0030.md), [ADR-0073](ADR-0073.md)

## Context

Three things have been recorded as blocked on Slint 1.17.1 since August, and
each record says it was *checked in the dependency's source rather than
assumed*:

| | The recorded reason |
| --- | --- |
| Input-method composition | `FocusScope` rejects `UpdateComposition` and `CommitComposition` in both key handlers and exposes no callback for either |
| Drag and drop to open | the winit backend has no file-drop plumbing, and `DataTransfer` carries only plain text or an image |
| Markdown preview | *"Slint 1.17.1 has no rich-text item -- no styled runs, no spans"* ([ADR-0048](ADR-0048.md), answering D14) |

Slint 1.18.0 shipped on 2026-09-16 and 1.18.1 on 2026-09-21. The record said
all three wanted a re-check on an upgrade, so both versions' source was
downloaded from crates.io and the three claims were checked against **both**
-- against 1.17.1 as well, because a re-check that only reads the new version
cannot tell a blocker that lifted from one that never existed.

**The command that tests each claim is in this ADR**, as
[ADR-0073](ADR-0073.md) asks of any decision resting on an external fact.

## What the source says

### Input-method composition: still blocked, in both versions

`i-slint-core/items/input_items.rs` still answers both composition events with
`EventResult::Reject` in both of `FocusScope`'s handlers, in 1.17.1 and 1.18.1
alike, and there is still no callback. The record was right and stays.

```
grep -n 'Composition' i-slint-core-1.18.1/items/input_items.rs
```

### Markdown preview: never blocked by the toolkit

`StyledText` is a public element in Slint 1.17.1 -- exported from
`i-slint-compiler/builtins.slint` as `export { StyledTextItem as StyledText }`
-- and it has been since **1.15.0**, released in February. Its `text` is a
`styled-text` value, and `slint::StyledText::from_markdown(&str)` builds one
from a runtime string; it sits behind the `std` feature, which is on by
default. It renders italics, strikethrough, inline code, links, ordered and
unordered lists, underline and colour, and `link-clicked` reports a clicked
link. It does **not** render headings, tables, images, block quotes or rules.

```
grep -n 'export { StyledTextItem as StyledText }' i-slint-compiler-1.17.1/builtins.slint
grep -n 'pub fn from_markdown' i-slint-core-1.17.1/styled_text.rs
```

So ADR-0048's premise -- *bold inside a sentence is not representable* -- was
false on the day it was written, and was true of every Slint before 1.15. Its
second argument, that HTML handed to a browser would write the document to a
plaintext temporary file, was true and no longer matters: a preview drawn by
`StyledText` never leaves the window.

**This does not answer D14 the other way.** It returns it to being a question.
A preview that renders inline formatting but draws a heading as a plain
paragraph is a real product decision, and so is whether a product being
reduced to Notepad wants a preview at all. That is Daniel's, and it is asked
in `project/DECISIONS_NEEDED.md`.

### Drag and drop to open: never blocked by the toolkit

Both halves of the recorded reason are true, and together they do not add up
to a blocker.

- **The winit backend has no file-drop plumbing.** True in 1.17.1 and still
  true in 1.18.1: nothing in `i-slint-backend-winit` handles
  `WindowEvent::DroppedFile`. 1.18.0 taught `DataTransfer` to carry file
  paths, but the winit backend does not fill it from an OS drop, so
  `DropArea` still cannot see one.
- **But the application can see winit's events without the backend.**
  `slint::winit_030::WinitWindowAccessor::on_winit_window_event` registers a
  filter that is handed every `winit::event::WindowEvent` for the window
  before Slint processes it. It exists in 1.17.1, behind the
  `unstable-winit-030` feature. `WindowEvent::DroppedFile(PathBuf)` arrives
  through it.

```
grep -n 'fn on_winit_window_event' i-slint-backend-winit-1.17.1/lib.rs
grep -rln 'DroppedFile' winit-0.30.13/src/platform_impl/
```

**winit 0.30.13, the version this workspace locks, emits `DroppedFile` on
Windows, X11 and macOS -- and not on Wayland.** So a drop-to-open built this
way works on Windows 10 and 11 and on an X11 Linux session, and does nothing
on a native Wayland one. [ADR-0001](ADR-0001.md) makes Windows and Linux
equal targets; a feature that reaches half of the Linux desktops is a
decision to take knowingly, not a detail. And `unstable-winit-030` is exempt
from Slint's semver promise, so a minor upgrade may break the call -- loudly,
at compile time, which is the acceptable way for it to break.

## Decision

1. **Correct the record.** Markdown preview and drag and drop to open leave
   every "blocked on Slint" list. Input-method composition stays on it, with
   1.18.1 added to the versions checked.
2. **Drag and drop to open becomes a ready item**, with the Wayland gap and
   the unstable feature stated in it. It is not built here: it is Notepad
   behaviour and within the reduction's target, but it takes a feature on an
   existing dependency and a decision about Wayland, and neither was asked
   for in this session.
3. **D14 is reopened as a question**, not answered. See above.
4. **No upgrade to 1.18.1 in this change.** None of the three moves because of
   it, and an upgrade is a separate change with its own gate run.

   **Amended 2026-09-25:** the upgrade happened the same day, for a different
   reason -- 1.17.1 overflowed drawing a document past about 2,000 lines
   ([ADR-0083](ADR-0083.md)). None of the three answers above moved.

## Consequences

**"Blocked means checked, not assumed" was followed, and was not enough.**
`prompts/rosettas/R014_LAND.md` holds drag and drop up as the example of doing
it right -- the blocker names the file and function in the dependency that
proves it. It did. The file proved that the *backend* had no plumbing, which
was true, and the conclusion drawn was that *the application* had no route,
which was not. **A check answers the question it was asked.** Both of these
were checked where the feature was expected to live -- the drop in
`DropArea`, the rich text in `Text` -- and not where it would have to be
found if it existed somewhere else.

The habit that would have caught both: **before recording a toolkit as
blocking something, search its public API for the noun, not the mechanism.**
`grep -rn StyledText` and `grep -rn winit_window_event` each take a second.
The grep that was run instead looked for the mechanism the author had in mind.

**And ADR-0048's answer to D14 is the second accepted ADR this month found
resting on a false external fact** -- after ADR-0016's "GitHub Actions is not
available" ([ADR-0073](ADR-0073.md)). Neither was careless. Both were settled,
which is how something stops being re-read.
