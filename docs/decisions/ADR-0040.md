# ADR-0040: `bp-execution` Runs A Cell As A Fresh Subprocess, Three Languages First

**Status:** Accepted
**Date:** 2026-08-21

## Context

ADR-0038 decided notebook mode's shape: run a cell on request, no persistent
kernel session, no "run all". `bp-notebook` already builds the half of this
that is safe to build without an interpreter anywhere near it -- `RunRequest`
is inert data (`cell: CellId`, `language: CellKind`, `source: String`),
produced only from a `UserGesture` that no parsed file can construct. Its own
module documentation names the crate that would consume a `RunRequest` and
actually run it: `bp-execution`. That crate does not exist. `CellKind`
already commits this product to five executable languages -- Python, Rust,
PowerShell, SQL, Shell -- and nothing has decided how any of them run, or in
what order to build them.

This is the largest remaining gap behind a wired menu row in this product,
and it is also the most security-sensitive: everything else this session
touched reads a document or writes one under a passphrase the user chose.
This runs arbitrary code from a file somebody else may have written, which
is precisely the act specs.md section 15 and `bp-notebook`'s own type system
exist to gate behind conscious consent.

## Decision

### The execution model ADR-0038 already implies: no session, no state, no IPC

**A cell run is one subprocess, started fresh and torn down after.** No
kernel, no persistent interpreter, no channel held open between cells. This
is not a simplification made for this ADR's convenience -- it is the literal
reading of "no persistent kernel session": a cell that ran a moment ago left
no process behind for the next one to talk to, so there is nothing for a
second cell's variables to inherit from a first cell's. **This is a real,
visible limitation and not an oversight**: `import pandas as pd` in one cell
and using `pd` in the next will not work, because there is no live
interpreter still holding `pd` in memory when the second cell runs. A
persistent-session model is a different, larger decision -- a kernel
protocol, a lifecycle, a question of when a session ends -- and ADR-0038
already declined to make it. `bp-execution`'s job is to run one `RunRequest`
and hand back what happened, nothing more.

This also removes the hardest part of a real kernel protocol before it
exists to get wrong: no handshake, no message framing, no matching a
response to the request that produced it across an async channel. `stdin`
in, `stdout`/`stderr`/exit code out, one process, one cell.

### Three languages first: Python, PowerShell, Shell

Of `CellKind`'s five executable kinds, three share one shape -- an
interpreter binary already on the machine, fed source on `stdin` or via a
temp file, producing text output and an exit code. Python (`python3` or
`python`, whichever resolves), PowerShell (`pwsh` or `powershell.exe`), and
POSIX shell (`sh`, or `bash` if that is what a Linux `Shell` cell actually
means -- `bp-execution` decides which at build time, not this ADR) all fit
that shape exactly, and all three ship first.

**Rust and SQL are explicitly deferred, not attempted at a lower standard.**
Rust is `rustc`/`cargo`, a compile step distinct from a run step with its
own error class (a compile failure is not a runtime failure, and conflating
them would mean a cell that fails to parse reports the same way as one that
raises), and single-cell compilation has its own question of what a
throwaway crate looks like. SQL has no interpreter to invoke at all --
running a query means a *database*, and nothing in this product has decided
what database a notebook cell talks to, whether it is local and file-based
or something reached over a connection, and if the latter that is a network
decision ADR-0006 already says needs its own ADR and a human to write it.
Both are real future work, named honestly as not yet decided rather than
implemented badly to make `CellKind::ALL` look complete.

### What every run gets, regardless of language

- **A `UserGesture` is a required parameter to the one function that starts
  a process**, mirroring `bp-notebook`'s own pattern exactly: the type that
  proves a human asked for this is threaded through rather than checked and
  discarded, so a future caller cannot reach the process-spawning function
  without one either.
- **A wall-clock timeout**, because an infinite loop in a notebook cell is
  not hypothetical and a hung subprocess with no way to interrupt it is a
  worse failure than a refusal. The process is killed, not merely abandoned,
  once the bound is reached.
- **A cap on captured output.** A `print` in a loop that never ends produces
  unbounded `stdout`; captured output is bounded and the result says so when
  it was truncated, the same honesty this codebase already applies to a
  secret scan's summary eliding past a few findings.
- **No sandboxing beyond the gesture, and this is stated rather than
  implied.** `bp-execution` does not run a cell in a container, a restricted
  token, or a network-denied namespace -- that is a materially larger
  undertaking than this ADR scopes, platform-specific in ways this crate's
  Rust-only, no-`unsafe` posture does not currently reach, and worth its own
  decision if it is wanted. What stands between an opened notebook and code
  running on this machine is exactly one thing: `UserGesture`, and a user
  reading a cell before running it. That is the whole of the guarantee,
  and overstating it would be worse than not building the feature.

### What `bp-execution` does not do

It does not know what a `Notebook` is, does not update cell outputs, does
not decide when a run is allowed (that is still `bp-notebook`'s
`request_run*` family). It takes a language and source text -- effectively
the two fields off a `RunRequest` a caller already has -- and returns what
happened. Wiring a `RunRequest` into a call, and writing the result back
into the cell that asked for it, is `bp-ui`'s job, and is not this crate's
concern any more than `bp-crypto` decides when a document gets encrypted.

## Consequences

- `bp-notebook`'s `RunRequest::request_run_all` stays in the library --
  removing it would be re-deciding ADR-0025's API for a UI-level policy.
  ADR-0038's "no run all" is enforced by `bp-ui` simply never calling it, the
  same way a menu row that does not exist enforces "not offered" without the
  library needing to forbid it.
- **`bp-execution` is a standalone library in this pass**, tested on its own
  the way `bp-notebook` was before anything called it. Wiring a `RunRequest`
  through it into a real Run Cell menu row, and rendering a cell's output
  back into the notebook view, is separate work this ADR does not claim to
  have done.
- The no-persistent-session limitation is a real product constraint a user
  will notice on first use, not a subtlety. It belongs in whatever
  documentation eventually describes Notebook mode to a user, in the same
  plain terms this ADR states it.
- A future session choosing to build Rust or SQL support, or a persistent
  session, or sandboxing, is choosing to extend this ADR's scope
  deliberately -- each is its own decision, not a gap this one left to be
  quietly filled in.
