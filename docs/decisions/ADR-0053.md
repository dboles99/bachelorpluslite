# ADR-0053: `main` Advances By Pull Request, And The Feature Branch Is Not Retired

**Status:** Accepted
**Date:** 2026-08-22

## Context

D13 was the longest-open question in this repository — six sessions — and for
five of those it was open on a **false premise**.

The record said: *"111 commits live on the branch; `main` has none of them."*
One command disproved it. `main` is at `10b7529`, *"Merge phases 1-19 into
main (PR #1)"*, so most of the branch's history is already there; what the
branch actually holds is the work done **since** that merge. That was
corrected on 2026-08-22 and the trap it produced is now trap 6 in `CLAUDE.md`:
**a claim in the record is not a property of the repository**, and a question
nobody can act on gets re-read rather than re-checked.

Re-checked again before asking a sixth time, which is the habit that trap
exists to install:

```text
git log --oneline main..HEAD          53
git merge-base --is-ancestor main HEAD  false
```

So the real question was small: **open PR #2 now, or keep accumulating and
merge at a milestone?**

## Decision

### `main` gets this work, by pull request, now

Answered by Daniel on 2026-08-22: **yes**, and by pull request again — the
same shape as PR #1.

A pull request rather than a direct push, for the reason it was one the first
time: the merge commit is the record of what arrived and when, it gives the
diff a URL that outlives the session that produced it, and it is the only
artefact in this project that a reader who has not cloned the repository can
look at.

**A fast-forward is not available and this is not a defect.** `10b7529` is a
merge commit that exists on `main` alone; the branch has never contained it.
So PR #2 produces a second merge commit, exactly as PR #1 did, and `main`'s
history is a sequence of merges rather than a replay of the branch. That is
the intended shape, not a thing to fix by rebasing — rebasing pushed history
is forbidden by `CLAUDE.md`'s standing authorities and would rewrite commits
that are already published.

### The feature branch keeps its name and keeps going

`feat/phase-01-foundation-ui` is a misleading name — it has carried nineteen
phases of work, not phase 1 — and it is **kept anyway**. Renaming it would
break every link that points at it, including PR #1's, for no gain; the branch
is where work happens and `main` is where it lands. If that ever stops being
true, it is a decision to record then rather than a tidy-up to do now.

### What still needs a human, and this ADR does not change it

`CLAUDE.md`'s standing authority 2 grants commit-and-push on a green gate and
explicitly withholds two things. **Only one of them is now answered.**

- **Merging to `main`** — answered here: yes, by PR. An agent may *open* the
  pull request; **clicking merge stays a human's**, because it is the one act
  in this project that changes what a fresh clone gets.
- **`git push --force`, rebasing pushed history, or rewriting a commit
  somebody may already have** — unchanged, and not covered by this ADR at all.

## Consequences

- **The first clone from `main` will now get a product rather than a
  prologue.** That was the stated cost of leaving D13 open, and it was the
  only real one: nothing in daily work was blocked by it, which is precisely
  why it sat for six sessions.
- Phase 20 — packaging, signing and release — becomes the first thing for
  which "does `main` have this?" is a question with consequences. It is also
  the only phase still marked *Not started* that is not blocked on a decision.
- **The premise-checking habit is the transferable part.** D13 cost six
  sessions of re-reading and one command to settle. `project/DECISIONS_NEEDED.md`
  now carries the instruction directly: a question that has waited several
  sessions gets its premise checked before it is asked again.

## The lesson

> **An unanswerable question and an unasked one look identical in a queue.**
> D13 was neither: it was a question whose *premise* had gone stale, which
> reads like a hard decision and is really a stale fact wearing one. The tell
> is that nobody could say what would change if it were answered either way —
> and when the premise was finally checked, the answer took one message.
