# ADR-0092: A Large File Says Typing May Lag, And Names The View That Does Not

**Status:** Accepted -- built 2026-10-01
**Date:** 2026-10-01
**Answers:** D29

## Context

W1-05 measured what the default editing surface costs per key. Slint's
`TextInput` lays out the whole document again on every keystroke: about
**80 ms of processor per key at 100 KB** on a Linux release build, and it grows
with the document. At half a megabyte that is a lag anybody typing would feel;
at a few megabytes it is a key every half second or worse.

The custom surface, `--editor-view`, draws only the lines on screen and does
not have the cost. It cannot be the default, because it has no input-method
composition: nobody could type Japanese or Chinese in it, and Slint offers no
route to fix that (ADR-0018, ADR-0081).

D29 asked whether this blocks 1.0, and offered three answers: accept it and
say so, warn when a large file opens, or treat it as a blocker and look for a
fix in Slint.

## Decision

**Warn, at open, from 512 KiB, and name the view that does not lag.** Answered
by Daniel on 2026-10-01.

When a file of 512 KiB or more opens in the default surface, the status bar
says:

> Large file (1.2 MB) -- typing may lag in this view; --editor-view draws only
> the lines on screen

and nothing else changes. The file opens, can be edited and saved. Under
`--editor-view` nothing is said, because nothing would be true.

Why a notice rather than anything stronger:

- **Most large files are read, not typed in.** Logs, exports, data. A warning
  that interrupted every one of them -- a question, a refusal, a forced switch
  of surface -- would cost the many to inform the few.
- **The way out is a flag, and the notice names it**, so a person who does
  need to type in a large file learns how in the moment it matters. A notice
  that only complains is not one.
- **A fix in Slint is not this project's to schedule.** The renderer re-lays
  out what it is given; until it can be given less, the honest product is
  the one that says so.

The README states the limit, because a claim nobody reads at the moment it
bites is still owed somewhere a person looks before downloading.

## Consequences

- **512 KiB is a judgement, not a measurement of where it becomes
  unusable.** It is where the measured cost passes a few hundred milliseconds
  on the machine that measured it; a slower machine feels it sooner. Moving
  it is a one-line change in `bp-ui/src/state.rs`, `SLOW_TYPING_BYTES`.
- **The notice is the status bar's ordinary message**, so the next action
  replaces it, like every other notice. Help > Diagnostics and the size in
  Tools > File Analysis remain.
- **Fixed in passing:** files named on the command line were opened before
  `--editor-view` was applied to the session, so anything deciding by the
  surface at open time decided wrongly for them. The flag is applied first
  now.

## Verification

Two tests in `bp-ui/src/state.rs`: the notice appears at the threshold and not
below it, never under `--editor-view`, and names the flag; and opening a file
over the threshold puts it in the status bar.
