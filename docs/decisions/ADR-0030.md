# ADR-0030: A Huge Document Opens In The Custom Surface, Read-Only, In Every Build

**Status:** Accepted
**Date:** 2026-08-20

## Context

ADR-0027 built the large-file engine and the open path now classifies every
document from its metadata before a byte is read. An ordinary document opens
as it always did, a large one opens and edits with its size in the status bar,
and a huge one is refused in `Access::ReadOnlyBySize`'s own words rather than
loaded whole. Opening a 2 GB file no longer costs 2 GB.

What is missing is showing one. `bp_buffer::LargeFile` has `display_lines`,
`index_through_line`, `line_start` and `WindowReader`, all tested and
benchmarked, and connecting them means `display_lines` driving a scroll
anchor — which the `TextInput` view does not have and cannot be given.
**`TextInput` owns its own text.** There is no way to hand it a window of a
file it does not hold, and no callback through which it would ask for the
next one.

So the viewer needs the custom editor surface, and the custom editor surface
is behind `--editor-view`, which is opt-in. That produced the question this
ADR answers, and the trap in it: left undecided, what happens by default is
that **the same file opens under one flag and is refused under the other**.

### Why `--editor-view` is opt-in, and why that reason does not apply here

ADR-0018 shipped the custom view opt-in, and one thing keeps it that way:
input-method composition cannot work on Slint 1.17.1. `FocusScope` returns
`EventResult::Reject` for `UpdateComposition` and `CommitComposition` in both
its handlers and exposes no callback for either; `TextInput` is the only item
in the toolkit that consumes them. Without it, CJK entry does not work at all.

That is a statement about **typing**. A viewer for a document that is served
from disk in chunks is read-only — `Access::ReadOnlyBySize` is its name — and
a read-only surface accepts no composition because it accepts no text. The
one reason the flag exists has nothing to say about this feature.

## Decision

**A huge document always opens in the custom editor surface, read-only, in
every build, regardless of `--editor-view`.**

The flag stays a statement about which view *edits* an ordinary document. It
does not gate the viewer, and there is no build of this product in which a
huge file opens for one user and is refused for another.

### Why not opt-in-only

It would make this the first *capability* that exists only behind a flag
rather than the first convenience, and it would leave the product answering
"can I open this file" with "which flag did you start with". A limitation a
user can discover by accident is worse than one they are told about, and this
one would be discoverable only by comparing two launches.

### Why not leave it unbuilt

Nothing is broken today — the refusal is honest and names the size. But the
refusal says the chunked reader is built and *not yet* connected to a view,
and a "not yet" that stays put for long enough becomes a "cannot". The
engine, its tests and its benchmarks already exist; what is missing is the
smallest part of the work.

### What this costs, honestly

- **Two surfaces can be on screen in one session.** A user who has not passed
  `--editor-view` edits ordinary documents in `TextInput` and views a huge one
  in the custom surface. The two draw differently — the custom one has a
  gutter and reports `Ln, Col`, the other reports a line count — so a person
  opening a huge file sees the editor change shape. That is accepted, and the
  status bar has to say why: the size is already reported there.
- **Five features are still `--editor-view` only** (duplicate and move line,
  date and time insertion, go to line). This ADR does not change that; those
  need the caret in an *editable* document, which is the flag's actual
  subject.
- **The viewer inherits the custom surface's unchecked behaviours.** The
  wheel direction, drag-to-select and resize have not been driven by a person
  (`project/NEXT_SESSION.md` names them). A read-only viewer is where a wheel
  defect is most visible, because scrolling is all it does.

## Consequences

- The last piece of phase 4 is unblocked, and D11 leaves
  `project/DECISIONS_NEEDED.md`.
- `--editor-view` acquires a precise meaning it did not have: it selects the
  editing surface for documents the rope holds. It is not a switch between two
  products.
- The open path gains a third outcome beside "ordinary" and "large": a
  document that opens into a different view than the one the user configured.
  Whatever chooses the surface has to be one function with a name, not an
  `if` in two places, or the two views will drift on which sizes they claim.
- `Access::ReadOnlyBySize`'s message stops saying "not yet connected to a
  view" once it is. That sentence exists to avoid a limitation becoming
  folklore, and leaving it in place after it stopped being true would be the
  same failure in the other direction.

## Built, and measured rather than asserted

Shipped 2026-08-20. The claim this whole design rests on is that a document
the rope does not hold costs nothing to hold, and it is a claim that can be
weighed:

| Opened | Peak working set |
| --- | --- |
| a few lines of text | 31.3 MiB |
| **a 192 MiB log** | **32.1 MiB** |

**0.8 MiB for 192 MiB of document.** Debug build, software renderer, sampled
every 50 ms while the window was up. What is resident is an open handle, a
scan buffer, a sparse line index and one screen of text — which is what
`LargeFile` promised and what nothing before this had checked from outside the
crate.

The window also renders. `--renderer=platform --measure-exit` on the same file
reaches `AfterRendering` and exits cleanly, which is the one seam a test in
this repository cannot see: what the toolkit does with the rows it is handed.
The number that run prints is a debug-build figure and is deliberately not
recorded beside ADR-0017's release measurements, because a fast-looking number
from a different build is worse than none.

### What is deliberately not built

- **Ctrl+End.** The end of the file is not known until the whole document has
  been indexed, which for these documents means reading two gigabytes to
  answer one question and blocking the window while it happens. The key
  reports what it would cost instead. That is a refusal with a reason rather
  than a missing feature, and it is the honest shape until indexing can happen
  off the UI thread.
- **A total line count in the status bar.** Same cost, same answer: the
  readout says which lines are on screen (`Ln 4812006-4812035`), which is true,
  cheap, and the question a reader of a huge log actually has.
- **Find, in a document served from disk.** `LargeFile::windows` exists for
  exactly this and `bp-search` decides what a match is, so the pieces are
  there. It is a feature rather than wiring and it is not in this change.
