# ADR-0017: Startup Targets and Default Renderer

**Status:** Accepted
**Date:** 2026-08-17

## Context

specs.md section 22 asked for cold startup < 150 ms, warm < 75 ms and idle
RAM < 50 MB. The ADR-0015 spike showed the GPU-rendered shell missing those by
several multiples, which raised the question of whether the targets were
wrong, the toolkit was wrong, or the measurement was.

It was partly the measurement. "Startup" was being read as one number when it
is two very different events, and the gap between them is large:

| Renderer | Time to window | `main()` → first frame | Idle working set | Idle private |
| --- | ---: | ---: | ---: | ---: |
| GPU (femtovg) | 129 ms | 411 ms | 62.7 MB | 69.1 MB |
| Software | **36 ms** | not measurable | **19.2 MB** | **6.4 MB** |

Measured on the real application, release build, Windows 10, rustc 1.97.1.
Raw data: `artifacts/benchmarks/startup-20260817-070513.json`.

Almost all of the GPU path's cost is graphics backend and driver
initialisation, not application code. A text editor does not need GPU
compositing to draw text.

## Decision

**1. Default to Slint's software renderer.** `bp-ui` selects it through
`BackendSelector` before the first window is created. An explicit
`SLINT_BACKEND` environment variable still wins, because someone debugging a
rendering problem set it deliberately.

**2. Split the startup target in specs.md section 22**, because one number was
hiding two events:

- **Time to window < 150 ms cold** -- a window on screen, themed, with the
  document's name in the title bar.
- **Time to first interaction < 250 ms cold** -- content drawn and accepting
  keystrokes.

Idle RAM stays at < 50 MB.

## Rationale

The software renderer meets every target with room to spare: 36 ms to window
against a 150 ms budget, and 19.2 MB idle against 50 MB. The GPU path meets
neither the RAM target nor, at 411 ms to first frame, any reasonable reading
of the old cold-start target.

Splitting the target is not moving the goalposts to where the ball landed. The
two events are separately observable, a user perceives them separately, and
optimising them means different work. Keeping one conflated number would have
made a 129 ms window with a 411 ms blank interior look like a pass.

## Consequences

- **Time to first interaction is unverified for the software renderer.** Slint
  provides no rendering notifier under it, so the in-app first-frame clock
  returns `BPSPIKE_READY_UNAVAILABLE` rather than a number, and the 250 ms half
  of the target currently has no measurement behind it. This is a known hole,
  not a pass.
- **Typing latency and scroll smoothness under CPU rasterisation are
  unmeasured.** specs.md section 22 also requires imperceptible typing
  latency. If measurement shows the software renderer regresses either, the
  default reverts to the platform renderer and the RAM target is what gets
  revisited instead. That is the explicit revert condition for this ADR.
- Anything that later demands GPU compositing -- animation, video, shader
  effects in a preview pane -- conflicts with this default and needs a new
  ADR rather than a quiet flip.
- `scripts/Measure-Startup.ps1` measures the real application and reports both
  clocks, leaving the first-frame column blank where the renderer cannot
  report one. A blank is honest; a zero would not be.
