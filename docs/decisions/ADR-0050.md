# ADR-0050: D4's Review Is Prepared, And The Format Had No Test That It Still Opened

**Status:** Accepted
**Date:** 2026-08-22

## Context

**D4 has been answered for five sessions and unstarted for five sessions.** An
outside review of `bp-crypto`'s `.bpadx` envelope, agreed *before phase 15
trusts real documents to it*, has sat at the top of the "largest unstarted
work" list while every queue item in front of it was finished and the queue
emptied three times.

The reason it never moved is worth naming, because it is not laziness and it
is not difficulty. **An agent cannot discharge D4** — a reviewer inside this
session is not an outside one — so every session correctly declined to do the
thing, and then did nothing *else* about it either. A task that cannot be
completed and can be substantially prepared gets treated as a task that cannot
be started.

`project/NEXT_SESSION.md` §3a broke that by asking a different question: not
"can this session review the envelope" but **"what would make a reviewer's
hour cheap?"** That has an answer, and the answer is the artefact below.

Writing it required reading the composition end to end, as a stranger would.
That is where the second half of this ADR came from.

## Decision

### 1. `docs/architecture/BPADX_ENVELOPE_REVIEW.md` is the brief

One document, aimed at somebody who has never seen this repository, holding
four things:

- **The composition written out** — the byte layout with offsets, how the key
  is derived, how nonces and additional authenticated data are constructed,
  and every bound a reader applies to a header it has not yet authenticated.
- **The four call sites**, because a composition is only as sound as its uses,
  and one of them — `bp-audit`, sealing one whole envelope per appended log
  line — stresses the design in a way a reviewer should attack.
- **A self-audit against fourteen standard pitfalls**, each answer naming the
  test that would fail if the claim stopped being true, and each *unanswered*
  one saying so plainly. Four are conceded rather than mitigated -- no key
  commitment, no domain separation, no padding, no streaming API -- and a
  further two are positions taken rather than gaps, listed in the brief's §7.
- **Ten questions, stated explicitly**, so a reviewer is not left inferring
  what is being asked.

**The rows with no test behind them are the point of the exercise, not an
embarrassment to be smoothed over.** A brief that claimed fourteen for
fourteen would be a brief a reviewer stops trusting the moment they find the
first gap themselves.

`SECURITY_MODEL.md` is the intent and ADR-0021 is the reasoning; this is the
artefact, and it links to both rather than restating either.

### 2. Nothing tested that a document written by an earlier build still opens

Found while writing §5, by asking of every claim what would fail if it stopped
being true — trap 3, applied to ADR-0021's own opening sentence: *"A document
written today has to open in ten years, on the other platform, by a build
nobody has written yet."*

**Nothing anywhere would have failed.** Every round-trip test in the
workspace — `bp-crypto`'s own, the integration tests, and the property test in
`fuzz/tests/envelope.rs` that seals arbitrary plaintexts under arbitrary
options — **seals and opens with the same build**. That proves the writer and
the reader agree with each other. It cannot prove either agrees with what is
already on somebody's disk.

So a change that altered the header layout, the additional authenticated data,
the nonce construction or the Argon2id invocation *coherently on both sides*
would have passed the entire suite and both gate legs, and silently orphaned
every document ever written. The one property the format exists to provide was
the one property nothing checked.

**The vectors were already there.** `fuzz/corpus/envelope/` has held
`sealed.bpadx`, `sealed-aes.bpadx` and `sealed-multichunk.bpadx` since the
corpus was seeded: real envelopes, checked into git, sealed under a known
passphrase over known plaintext. `the_corpus_is_survivable` fed all three to
`open` and **discarded the result**, because a survival harness asserts
survival. The assertion that would have caught a format break was one line
away and nobody had written it.

Two tests now say it:

- `a_document_sealed_by_an_earlier_build_still_opens` — all three vectors, to
  the exact bytes they were sealed with;
- `an_earlier_builds_document_does_not_open_under_the_wrong_passphrase` — the
  cryptographic claim the survival harness deliberately does not make.

They live beside the corpus rather than in `bp-crypto`, so the bytes have one
home. **The failure message says what a failure means**: the format changed, and
that is either a deliberate version bump — in which case this build must still
read version 1 — or a regression that has orphaned every existing document.

### 3. The fuzz workspace was still documenting a ceiling that had been lowered

[ADR-0035](ADR-0035.md) lowered the pre-authentication Argon2id ceiling from
1 GiB and 64 iterations to 256 MiB and 16. `fuzz/` never followed, in three
comments, a doc comment and a README table.

That is not merely stale prose. `the_declared_kdf_cost_is_paid_before_anything_is_authenticated`
swept memory costs of 512 MiB and 1 GiB and a pass count of 64 — **all three
past the ceiling, and therefore all three measuring an instant refusal rather
than the work.** The printed numbers were real; they were measuring the wrong
thing, and the README's headline of *"roughly 75 seconds and a gigabyte of
resident memory per attempt"* described a bound the code stopped enforcing a
session earlier.

The sweeps are now pinned to `KdfParams::validate`'s actual bounds, and the
control moved from 4 GiB — sixteen times past the ceiling — to **one KiB
past**. A test that refuses 4 GiB says nothing about where the refusal starts;
a bound is only demonstrated at its edge.

## Consequences

- **D4 becomes an hour of somebody's time rather than a project**, which was
  the whole objective. It is still not discharged, and this ADR does not claim
  it is.
- **Regenerating `fuzz/corpus/envelope/` now has a consequence**, and it is the
  one thing that would make the golden-vector test pass vacuously. The
  seeder's own header already warned it is not idempotent there; the brief and
  the test's doc comment now say what that warning is protecting.
- **Three questions in the brief are live design questions**, not rhetorical:
  key commitment, domain separation between the four kinds of secret sharing
  this construction, and whether 128 bits of salt is the right place to rest
  the whole of the cross-file `(key, nonce)` guarantee. If a reviewer answers
  any of them "no", the answer is an ADR and a format version.
- **The brief will drift**, like every document describing code. It names
  tests by function name for exactly that reason: a renamed test is a
  `cargo test` away from being noticed, where a paraphrased claim is not.

## The lessons

Both are recorded in `DECISIONS.md`; they are here because this is where they
were learned.

> **A round trip through one build is not evidence about another build.** Seal
> and open agreeing with each other is a weaker claim than it reads as, and it
> is the claim almost every format test in almost every repository actually
> makes. The test that means something is a byte vector somebody committed
> before the change.

> **A task that cannot be finished can usually be prepared, and "I cannot do
> this" is not the same as "there is nothing to do."** D4 waited five sessions
> because every session asked whether it could review the envelope instead of
> asking what the review would need.
