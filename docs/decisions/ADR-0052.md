# ADR-0052: Pressing Enter Twice In The Find Box Replaced The Match With A Line Break

**Status:** Accepted, and **confirmed in the window on 2026-08-22** by Daniel,
who had the foreground this session did not.
**Date:** 2026-08-22

## Context

[ADR-0051](ADR-0051.md) left three rows of `project/NEXT_SESSION.md` §3b
undone, one of them Find Next/Previous on a document taller than the window.
Driving it found the worst defect this project has had since a passphrase was
typed into the open document.

**Find Next silently edits the document.** The whole reproduction is: open
Find, type a query, press Enter twice.

## What was observed

A 601-line fixture with the token `MARKER` on lines 100, 300 and 500. Five
captures, `-Keys "^f","MARKER","{ENTER}","{ENTER}","{ENTER}"`:

| After | Find bar | Document |
| --- | --- | --- |
| typing `MARKER` | `1 of 3`, view at line 100 | clean, 601 lines |
| Enter #1 | `2 of 3`, view at line 300 | clean, 601 lines |
| Enter #2 | `2 of 3` — unchanged | **dirty, 602 lines**; line 300 split, `MARKER` gone |
| Enter #3 | `2 of 3` — unchanged | **603 lines**; another break |

The match is *replaced by a newline*, which is what typing Enter into a text
widget with a selection does. It then keeps inserting, one per press.

**Three things make this worse than the line count suggests.**

- **The bar keeps inviting the keystroke that is doing the damage.** It stays
  open, still reads `2 of 3`, and Enter is how a user asks for the next match.
  The counter never advances again, so the interface is simultaneously
  ignoring the input and acting on it.
- **The evidence is off-screen.** The caret is at the match, and the match is
  wherever the reader last jumped to; the only signals are the dirty dot and a
  line count. **A fixture that fits on one screen cannot show this at all** —
  the same reason four manual passes missed a Find defect on 2026-08-21, and
  the reason a 601-line fixture is now a fixture rather than a one-off.
- **Nothing stops it reaching disk.** Ctrl+S after this saves the damage.

Go to Line has the identical shape and was never observed failing -- it was
fixed on the reasoning below and confirmed only after the fix, which is the
weaker of the two orders and is said so plainly.

## The cause, which is a comment rather than a bug

`dispatch::select` sets the selection and then moves focus into the editor.
Its doc comment gave the reason:

> `select` is for a completed "jump to this now" action -- Find Next/Previous,
> Go to Line, and clicking a cross-file search result all move focus into the
> editor on purpose, because **each of those is a single deliberate jump the
> user makes once**.

Two of those three are not made once. They are made repeatedly, from a bar
that stays open **on purpose** — and Go to Line's own call site says so, three
lines from the call:

> The bar stays open: going to a line is often the first of several, and
> closing it would make the second one two keystrokes further away.

**Two claims about one call, in direct contradiction, sitting three lines
apart for as long as nothing asked.** That is trap 4, with the twist that both
claims are about *design* rather than behaviour, so neither was the sort of
thing a test would have been written for.

The machinery to do it correctly already existed and was one function away.
`preview_match` set the same selection and left focus alone, and its own
comment explained the hazard precisely — for the *typing* case only:

> `select`'s focus-stealing would send the very next character typed into the
> document instead of the box.

That sentence is true of Find Next too. It was written about one caller and
never asked of the others.

## Decision

### `reveal` is the default; `select` is the exception

`preview_match` is renamed **`reveal`** — it selects a range and scrolls it
into view, and it never touches focus. The name stops being about previewing,
because it was never really about previewing: it is about not taking something
that belongs to somebody else.

`select` keeps the focus-taking and is now documented as the narrow case: use
it when the action came from somewhere that is not a text box, so there is no
box a caret can be stolen from.

| Caller | Now | Why |
| --- | --- | --- |
| Find box, per keystroke | `reveal` | unchanged; this is the one that already worked |
| **Find Next / Previous** | **`reveal`** | the bar stays open and Enter means "next" |
| **Go to Line submitted** | **`reveal`** | the bar stays open, by a decision recorded at the call site |
| Cell outline row clicked | `select` | a panel click; no box holds the caret |
| Cross-file result clicked | `select` | the same |

**The two panel paths are deliberately untouched.** An earlier attempt at this
put the rule inside `select-range` in `app.slint`, keyed on `find-open ||
goto-open` — which would also have changed the cross-file result path, because
a folder search leaves the find bar open behind its results panel. That is a
behaviour change on a path this session could not observe, and guessing at one
is how a fix becomes a regression. Routing the three bar callers to a function
that already existed changes nothing else, and needs no Slint change at all.

### Focus is deferred, not lost

Both bars restore it: `find-bar`'s and `goto-bar`'s `closed` handlers each
call `focus-editor()`, and Escape does the same for both. The caret returns
when the user is finished with the box instead of while they are still typing
into one that is still on screen.

This is also the rule `focus-editor-soon` already states — *a bar that holds
the caret outranks anything that merely wants it* — whose own doc comment
calls the guard "the whole of the difference between this and a defect". The
rule was written down, justified, and applied in one place; `select` was the
path that did not know about it.

## Verification, and why it took two people

**Both halves are now confirmed.** The defect by driving, the fix by Daniel
running the two sequences below at the keyboard on 2026-08-22 — the line count
held at 601 and the document stayed "Never saved", and the second Go to Line
landed on 500 rather than typing it into the document.

**What follows is why this session could not do the second half itself**, kept
because the constraint will recur and the wrong response to it is worse than
the delay.

The desktop lost its foreground window partway through the session —
`GetForegroundWindow()` returned 0 and still did after a four-minute wait — so
`SendKeys` became unavailable, and with it every keyboard path. Posted clicks
still work; Enter is not a click.

Verifying a *focus* fix through a channel with different focus semantics would
prove nothing, and a negative result would be indistinguishable from the
foreground problem — which is precisely the ambiguity ADR-0049 was written
about, and the reason a defect report was once filed and withdrawn. So this
was not attempted.

**The gate cannot settle it either.** This is the seam `CLAUDE.md` names as
the one no test can catch — what a toolkit does with what it is handed — and
it is now the sixth defect to live there.

**The thirty-second confirmation, which is what was run:**

```powershell
./scripts/Drive-Window.ps1 -File <a document taller than the window> `
    -Keys "^f","<a token in it>","{ENTER}","{ENTER}","{ENTER}" -Out ./shots -Kill
```

The line count in the status bar must not change, and the document must still
read "Never saved". Then the same with `-Keys "^g","300{ENTER}","500{ENTER}"`:
the second jump must land on line 500 rather than typing `500` into the
document.

## Consequences

- **Find Next and Go to Line no longer hand the caret back at all**, so a user
  who wants to edit at the match must close the bar first — Escape, or its ×.
  That is one keystroke, it is what every mainstream editor does, and it is
  the direction that cannot destroy text.
- `preview_match` is gone by that name. Anything reaching for it wants
  `reveal`.
- **The 601-line fixture earns a permanent place.** Two sessions running, the
  defect of the session was invisible on a document that fits on one screen.

## The lesson

> **A comment that enumerates its cases is asserting something about every one
> of them.** "Find Next, Go to Line, and a cross-file result are each a single
> deliberate jump the user makes once" reads as an explanation and is really
> three claims, of which one was true. It survived because a list in prose
> looks like description rather than specification — and because the call site
> that contradicted it was three lines away, close enough that anyone reading
> either had already stopped reading the other.
