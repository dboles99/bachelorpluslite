# ADR-0020: The Security Profile Model

**Status:** Accepted
**Date:** 2026-08-19

## Context

ADR-0011 says security policy propagates from a document to every derived
artefact, and lists them: autosave, recovery journal, revision history,
clipboard persistence, semantic metadata, embeddings, temporary files, audit
events and network eligibility. specs.md section 15 names five per-document
profiles — Standard, Private, Confidential, Maximum, Custom.

Neither says what a profile *is*. That gap is now the largest structural one
in the product, and it has three dependants that are not hypothetical:

- **`bp-history` writes unsaved document text to disk in plaintext.** Running
  today. Its module header already says the profile is what should govern it.
- **`bp-clipboard` holds copied text in memory** for up to `MAX_ENTRIES`
  entries, with no clearing policy. Running today.
- **`bp-storage` is built, tested and deliberately unreachable** (ADR-0019),
  because recording a document's extracted title puts a plaintext index of
  what the user writes about on disk.

The first two are *running*; the third is *waiting*, which is the better
failure mode and the reason it was left unwired. None of them can be fixed
without first deciding what a profile permits, because each fix is a policy
choice wearing an implementation.

## Decision

### A profile resolves to a policy; the policy is what code reads

`bp-security` gains a `Policy`: one value per axis, and one function —
`Security::policy()` — that every caller goes through. Nothing branches on a
profile's *name*. A profile is a name for a set of answers, and code that
matched on the name would have to be revisited every time a profile was added
or a Custom one was configured.

### Seven axes, each with a reader that exists or is specified

| Axis | Values, permissive first | Read by |
| --- | --- | --- |
| `recovery` | `Plaintext`, `Encrypted`, `Disabled` | `bp-history` |
| `clipboard` | `Persistent`, `InMemory`, `Disabled` | `bp-clipboard` |
| `metadata` | `Summary`, `PathOnly`, `Disabled` | `bp-storage` (ADR-0019) |
| `embeddings` | `Cloud`, `Local`, `None` | phase 10 |
| `network` | `Allowed`, `Denied` | phases 8 and 10 |
| `temporary_files` | `Allowed`, `Denied` | `bp-files`, `bp-data` |
| `zeroise` | `Off`, `On` | specs.md §15, sensitive-memory wrappers |

Seven and not more. Every axis here has a named reader; an axis with no reader
is a guess about a future feature, and a policy field nothing consults is
worse than absent because it reads as a guarantee.

### Standard is exactly today's behaviour

Adopting the model changes nothing until somebody chooses a different
profile. That is deliberate: a policy layer added to a working product either
lands as a no-op or lands as a flag day, and a flag day here would mean
silently disabling recovery for every existing user.

It also means `Profile::Standard`'s row is a description of the current
product, and any drift between the two is a bug in one of them.

### The named profiles are monotonic

Standard, Private, Confidential and Maximum are ordered, and each is at least
as restrictive as the one before it **on every axis**. The values of each axis
are ordered permissive-to-strict so this is checkable rather than asserted,
and it is checked.

This is the property that decays. The failure is specific and dull: somebody
adds an eighth axis, fills in Standard and Maximum because those are the
interesting ones, and leaves Private quietly more permissive than
Confidential on that row. A user who moves *up* a profile then loses a
guarantee. Nothing else in the design catches that.

`Custom` sits outside the chain by definition — it is an explicit `Policy`,
and constraining it would make it not custom.

### What this does not decide

**Which network destinations are acceptable when `network` is `Allowed`.**
That is a separate decision and is deliberately not encoded here. Phases 8 and
10 both imply sending document content somewhere, and the acceptable-provider
question has not been answered. `network: Allowed` means "this profile does
not forbid it"; it does not mean any particular provider is approved. A
default provider list baked in here would be an answer nobody gave.

**How a document acquires a profile.** Whether it is chosen per document,
inherited from a folder, implied by `.bpadx`, or defaulted from config is a
product question that wants its own ADR once there is a UI to set it.

**Encryption itself.** `recovery: Encrypted` names a requirement; `bp-crypto`
and ADR-0011's envelope work (phase 15) supply it. Until then a profile
requiring encryption is refused rather than silently downgraded — see below.

## Consequences

- Every feature that persists anything derived from a document consults
  `Policy` first. "It only went to a temp file" was already not an exemption
  under ADR-0011; now there is a field that says so.
- **A policy that cannot be honoured must fail loudly, not degrade.**
  `recovery: Encrypted` before `bp-crypto` exists means the journal is
  disabled and the user is told, not that it silently writes plaintext. A
  security control that quietly weakens itself is worse than one that is
  absent, because the user has been told it is on.
- The three dependants each become a bounded piece of work with a decision
  already made, rather than a design question.
- `Profile::Standard` is load-bearing documentation. Changing the product's
  default behaviour without changing that row makes the model lie.
- ADR-0019 (`bp-storage` unwired) gets its answer from `metadata`, and can be
  revisited on that basis rather than reversed by hand.
