# ADR-0058: A Hash Manifest Nobody Verifies Is Deleted, Not Regenerated

**Status:** Accepted
**Date:** 2026-08-29
**Related:** [ADR-0054](ADR-0054.md), [ADR-0050](ADR-0050.md), [ADR-0057](ADR-0057.md)

## Context

`metadata/repository_manifest.json` was written by the commit that scaffolded
this repository. It is 911 lines: a project name, a `generated_at` of
2026-08-16, an absolute `target_path` naming one machine's `G:\` drive, and
181 objects each carrying a path, a byte count and a sha256.

It has never been regenerated, no script exists that could, and **nothing in
the workspace reads it** -- `grep -r repository_manifest` over every `.rs`,
`.ps1` and `.md` in the tree returns the file itself and nothing else.

It was found while sweeping the record for ADR-0057, which is the only reason
anybody looked inside it. Measured against the tree it claims to describe:

| | |
| --- | ---: |
| Entries in the manifest | 181 |
| Files the repository actually tracks | 456 |
| Entries whose sha256 still matches | 79 |
| Entries whose sha256 is **wrong** | 86 |
| Entries whose file no longer exists | 16 |

**102 of 181 entries are false and 275 files were never listed at all.**

## Decision

**Delete it.** Do not regenerate it, and do not wire a regeneration step into
the gate.

Deleting rather than fixing, because fixing presumes the artefact has a job.
It does not have one that anything in this repository needs:

- **Integrity of what ships** is [ADR-0026](ADR-0026.md)'s and
  [ADR-0031](ADR-0031.md)'s: a detached Ed25519 signature over a document,
  with a sidecar, verified by `bp-integrity`. That is a real mechanism with a
  real verifier and tests behind it.
- **Integrity of the release** is [ADR-0055](ADR-0055.md)'s:
  `scripts/New-Release.ps1` writes checksums beside each archive, every run.
- **Integrity of the source tree** is `git`'s. Every object in it is already
  content-addressed by sha1 and every commit is already a Merkle root over the
  whole tree. A second, partial, hand-rolled hash list over 40% of the files
  is not an additional guarantee; it is a worse copy of one that is already
  total.

`metadata/README.md` stays, and so does `artifact.schema.json`. The directory
is still where machine-readable provenance goes when something produces some;
what is removed is one snapshot that never had a producer.

## Consequences

**This is ADR-0054's licence finding, in a second place.** That ADR found
every manifest claiming `MIT OR Apache-2.0` with neither licence file in the
tree -- a claim nothing in a build reads, so nothing fails, so it survived
until a release would have shipped it. This is the same shape with the
polarity reversed: a *file* that makes 181 checkable claims, of which nothing
checks any, and 102 are wrong.

**The 79 correct rows are the hazard, not the 102 wrong ones.** A manifest
that was wholly stale would be dismissed at a glance. One that is 44% right
looks like a record with some drift in it, and invites somebody to trust a row
rather than the tree -- which is [trap 3](../../DECISIONS.md) with an
artefact instead of a comment: **a claim nothing would fail to disprove.**

**Regeneration was considered and refused as the more expensive wrong
answer.** A script plus a gate stage would make the file true and leave it
still answering no question, at the cost of a stage on every run. That is the
inverse of the test ADR-0050 argued *for*: golden vectors earn their cost
because a byte committed before a change is the only evidence an earlier
build's output still opens. A hash of a file in the same commit as the hash is
evidence of nothing.

**If provenance is wanted later, it needs a purpose first.** What would be
worth building is a record of *what a release was built from* -- commit,
toolchain, target, and the checksums `New-Release.ps1` already writes -- which
is a manifest with a reader, produced at the moment there is something to
attest. That is a decision to take when a release needs it, not a file to keep
warm in the meantime.
