# ADR-0015: UI Toolkit

**Status:** Proposed
**Date:** 2026-08-17

## Context

`PROJECT_MEMORY.md` names Slint as the leading candidate but requires that the
toolkit be benchmarked and prototyped before an irreversible commitment. The
toolkit choice constrains ADR-0009 (data-driven themes must restyle every
surface) and is measured against specs.md section 22 (cold start < 150 ms,
warm < 75 ms, idle RAM < 50 MB).

The same shell -- menu bar, tab strip, gutter, live editable buffer, two-line
status bar, four themes -- was built twice and measured under identical
release profiles. Full report: `artifacts/ui/ui-toolkit-spike-17AUG2026.md`.

| Metric | Slint 1.17 | egui/eframe 0.36 |
| --- | ---: | ---: |
| Warm launch (wall clock, median) | 588 ms | 1156 ms |
| `main()` → first frame | 443 ms | 878 ms |
| Idle working set | 61.8 MB | 153.9 MB |
| Idle private bytes | 68.6 MB | 361.1 MB |
| Release binary | 10.4 MB | 12.2 MB |

## Decision

Adopt **Slint** as the UI toolkit for BachelorPad+.

## Rationale

- Faster on startup by roughly 2× and lighter on idle working set by roughly
  2.5×, on every run, on the metrics the product is specified against.
- Theming fits ADR-0009: a `global Palette` of computed properties restyles
  every surface including text input, rather than filling a fixed set of
  toolkit-defined slots.
- API stability. egui 0.36 broke four separate APIs used by a shell this
  small (`App::update` removed, panels moved to `&mut Ui`, `TopBottomPanel`
  folded into `Panel`, `TextEdit::frame` retyped) and ships breaking releases
  roughly quarterly. Slint has held a stable 1.x API since 1.0. For a product
  with this scope, toolkit churn is a recurring tax.

egui is the better prototyping experience and the better choice for a tool
where UI iteration speed dominates. That is not this product's constraint.

## Consequences

- `bp-ui` takes a Slint dependency; `.slint` markup is compiled by a build
  script. Layout lives in a second language, and the build has a codegen step.
- **Neither toolkit meets the specs.md section 22 startup targets.** Slint
  misses cold start by ~6× and warm by ~8×, with the time going to graphics
  backend initialisation rather than application code. This ADR does not
  resolve that; it selects the better of two candidates that both miss.
  Section 22 needs either a follow-up spike on Slint's software renderer, or
  revised targets, or a split between time-to-window and time-to-interactive.
  That is tracked as a separate decision, not assumed here.
- **Linux is unmeasured.** BP-ADR-0001 makes Linux first-class and the WSL
  distro has no Rust toolchain, so the evidence behind this ADR is
  Windows-only. Confirming the ordering holds on Linux is outstanding work,
  and a large enough divergence there is grounds to revisit.
- The losing spike under `spikes/ui-toolkit/` should be deleted once this ADR
  is accepted, and the winner folded into `bp-ui` rather than left to rot as
  a parallel implementation.

## Status note

Proposed rather than Accepted: the measurements are in and the recommendation
is unambiguous, but committing the product's UI toolkit is the owner's call,
and one caveat above (Linux) is unresolved evidence rather than a known
trade-off. Flip to Accepted to proceed.
