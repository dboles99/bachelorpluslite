# ADR-0019: The Local Metadata Store

**Status:** Accepted
**Date:** 2026-08-17

## Context

specs.md section 21 asks for a local metadata store, and phase 9 — related
notes, topics, tags, duplicate detection — cannot start without one. Every
question that phase asks is a query over a set of documents rather than a
lookup on one, which is what distinguishes it from the recent-files list
already in `bp-config`.

Three choices had to be made before any code existed: what to store it in,
how the schema is allowed to change, and what may go in it.

## Decision

**1. SQLite, through `rusqlite`, with the `bundled` feature.** SQLite was
already the recommendation in PROJECT_MEMORY; `bundled` is the part being
decided here. It compiles SQLite from source as part of the build rather than
linking whatever the machine happens to have.

**2. Migrations are append-only and versioned in `PRAGMA user_version`.** Each
migration runs in its own transaction with the version bump inside it. A file
whose version is *higher* than the build understands is refused, not opened.

**3. The store holds metadata, never document content.** Even a title — which
is a summary of what the user wrote — is as far as this goes until phase 14
exists.

**4. Time is a parameter.** Nothing here reads a clock.

## Rationale

`bundled` costs build time and requires a C compiler; both Windows and the
WSL Ubuntu-24.04 image the Linux leg uses already have one. What it buys is
that ADR-0001's two targets get the same SQLite version with the same
compile-time options, and that neither needs anything installed. "Works on
this machine" is not a build strategy for a product meant to be packaged.

`user_version` rather than a `schema_version` table because it needs no query
to read, cannot be dropped by accident, and — the deciding point — already
exists before any schema does, which is exactly when the first migration needs
to ask what version it is looking at.

Refusing a file from a newer build matters more than it looks. The failure it
prevents is an older BachelorPad+ opening a store it half-understands, writing
to it, and quietly corrupting metadata a newer one would have read fine.

Keeping content out is the ADR-0011 constraint applied early rather than
retrofitted. The recovery journal already writes unsaved text to disk in
plaintext and the DECISIONS log lists it as waiting on a security profile;
adding a second place with the same problem, in a file that by design outlives
every document it describes, would be repeating a known mistake on purpose.

## Consequences

- **A C compiler is now a build requirement** on both platforms. Local CI
  proves this on Windows and in WSL on every run, so a regression is visible
  rather than discovered at packaging time.
- **An applied migration may never be edited.** Changing one alters the schema
  of new databases while leaving existing ones behind, with nothing to say the
  two disagree. Mistakes get a new migration.
- **Nothing writes to the store yet**, and that is deliberate. `bp-organize`
  does not exist, and the useful thing to record — a document's extracted
  title — is precisely what ADR-0011 says a security profile should govern.
  Wiring it in before phase 14 would put a plaintext index of what the user
  writes about on disk, which is a decision to take deliberately rather than
  as a side effect of building the table it would go in.
- Schema v1 covers documents, tags and the join between them. The rest of
  specs.md section 21's list — versions, entities, embeddings, security events
  — arrives with the phases that consume it, for the same reason the crate map
  does not create empty crates.
- Foreign keys are enabled per connection, because SQLite disables them by
  default and every `ON DELETE CASCADE` in the schema is inert without it.
  There is a test asserting the pragma actually took.
- WAL journalling is on, so a reader can run while a writer works. That is a
  precondition for indexing off the UI thread, which phase 9 will want.
