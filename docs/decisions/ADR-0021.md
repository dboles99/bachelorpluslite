# ADR-0021: The `.bpadx` Envelope

**Status:** Accepted
**Date:** 2026-08-19

## Context

specs.md section 15 requires encrypted `.bpadx` documents with passphrase
protection, Argon2id and an established AEAD. ADR-0011 forbids custom
cryptography and, as clarified on 2026-08-19, draws the line at *implementing*
primitives rather than *composing* them: no off-the-shelf format supplies the
envelope this product needs, so the layout, the version scheme and the AEAD
framing are ours to specify.

ADR-0020 already depends on this. Two of the four security profiles require an
encrypted recovery journal, and until `bp-crypto` exists the journal refuses
rather than degrading — visibly, and by design.

A file format is the most expensive kind of decision in this product. A
document written today has to open in ten years, on the other platform, by a
build nobody has written yet.

## Decision

### Two AEADs, chosen per document and recorded in the envelope

`XChaCha20-Poly1305` and `AES-256-GCM`. The envelope names which was used, so
a reader supports both and a writer picks one.

XChaCha20-Poly1305 is the default. Its 192-bit nonce makes a random per-file
nonce prefix safe without ceremony, and it is constant-time in software on any
CPU — including the ones without AES instructions, which is where a
software-only implementation of AES leaks timing.

AES-256-GCM is offered because it is hardware-accelerated almost everywhere
and is the answer to compliance questions that will eventually be asked. Its
96-bit nonce leaves less room, which the chunk numbering below accounts for.

Carrying both costs two code paths and two sets of failure tests. That is the
price of not having to break the format later to add the one we did not pick.

### Argon2id, at the OWASP baseline, recorded per document

19 MiB memory, 2 iterations, 1 lane. Roughly 50–100 ms to unlock, so opening a
document feels immediate.

The parameters live **in the envelope**, not in the code. That is the whole
point: raising them later strengthens new documents without orphaning old
ones, which is impossible if the reader assumes a fixed cost.

A reader must therefore treat the stored parameters as untrusted input. A file
claiming 64 GiB of memory cost is a denial-of-service, not a strong document,
and is refused by a bound rather than attempted.

### Chunked, with the position bound into every chunk

Fixed-size segments, each sealed separately. Three reasons, in order of how
much they matter:

1. **Integrity has to cover position, not just content.** Each chunk's
   additional authenticated data carries the whole header, the chunk's index,
   and whether it is the last one. Without the index, chunks can be reordered
   or duplicated and every one still authenticates. Without the last-chunk
   flag, a file can be truncated and the remainder still authenticates — which
   is silent data loss that looks like a successful decrypt.
2. A document larger than memory can be written and read, which phase 4
   requires regardless.
3. Corruption stays local: one damaged chunk is one damaged region, not a
   whole document that will not open.

Nonces are a random per-file prefix followed by the chunk index as a big-endian
counter. The key is unique per file — a fresh random salt each time — so the
(key, nonce) pair cannot repeat across documents, and the counter guarantees it
cannot repeat within one.

### The header is authenticated, not merely present

Because the entire header is in every chunk's AAD, an attacker cannot change
the suite, the KDF parameters or the chunk size without every chunk failing to
authenticate. A header that is only *read* is a header that can be edited to
downgrade the document.

### Platform key protection is phase 16

Passphrase only for now. ADR-0011 already says DPAPI, Windows Hello and the
Linux Secret Service are a convenience layer over the passphrase and never a
replacement, so deferring them changes nothing about the format — and they are
the part with the most per-platform code.

### Dependencies

All named here because dependency choices are ADR material in this
repository. RustCrypto throughout, plus `ed25519-dalek`, which is the
conventional and audited Rust Ed25519:

| Crate | For | Why this one |
| --- | --- | --- |
| `argon2` | Argon2id | The reference Rust implementation; RustCrypto |
| `chacha20poly1305` | XChaCha20-Poly1305 | Same |
| `aes-gcm` | AES-256-GCM | Same |
| `getrandom` | Salts and nonce prefixes | The OS CSPRNG, no userspace pool to get wrong |
| `zeroize` | Wiping key material | specs.md §15 asks for sensitive-memory wrappers |
| `sha2` | Document hashing, and naming journal files by a digest of their path | Same family; not used for key derivation, which is Argon2id's |
| `ed25519-dalek` | Document signatures | The audited, conventional Rust Ed25519; `verify_strict` rejects small-order keys |
| `rand_core` | Seeding a signing key | Already in the tree; used through its fallible API, never the panicking one |

Composing these is exactly what ADR-0011 permits and what it requires: none of
them is reimplemented here.

## Signatures and hashes (added 2026-08-19)

The same "compose, never implement" rule, applied to specs.md §15's hashing
and signature requirements. Three choices worth recording, because each has a
cheaper alternative that is worse:

**Detached signatures, not embedded.** A `.sig` beside the document rather
than a wrapper around it. An embedded signature changes the document's bytes,
so signing would alter the thing being signed and every other program would
see a file it no longer understands. The cost is that a signature can be
separated from its document by a move or a copy — which the shell has to carry
deliberately, or the signature is silently lost.

**Raw RFC 8032 encodings, deliberately unlike the `.bpadx` envelope.** The
signing key is the 32-byte seed, the verifying key the 32-byte compressed
point, the signature 64 bytes of `R || s`. No magic, no length prefix, no
version. The envelope is ours and has to be able to grow; these three are
fixed-length values pinned by a standard that will not be revised, and
wrapping them would make keys this product writes unreadable to every other
Ed25519 tool for no gain.

**`verify_strict`, not `verify`.** It rejects small-order keys and
non-canonical encodings. A signature here is evidence, and evidence has to
bind to exactly one key and one document.

**A verified signature says a key signed these bytes. It says nothing about
whose key it is.** Binding a key to a person needs a trust store this product
does not have, and any UI that renders "signature valid" as "this is from
Alice" is lying. That constraint belongs to whoever wires it.

## Consequences

- **A wrong passphrase and a corrupted file are the same event.** Both are an
  authentication failure, and no honest implementation can tell them apart —
  claiming to would mean trusting something outside the authenticated data.
  The error says both, and the tests assert that it does.
- **Every failure path is a required test**, per ADR-0011: wrong passphrase,
  flipped ciphertext bit, edited header, reordered chunks, dropped chunk,
  truncated file, unknown version, unknown suite, absurd KDF parameters.
- The format is versioned from byte 6. A reader that meets a version it does
  not know refuses by name rather than guessing at the layout.
- Recovery-journal encryption (ADR-0020's `Recovery::Encrypted`) becomes
  implementable. Until it is wired, the journal still refuses.
- `bp-crypto` performs cryptography and decides nothing about policy;
  `bp-security` decides policy and performs nothing. Neither depends on the
  other.
- Hashes and `.sig` files are artefacts derived from a document, so ADR-0011
  and ADR-0020 apply: the document's profile decides whether either may be
  written before the shell writes one.
- **A digest describes the bytes on disk, not the editor buffer.** A recipient
  computes theirs over the saved file, so showing a digest of unsaved text
  describes bytes nobody else has. Whoever wires it must refuse or warn while
  the document is dirty.
