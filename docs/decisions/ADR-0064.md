# ADR-0064: The Security Stack Leaves, And What Governed It Stays As Privacy

**Status:** Accepted
**Date:** 2026-08-30
**Implements:** [ADR-0059](ADR-0059.md) R5 — the last of the five
**Supersedes:** [ADR-0021](ADR-0021.md), [ADR-0022](ADR-0022.md), [ADR-0024](ADR-0024.md), [ADR-0026](ADR-0026.md), [ADR-0028](ADR-0028.md), [ADR-0031](ADR-0031.md), [ADR-0035](ADR-0035.md), [ADR-0036](ADR-0036.md)
**Amends:** [ADR-0011](ADR-0011.md), [ADR-0020](ADR-0020.md), [ADR-0050](ADR-0050.md)

## Context

[ADR-0059](ADR-0059.md) put the security stack last, and said why: **it is the
only removal that forces behaviour decisions in crates that stay.** R1 to R4
deleted things; this one changes what the survivors do.

Five crates go — `bp-crypto`, `bp-integrity`, `bp-audit`, `bp-redaction`,
`bp-secrets`, 13,742 lines — and `bp-security` stays, narrowed. That split was
ADR-0059's central finding: `bp-security` is not a security *feature*, it is
what decides whether the kept features record anything, and deleting it while
keeping the note layer whole would have produced **a smaller product that
knows more about its user than the larger one did.**

## Decision

**Remove the five crates, keep `bp-security`, and rename the menu.**

Deleted with them: `bp-ui`'s `state/security.rs` (2,771 lines),
`state/encryption.rs`, `audit.rs`, `passphrase.rs` and the passphrase bar's
wiring; the action ids 200–206 and 212 and `ENCRYPT_DOCUMENT`; nine dispatch
arms; `fuzz/tests/envelope.rs` and `corpus/envelope/`; and four integration
tests whose whole subject was encryption, signing, redaction or the audit log.

### The Security menu becomes the Privacy menu

Thirteen rows become seven: four profiles, two readouts and Privacy Mode.

**Renamed rather than kept**, because *Security* over four profiles and a
toggle is the kind of label that reads as a promise. What the menu now does is
tell you what this program may write down about a document, which is privacy.
The two readouts that survived are the two axes something **enforces** —
the recovery journal and the metadata store — which is ADR-0059 §4's count
made visible.

### `Recovery::Encrypted` is deleted, not degraded

ADR-0059 named this and it is the sharpest of the four forced decisions.
[ADR-0022](ADR-0022.md) sealed the journal with the document's own passphrase
for Private and Confidential. With no `bp-crypto` there is no implementation,
and there were two ways to handle that:

- point those profiles at `Plaintext` — **a journal somebody was told was
  encrypted**, silently written in clear;
- delete the variant, so those profiles now ask for `Disabled` — **no journal
  at all.**

The second, and it is not a close call: [ADR-0020](ADR-0020.md) is explicit
that a control which quietly weakens itself is worse than an absent one,
because the user has been told it is on. `Policy::needs_encryption` existed to
make exactly this fail loudly, and it is gone with the thing it guarded.

**The cost is real and is accepted knowingly**: a Private document now gets no
crash recovery. Losing unsaved work is its own harm; being told your journal
is protected when it is plaintext is a worse one.

### `.bpadx` documents become unopenable, and there is no migration

The format is gone. A document already sealed on somebody's disk cannot be
read by this build or any later one.

**No migration path is provided**, and the honest reason is that any of them
would be a lie about effort: a build that can still decrypt is `bp-crypto`
kept under another name, and a documented "decrypt before upgrading" assumes a
release cadence and an audience this project does not have. What it gets
instead is a sentence in `README.md` and this paragraph.

## What survives, and each one is a decision

**`bp-security`, at two axes and two switches.** `Profile`, `Privacy`,
`Recovery` (minus `Encrypted`) and `Metadata`. The four axes that had no
enforcing reader — `clipboard` went under [ADR-0061](ADR-0061.md), and
`embeddings`, `network`, `temporary_files` and `zeroise` are still there —
**are not removed here.** ADR-0059 said they would be, and they are left
because the Tools inspector still reports them and cutting them is a second
change with its own consequences. The doc comment on
`security_inspector_report` names which three govern nothing, so the readout is
not a claim the code fails to keep.

**`state/privacy.rs`, at 193 lines from 2,771.** The profile switch and
Privacy Mode, in a module named for what it does. A module called `security`
holding four profiles and a toggle would make the same overclaim the menu did.

**The plaintext recovery journal, untouched.** Worth stating because a survey
early in this change claimed `bp_crypto::stable_name` named *every* journal
file and that removing crypto would orphan unsaved work. **That was wrong**:
`stable_name` named only the sealed journal, and plaintext journals are
`{document_id}.json`. One `grep` settled it. It is trap 6 committed by the
person warning about trap 6, and it is recorded because the near-miss was a
whole redesign of journal naming that was not needed.

## Consequences

**Trap 7's upgrade coverage drops from four files to three.**
`what_an_earlier_build_wrote.rs` pinned committed bytes for `config.toml`,
`recent.toml`, `security.log` and a recovery checkpoint. The `security.log`
fixture is **deleted, not regenerated and not kept as a tombstone** — there is
no reader left, and a committed byte string with no reader is evidence about
nothing, which is the argument [ADR-0058](ADR-0058.md) made about a hash
manifest. The file's own header now says the count is three and why.
`fuzz/tests/envelope.rs`'s three golden vectors — [ADR-0050](ADR-0050.md)'s
whole contribution — go the same way.

**ADR-0011 becomes vacuous.** "No custom cryptography — compose vetted
primitives" cannot fail when there is no cryptography, so by the rule
[ADR-0057](ADR-0057.md) set it is recorded as removed rather than left to read
as live. It was a good rule and it was kept.

**Three fuzz harnesses become two**: `data.rs` (`bp_formats::sniff`) and
`files.rs` (`bp_files::load`). `envelope.rs` was the highest-value target in
the suite by some distance — exhaustive single-byte corruption, every prefix
of a real document, and the only assertion anywhere about a document *this
build did not write*. Losing it is the largest reduction in assurance in this
whole sequence, and it is a consequence of having nothing left to assure.

**The compiler caught a regression this change would otherwise have
shipped.** Deleting the block of dispatch arms between `ENCRYPT_DOCUMENT` and
`NEW_WINDOW` took `SET_DEFAULT_EDITOR` with it — File ▸ Set as Default Editor
would have silently done nothing. It surfaced as a dead-code warning on
`crate::default_editor::PRESET`, not as an error, which is the part worth
remembering: **a deleted arm is not a compile failure, it is a menu row that
stops working.** `no_menu_offers_a_row_that_does_nothing` does not catch it
either, because the row still has an action id.

**A label was too long and a test said so.** The new "Recorded about this
document: path, title and tags" readout was 50 characters and would have been
elided by the popup — [ADR-0049](ADR-0049.md)'s finding, mechanised, catching
its first new offender. Shortened to "Recorded: …".

## The lesson

> **The last removal in a sequence is the one that changes what stays.**

R1 to R4 were deletions: a crate left, its callers left with it, and the
survivors were untouched. R5 could not be, because `bp-security` was never a
security feature — it was the *governor* of features, and four of the things
it governed had already gone. What was left was a governor with two subjects
and a name that described its origins rather than its job.

The general form, and it is the whole argument for ADR-0059's ordering:
**a thing that decides on behalf of other things outlives them, and it should
be renamed when it does.** Keeping "Security" would have been free, and it
would have left every future reader believing this product does something it
does not.
