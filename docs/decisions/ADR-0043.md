# ADR-0043: Notebook Mode Arrives As A Run Menu Over A Literate Document, Not As A Cell View

**Status:** Accepted
**Date:** 2026-08-21

## Context

Two decisions and two crates are already built, and nothing can reach any of
them. [ADR-0038](ADR-0038.md) settled notebook mode's shape — a lightweight,
one-cell-at-a-time utility, no persistent kernel session, no "run all".
[ADR-0040](ADR-0040.md) built `bp-execution`, which runs a cell as a fresh
subprocess for Python, PowerShell and Shell, with an output cap, a wall-clock
timeout, and a `UserGesture` required to start a process at all. `bp-notebook`
parses `.ipynb`, models eight cell kinds, and produces a `RunRequest` that
only a `UserGesture` can obtain.

**Nothing in `bp-ui` names either crate.** That is roughly 9,500 lines with
no route to a person, and `project/NEXT_SESSION.md` has called it the largest
remaining gap in the product for three sessions.

What has been missing is not effort. It is an answer to *what the mode is
for*, because ADR-0038's central limitation decides which uses are honest:

> `import pandas as pd` in one cell and using `pd` in the next will not work,
> because there is no live interpreter still holding `pd` in memory when the
> second cell runs.

That is fatal to exploratory data analysis, which is what most people mean by
"notebook". It costs nothing at all to a document whose code samples are
meant to stand alone.

## Decision

### The purpose is a literate document that happens to run

**A manual, a runbook or a README whose code samples are verified rather than
asserted.** Prose first, with occasional executable examples that a reader can
run to check they still work.

This is chosen because it is the use ADR-0038's design already fits, rather
than the use that would require reversing it. Every cell in such a document is
self-contained by intent — a reader running one example does not expect it to
inherit variables from an example three paragraphs earlier — so "no persistent
session" stops being a limitation and becomes a property. An `.ipynb` is
already exactly this shape: markdown cells carrying the prose, code cells
carrying the examples.

Rejected: **data exploration.** It is what "notebook" usually means, and it is
the one purpose no-session actively hurts — every cell would re-read and
re-parse its inputs. Serving it honestly would mean reversing ADR-0038, which
is a larger decision than this one and should be made on its own evidence, not
smuggled in under a view.

### The first surface is the Run menu, not a cell view

**Open a `.ipynb` and its runnable cells appear as rows in the Run menu.**
Choosing one runs it and shows what happened. There is no cell-sequence view,
no per-cell editor, and no second kind of document.

The document itself stays what it already is: its raw `.ipynb` JSON, in the
ordinary editor. `bp-notebook` anticipated this — `raw_json_view` exists
because the JSON "is the thing the user might want to hand-edit" — so the
editing story for a notebook is the editing story for JSON, which this product
already has, including validation and formatting from `bp-data`.

**The argument is reachability against size.** A cell-sequence view is a
second document kind: its own editing, selection, undo, save, and dirty-state
story, none of which the rope-plus-two-surfaces design has a place for, and
all of which would have to be designed before a single cell could be run. A
menu is a menu. It turns two finished crates into something a person can
exercise today, and everything learned from exercising it is evidence the view
can be designed against rather than guessed at.

**This is explicitly a first surface and not the shape of the mode.** It is
recorded that way so that "we already have notebook support" cannot later be
read off a menu with five rows in it.

### Output goes to a panel, and is discarded when it closes

A run's `stdout`, `stderr`, exit code and duration appear in a collapsible
panel — the pattern `results_panel.slint` established for cross-file search
and `organize_panel.slint` reuses for related notes. It is transient: closing
the panel discards it, and a new run replaces it.

**Nothing is written back into the notebook.** Persisting output would mean a
format decision, a save story, a new way for a document to become dirty
without anyone typing, and an answer to what a stale output means once the
code beside it has changed. None of those is needed to check that an example
still works, which is the whole purpose above.

It also matches the execution model. A fresh subprocess per cell makes a run
an *event*, not a document state — and an event's natural lifetime is until
you stop looking at it.

### A run is resumable, so the window never freezes for the timeout

`bp_execution::run` blocks until the cell finishes or the 30-second deadline
kills it. A window cannot afford that: a cell that sleeps would freeze it for
as long as it sleeps, and a *hung* cell would freeze it for the full timeout —
turning the protection against a hang into a scheduled one.

So `bp-execution` gains `Run::start` and `Run::poll`, and the shell drives a
run the same way [ADR-0042](ADR-0042.md) drives a scan: a timer asks once per
tick whether it is done. `run` and `run_with_timeout` keep their blocking
contract for tests and batch callers, and are now *written over* the resumable
pair, so there is one implementation of what a run is.

**`Run::poll` takes `self` and hands the run back only while it is still
going.** That is what makes a finished run impossible to poll again: the
reader threads are joined exactly once, when the outcome is built, and no
state exists in which a `Run` holds a `JoinHandle` it has already joined.

`Run::stop` is what the Run menu's Stop row does, and it **keeps whatever the
cell printed before it was stopped** — a cell that produced ten seconds of
output and was then stopped has ten seconds of output worth reading. It
deliberately does not report `timed_out`: that would blame the cell for the
user's decision.

### Consent stays exactly where `bp-notebook` put it

specs.md section 15 says never auto-run an opened or pasted notebook.
`UserGesture::from_user_command()` is called in **one** place in the shell —
the arm that handles the Run menu's click — and both `bp-notebook` and
`bp-execution` demand one by value. Opening a notebook parses it and lists its
cells; nothing runs until a row is chosen.

Listing the cells is deliberately *not* gated: reading a document to say what
is in it is what every other menu here does, and requiring a gesture to look
would make the gesture mean something weaker than it does now.

## Consequences

- `bp-notebook` and `bp-execution` stop being unreachable. The README's
  "built and unreachable" count drops by two crates.
- The Run menu's rows become data, like the Edit menu's clipboard history and
  the Insert menu's timestamps: rebuilt per refresh from the active document.
  A menu built once at startup would list the last notebook's cells.
- A notebook that fails to parse must say so in the menu rather than showing
  an empty Run menu, which reads as "this document has no cells" — a different
  and wrong statement.
- **Markdown fences are the obvious next step and are not in this change.**
  The same purpose — a README whose examples are verified — wants
  ```` ```python ```` blocks in an ordinary `.md` file to be runnable too.
  That needs a fence parser and a decision about what names a block; neither
  is required to make the `.ipynb` path work, and doing both at once would
  make it impossible to tell which one the evidence was about.
- Rendering a notebook's markdown cells as *formatted* prose remains blocked
  on the same thing it always was: Slint has no HTML view, and no rendering
  decision has been made. A literate document read as its own source is legible
  in a way a data notebook would not be, which is part of why this purpose
  fits this surface.

## Built, and watched working rather than asserted

Shipped 2026-08-21. Driven against a five-cell `.ipynb` runbook — two
markdown cells, three Python cells, one of which fails on purpose:

| Asked | What happened |
| --- | --- |
| Open the Run menu | `Cell 2 · Python · import sys`, `Cell 4 · Python · import json`, `Cell 5 · Python · raise SystemExit(…)`, then a greyed `Stop`. The two prose cells are not listed; the numbers are file positions |
| Run cell 2 | `Python · import sys — finished in 0.2s`, and `python 3` in the panel |
| Run the cell that fails | `— exit 1 in 0.2s`, with `this example is out of date` in the accent, on the `stderr` half. **That is the purpose working**: an example that has rotted says so |
| Run a cell that sleeps 25 s | `Running Python · import sys, time… 7.7s`, ticking, while the window kept redrawing and accepting keys. It finished at `25.2s` |
| Open the menu mid-run | The cell row greyed and `Stop` live — one at a time, per ADR-0038 |
| Stop it | `— stopped in 5.3s`, with `starting` kept and `never reached` correctly absent |
| Open a `.txt` and the Run menu | `Open an .ipynb to run its cells` |

No child process outlived its run: the machine's Python processes after the
pass were the same ones that were there before it, all of them older than the
session. Checked rather than assumed, because a killed-but-unreaped child is
the failure this design has three `wait` calls to avoid.

### One thing the build found, and it is now a case of its own

**A Jupyter file names its language once for the whole notebook**, in
`metadata.kernelspec`, and a file written without one has code cells this
product cannot identify — `bp-notebook` keeps each verbatim as a `Raw` cell
and says so in an `ImportWarning`. The first fixture written for these tests
had no kernelspec, so every one of its code cells was unrunnable and the menu
said *"This notebook has no cells that can run."*

That sentence is true and useless. `RunMenu::NoKnownLanguage` is now its own
case, carrying the count, and the row says the notebook has no kernelspec —
which is the thing the reader can act on. It is also what makes
`import_ipynb` returning a *report* rather than a notebook earn the extra
call it costs every caller: the warnings are the only place that distinction
survives, because `Raw` is equally what a deliberately-raw cell is.
