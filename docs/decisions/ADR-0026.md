# ADR-0026: `.sig` Sidecars and Signing Keys on Disk

**Status:** Accepted
**Date:** 2026-08-19

## Context

ADR-0021 chose detached signatures and raw RFC 8032 encodings, and stopped
there: `bp-crypto` produces 64 bytes and has no opinion about where they
live. What was left undecided is the part a user actually meets — what the
file beside the document is called, what is in it, what a reader is told when
the answer is no, and what happens to a private key that has to sit on a
disk.

`bp-integrity` implements no cryptography and re-wraps none. SHA-256,
SHA-512 and Ed25519 all come from `bp-crypto` and are re-exported unchanged,
so a caller needs one dependency rather than two and gets the identical types
either way. What is here is the story of a file on a disk.

ADR-0001 makes Windows and Linux both first-class. They are not equally
protectable from safe Rust, and a key file is the one place in this crate
where that difference has a consequence.

## Decision

### The sidecar is `document.ext.sig`, appended and not substituted

`report.docx` is signed by `report.docx.sig`. The suffix is appended to the
whole file name. Substituting for the extension would give `report.docx` and
`report.pdf` the same `report.sig`, so exporting a document would silently
overwrite the signature over the original — a data-loss bug with a security
blast radius.

Appending also sorts the sidecar directly under its document in every file
manager, which is the cheapest available defence against the one real hazard
of a detached signature: the two files getting separated. It is the same
convention as `linux-6.1.tar.xz.sig`, `.asc` and `.sha256`, so it needs no
explaining to anyone who has ever verified a download.

`sidecar_path` is a function rather than a rule left to each caller, because
two callers that disagree about the name produce a document one half of the
product believes is unsigned.

### Four lines of text, and they record the signer's key

```text
BachelorPad+ signature v1
algorithm: ed25519
key: 3b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29
signature: e5564300c360ac729086e2cc806e828a84877f1eb8e5d974d873e06...
```

The exact 64 bytes ADR-0021 specified are on the last line, in hex, decoding
to the identical value. What is added is the line above it, and that line is
the entire reason this format exists rather than the bare one.

**A bare signature cannot say who signed.** Ed25519 verification needs a
public key supplied from outside, so with a raw `.sig` the only two available
answers are "verifies under the key you gave me" and "does not". A user
handed the second cannot tell a document that was tampered with from a
document that is perfectly intact and was signed by a colleague — and those
two call for opposite reactions. Recording the signer's key makes
`Verification::DoesNotMatch` and `Verification::SignedByAnotherKey` two
separate verdicts.

Note what it does not do: the recorded key is a claim, not a credential. It
says which key to check against. ADR-0021 already states that no key proves
whose it is, and that remains true with the key written into a file, where it
looks more like an identity than it did as 32 loose bytes.

The rest follows from that one decision: **text rather than binary**, because
a sidecar separated from its document travels by email and chat where 64 raw
bytes do not survive and hex does, and because a user can read the signer's
key without any tool of ours; **a version on the first line**, because a
format that can grow needs somewhere to say that it has and the raw form has
nowhere — a reader of `v1` refuses a `v2` file loudly instead of decoding it
wrongly; **the algorithm named**, so "this is an Ed25519 signature" is a fact
in the file rather than an assumption in the reader.

The format is fixed: four lines, in that order, lowercase hex, one trailing
newline. A reader additionally accepts `\r\n` and trailing blank lines,
because a text file that has been through Windows, a mail client and a paste
buffer comes back with those and refusing it would be pedantry at the user's
expense. Nothing else: no reordering, no extra fields, no uppercase digits. A
security artefact with several spellings is one whose comparisons are
unreliable. Signing is deterministic in `bp-crypto` and this encoding is
canonical on the way out, so re-signing an unchanged document reproduces the
sidecar byte for byte.

### A missing sidecar fails closed

`Verification::MissingSidecar` is a verdict and a failing one. **The unsigned
document fails.** A signature that can be deleted to produce a pass is not a
signature. `Verification::is_trusted` exists so no caller has to write the
`match`, because a caller who writes it and forgets a variant fails *open*,
and the variant most easily forgotten is exactly this one.

A missing *document*, by contrast, is an error rather than a verdict: there
is nothing to have an opinion about.

Five verdicts and not one, because four of them are "no" and their fixes are
four different things: find the file, get an undamaged copy, get an
untampered document, get the right key. Malformedness is likewise kept apart
from failure — a truncated file is a copying accident and a bad signature is
an accusation, and telling a user the second when the first happened sends
them looking for an attacker who does not exist.

### The signature is checked against the sidecar's own key first

The order is a decision, not an accident. The signature is tested against the
key the *sidecar* names before that key is compared with the caller's,
because a sidecar that does not hold together internally is unauthenticated
text: the key written in it is evidence of nothing, and reporting "signed by
someone else" off the back of it would be repeating an attacker's claim. A
broken sidecar is `DoesNotMatch` whatever key it names, and the key it
carries is returned marked as an unconfirmed claim.

`Expectation` is an enum rather than an `Option<&VerifyingKey>` so the
permissive choice has to be typed out. `AnySigner` is a weaker claim than it
looks: it establishes only that the document has not changed since the key
named in the sidecar signed it, and anyone who alters a document can re-sign
it with a key of their own and get `Verified`. It is honest for "show me who
signed this"; it is not a security check on its own.

Signing signs **what is on the disk**, not what an editor holds in memory,
because what is on the disk is what a recipient will check. A caller with
unsaved changes must save first.

### Key protection differs by platform, and the value says which

`write_signing_key` returns `KeyFileProtection` rather than `()`, because on
one of the two supported platforms the answer is "none of my doing" and a
caller that never sees that will never tell the user.

**Linux and other Unix: `OwnerOnly`.** Mode `0600`, set *before the first
secret byte is written* — the only ordering with no instant in which the file
exists, holds the key, and is readable by anyone else. Still not enforced,
even here: the containing directory's permissions (a world-writable directory
lets anyone replace the key file, though not read it); POSIX ACLs, which can
widen access past what the mode bits show; `root`, which reads everything;
and filesystems that do not carry Unix modes at all — an exFAT stick, an NTFS
or SMB mount with a fixed `fmask`, a Windows drive mounted under WSL — where
the mode is quietly ignored and `OwnerOnly` is still reported, because the
call to set it succeeded.

`ReadableByOthers { mode }` is only ever reported about a file this crate did
not write: one restored from a tar archive, copied off a stick, or checked
out of a repository, all of which lose or flatten the mode.

**Windows: `InheritedFromDirectory`, and `is_confirmed_private()` is
`false`.** This crate narrows nothing. It cannot: `std::fs::Permissions` on
Windows exposes exactly one bit, the read-only attribute, which controls
*writing* rather than reading and would additionally break the atomic rename
that replaces an existing key file. Narrowing the DACL properly means
`SetNamedSecurityInfo` or a `SECURITY_ATTRIBUTES` on create, both Win32 calls,
and this crate is `#![forbid(unsafe_code)]`. There is no umask on Windows and
no equivalent fallback.

What the inherited ACL gives depends entirely on the directory. Under
`%LOCALAPPDATA%` or the user's profile it usually grants that user, `SYSTEM`
and the local `Administrators` group, so other standard users cannot read the
key but any local administrator can. Under a drive root, a shared folder, a
network share or a synchronised folder it can be far wider, and a synchronised
folder additionally copies the key somewhere else entirely.

`is_confirmed_private()` is `false` for `InheritedFromDirectory`, which is not
the same as "insecure" — it means unknown, and a security indicator that
treats unknown as safe is the one that gets somebody's key copied.

## Consequences

- **Neither platform protects a key from the machine's administrator**, and
  nothing here protects it in memory once loaded. It is held in `bp-crypto`'s
  zeroizing types and wiped on drop, but pinning it out of the swap file needs
  `mlock`/`VirtualLock` and therefore `unsafe`, which this crate forbids. A
  key read from disk can reach the page file.
- **A replaced key file is not shredded.** On a journalling, copy-on-write or
  flash-backed filesystem the previous seed's blocks may outlive the rewrite,
  so a key believed to be rotated may still be recoverable from the media.
- Key encodings are `bp-crypto`'s and are asymmetric on purpose: a signing key
  file is the 32 raw seed bytes, a verifying key file is lowercase hex with a
  newline. Hex would double the number of copies of the secret in memory and
  leave a `String` nobody wipes; a public key exists to be pasted into an
  email, so it gets the text form and its reader tolerates the whitespace that
  survives that journey.
- A raw seed file has no magic bytes, so nothing but its length says it is a
  key. That is the price of matching RFC 8032 rather than inventing a wrapper,
  and it is the same trade ADR-0021 made. A file of the wrong length is
  refused rather than padded or truncated: a key read one byte short signs
  perfectly well, matches nothing anyone has verified against, and the failure
  surfaces only at the recipient.
- Writing a *verifying* key deliberately widens to `0644` on Unix. The
  temporary file the atomic write goes through is `0600`, so leaving it alone
  would produce a public key only its owner can read, discovered when a
  colleague cannot verify a document.
- Rotation does not inherit permissions. Unlike `bp-files`, this crate's
  atomic write does not preserve the mode of the file it replaces: a key that
  arrived world-readable must not stay world-readable because it was rotated
  in place.
- `key_file_protection` is separate from reading the key, so a caller can warn
  about a key file it did not write before the key is used — and so a loose
  key still loads, because refusing would leave the user unable to fix
  anything.
