# ADR-0093: An Installer For Windows, And A Package For Each Kind Of Linux

**Status:** Accepted -- built 2026-10-01
**Date:** 2026-10-01
**Supersedes:** [ADR-0067](ADR-0067.md) (there is no installer)
**Depends on:** [ADR-0012](ADR-0012.md), [ADR-0055](ADR-0055.md), [ADR-0087](ADR-0087.md), [ADR-0091](ADR-0091.md)

## Context

[ADR-0067](ADR-0067.md) decided there would be no installer, on three
arguments: an unsigned installer *asks for elevation*, which is the worst
moment to be unsigned; an installer would have almost nothing to do; and the
one thing it might do -- register file types -- [ADR-0012](ADR-0012.md)
forbids as an install step.

For 1.0, Daniel asked on 2026-10-01 for an `.exe` installer and a ZIP on
Windows, and an installation for the Linux distributions people use. Asked of
ADR-0067's arguments again, from evidence rather than appetite, as its own
closing section invited:

- **The elevation argument was about a per-machine installer.** Inno Setup's
  `PrivilegesRequired=lowest` installs to `%LOCALAPPDATA%\Programs`, writes
  only under `HKEY_CURRENT_USER`, and never shows an administrator prompt.
  Unsigned, it costs the person running it the same SmartScreen warning the
  zip's executable already does, and nothing more.
- **"Almost nothing to do" undersold what people expect of a program on
  Windows**: a Start menu entry, an entry in Settings > Apps that uninstalls
  it, and a place it lives that is not a folder they had to choose.
- **ADR-0012 forbids seizing an association, not offering one.** The
  installer's one optional task offers the program in Open With and in
  Settings > Default apps, unticked, and makes nothing the default.
- **On Linux the question was never asked.** A `.tar.gz` is not how most
  Linux users install software; their distribution's package manager is.

## Decision

**Ship an installer beside the ZIP on Windows, and on Linux a package for
each family beside the archive.** Every one of them is built by the release
workflow from the archive of the same run, so all of them hold the same files.

| File | For | Built by |
| --- | --- | --- |
| `…-windows-x86_64-setup.exe` | Windows 10 and 11 | Inno Setup 6, `packaging/windows/` |
| `…-windows-x86_64.zip` | Windows, unpacked anywhere | `scripts/New-Release.ps1`, as before |
| `…_amd64.deb` | Debian, Ubuntu, Mint, Pop!_OS | `dpkg-deb`, `packaging/linux/build-packages.sh` |
| `…-1.x86_64.rpm` | Fedora, openSUSE, RHEL-alikes | `rpmbuild`, the same script |
| `…-x86_64.AppImage` | any other distribution | `appimagetool`, the same script |
| `…-linux-x86_64.tar.gz` | Linux, unpacked anywhere | `scripts/release-linux.sh`, as before |
| `PKGBUILD` | Arch, through the AUR | rendered by the same script |
| Flatpak manifest | Flathub | committed in `packaging/flatpak/`, built by Flathub |

### The Windows installer

- **Per-user, never elevated.** `PrivilegesRequired=lowest`, and nothing may
  override it; a test asserts both.
- **Its `[Registry]` section is generated** from `bp-platform`'s own
  registration plan for the *Text + Notes* preset, into
  `packaging/windows/registry.iss`, and a test fails when the committed file
  and the code differ. The installer and File > Set as Default Editor
  therefore cannot register different keys -- which a hand-written copy
  would, the first time either changed.
- **Uninstalling removes what it wrote**: the program, its shortcuts, our own
  keys whole, and only our *values* from keys other applications share. It
  does not touch the settings, recent files, recovery journal or note store
  in the user's profile, for [ADR-0070](ADR-0070.md)'s reason.
- **The `AppId` GUID is permanent.** It is how Windows recognises a later
  installer as an upgrade rather than a second copy.

### The Linux packages

- **Built with the distributions' own tools, `dpkg-deb` and `rpmbuild`**,
  rather than `cargo-deb` and `cargo-generate-rpm`. Both of those work out
  dependencies from the binary's link table, and this binary loads almost
  everything it needs with `dlopen` -- xkbcommon, X11, xcb, Wayland, EGL.
  The tools would have declared fontconfig and libc, and the rest would have
  been discovered by a user as a window that never opens. **The list was read
  from the binary instead** -- `strings` on the CI-built Linux binary, which
  is where `dlopen`'s names live -- and both formats declare it by hand: the
  `.rpm` by soname, so one package serves Fedora's and openSUSE's differently
  named libraries.
- **The program and what it reads beside itself install together**, under
  `/usr/lib/bachelorpad-lite/`, with `/usr/bin/bachelorpad` and `bpad` as
  symlinks. The program finds its help and its window icon beside its own
  executable, which the kernel resolves through the symlink; the conventional
  split -- help under `/usr/share` -- would give Help > User Guide nothing to
  open.
- **The `.desktop` entry and the AppStream metadata are one copy each**, in
  `packaging/linux/`, carried inside the `.tar.gz` and installed by every
  package from there. A test pins their name, id, summary and licence to the
  program's constants -- ADR-0074 found what literal copies do across a
  rename.
- **`appimagetool` is fetched at a pinned version and refused unless its
  SHA-256 matches** the digest GitHub records for that release asset. A tool
  downloaded at build time and run unchecked is a stranger's code inside
  every AppImage.

### New dependencies: none

Inno Setup, `dpkg-deb`, `rpmbuild` and `appimagetool` are build tools on the
release runner. None is a Cargo dependency, none enters `cargo deny`'s graph,
and nothing of theirs is linked into `bachelorpad`. Two put code *beside* it
in an artefact: the Inno Setup installer stub (Inno's own permissive licence)
and the AppImage runtime, which contains `libfuse` under LGPL-2.1 -- mere
aggregation, and named here so the AppImage's notices can say so.

## What it costs, and what is not done

- **Three of the eight are not built here.** The Flatpak manifest is written
  and unbuilt: Flathub builds it, and submitting is a pull request to
  `flathub/flathub` that needs a screenshot this repository does not yet
  have. The `PKGBUILD` is rendered, and publishing it needs an AUR account --
  **AUR registration has been closed since 2026-09-09**
  (<https://bbs.archlinux.org/viewtopic.php?id=314858>), so that is Daniel's
  existing account or nothing for now. winget, which ADR-0086 made a 1.0
  task, can point at the installer once a release exists.
- **The packages pin the release to `ubuntu-22.04`**, whose image GitHub
  retires on 2027-04-17 (ADR-0087 records the choice to be made then).
- **The `.deb` and `.rpm` have been inspected, not installed** on a clean
  Debian, Ubuntu or Fedora machine; the manual pass does that.

## Verification

- `bp-platform`: the committed `registry.iss` is exactly what the
  registration generates; the installer deletes our keys whole and only our
  values from shared ones, per-user, never naming Notepad.
- `tests/integration/tests/the_packages_name_the_product_as_the_program_does.rs`:
  the `.desktop` entry, AppStream file, Flatpak manifest, Inno script and
  PKGBUILD agree with `APP_ID`, `DISPLAY_NAME`, `DESCRIPTION` and the
  licence; the installer is per-user and its Open with task unticked; the
  Flatpak sandbox has no network.
- The release workflow's dry run builds every artefact on clean runners;
  that run is the first evidence each one builds at all.
