# ADR-0049: The Window Is Driven By A Script, And A Temp Path A Recycled Pid Can Reuse Is Not Unique

**Status:** Accepted
**Date:** 2026-08-22

## Context

Two things this repository believes about verification turned out to be
half-true, and both were found in the same hour by trying to check
[ADR-0048](ADR-0048.md)'s ten new menu rows.

**The first: "a manual pass needs a person."** It mostly does — `rfd` modals
swallow synthetic input, and File ▸ Set as Default Editor changes state
outside the application. But five sessions have each re-derived the same Win32
plumbing from scratch to get as far as they could, and none of it was written
down. `project/NEXT_SESSION.md` has carried "drive the window" as the top item
since the fourth session while the *means* of doing it was rebuilt each time.

**The second: "these tests pass."** They do, most of the time.

## Decision

### `scripts/Drive-Window.ps1` is the plumbing, written once

Launch the application, find its window, click at a point, send keys, capture
to a PNG. Four things in it are load-bearing and every one cost something to
learn:

- **Clicks are posted to the window, not synthesised at the cursor.**
  `mouse_event` requires this window to be in front, which Windows refuses at
  random — the failure that produced a defect report which was later
  withdrawn. A posted `WM_LBUTTONDOWN` lands on the window's queue whatever is
  on top, and leaves the user's real pointer alone. Only `SendKeys` still
  needs focus, so only `SendKeys` is gated on it.
- **The foreground check refuses rather than proceeding.** A lost foreground
  and an application dropping keystrokes look identical from outside.
- **`MainWindowHandle` is not reliably the window.** For this application it
  reports a handle that accepts posted clicks and returns nothing from
  `GetClientRect`, so a capture came back 1×1 and a run that had worked looked
  broken. The window is found by enumerating the process's own top-level
  windows and taking winit's `Window Class` — *not* "the biggest one", because
  a 16×16 `Winit Thread Event Target` sits beside it.
- **A dialog is its own top-level window**, class `#32770`. Photographing the
  application's window gets the one behind it, so the dialog is simply absent
  — which reads as "the row did nothing", the one conclusion a capture must
  never invite by accident. `CopyFromScreen` is the obvious alternative and
  throws "handle is invalid" in a session with no interactive desktop.

A failure now terminates the process it started. It did not, and a leaked
`bachelorpad.exe` holds the binary open so the next `cargo build --release`
fails with "Access is denied" — which reads as a permissions problem and is
not one.

### What driving found: a clipped label is not a cosmetic defect

`MenuPopup` is a deliberate fixed 280px and the `Flickable` around it clips.
A label longer than that was cut **mid-word with nothing to say it had been**:

> `Sign Document — this document has never b`

Every label it happened to was a **greyed row's reason** — the one text on
screen whose entire job is to explain why a row cannot be clicked. Losing it
silently is the worst case, not a cosmetic one, and it had been shipping since
those rows were built.

Two halves, because either alone is insufficient:

- `overflow: elide` on the row's label, so a truncation always *looks* like a
  truncation. A stylesheet cannot decide what the words should be;
- the four over-long labels shortened to fit, and
  `no_row_label_is_too_long_for_the_popup_to_show` to keep them that way. Its
  budget is deliberately generous — proportional text has no character count,
  and a test that pretended to know the exact one would fail on a font change
  for a reason nobody could act on.

### `crate::testpaths`: unique means "no earlier run either"

`audit::audit_path` and `state::security::default_signing_key_path` each built
a per-test temp name from the process id and a counter, each with a doc
comment explaining that the pid is there "so two runs at once cannot collide".
That is true, and it is not the dangerous case.

**Nothing ever deleted the files, and Windows recycles process ids.** A test
process eventually starts with a pid an earlier run already used, and its
"unique" path names that run's leftover. For the audit log that means opening
a history whose sequence numbers already start at one, which `AuditLog`
correctly refuses; for the signing key it means `begin_signing` finding a key
sealed under a passphrase the test does not know.

Measured when found: **5,862 leftover files across 495 distinct pids**, and
`signing_reaches_the_security_history` failing **one run in five in
isolation**. After the fix, eight runs out of eight, and the sweep took the
directory from 5,862 files to 696.

> **The suite got flakier the more it was run**, which is the worst shape a
> flake can have: the machine that runs the tests most is the one that trusts
> them least. And it degrades so slowly that every individual session
> reasonably concludes it saw a one-off.

One home, `crate::testpaths::unique`, because two places invented the same
scheme and got it wrong the same way — which is the trap
`bp_platform::paths::reserved_device_name` exists for, in a different costume.
A nanosecond timestamp makes a recycled pid unable to reproduce a name; the
file is removed first regardless; and a once-per-process sweep clears anything
this module made over an hour ago, since a scheme that only prevents
*collisions* still grows the temp directory by a file per test for ever.

## Consequences

- **Ten rows were driven and photographed**, and Security Inspector,
  Configuration and Interpreters were read on screen. Interpreters reported
  `Python: python3`, `PowerShell: pwsh`, `Shell: not found — tried sh`, which
  is correct on this machine and is exactly the question the row exists to
  answer.
- Every menu was opened and confirmed to contain no inert command row.
- **A test that fails one run in five is a test nobody can act on**, and the
  cost is not the failures — it is that a real regression in that area would
  have been read as the flake. Nothing is known to have been missed this way,
  which is the most that can honestly be said.
- **One Linux gate run failed and was never explained**, and it is recorded
  rather than dropped. `cargo nextest` exits 100 for a test failure, so a test
  did fail; it did not recur in five subsequent whole-suite runs on the same
  tree, nor in the gate run that followed. **The name is unknown because the
  gate's output was piped through `Select-Object -Last 18`** -- the failure's
  detail is above the summary, so the one thing needed was the one thing
  discarded. `CLAUDE.md` now says not to do that.

  It is written down because this ADR's other half is about a flake that
  degraded slowly enough for two sessions to each dismiss it as a one-off, and
  dismissing this one silently would be the same mistake in the same commit.

- The driving script is not part of the gate and should not be: it needs a
  desktop, and the gate's `launch` stage already proves the binary starts.
- **`rfd` modals still swallow synthetic input**, so a driven run that opens
  one ends by killing the process. Set as Default Editor and completing a
  signature remain a person's job, and `project/NEXT_SESSION.md` §3 still says
  which parts and why.
