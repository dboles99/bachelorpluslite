# ADR-0088: The Release Candidate Is Reachable By Keyboard And Names Its Controls; 1.0 Is Tested With A Screen Reader

**Status:** Accepted -- release-candidate half built (W4-02, 2026-09-26); the
screen-reader half moves to a 1.x release ([ADR-0094](ADR-0094.md)), and
accessibility is still claimed nowhere until it has happened
**Date:** 2026-09-25
**Answers:** D26
**Related:** [ADR-0001](ADR-0001.md), [ADR-0080](ADR-0080.md)

## Context

The release-candidate audit counted **zero** `accessible-*` properties in
the `.slint` sources. The menu bar is a row of `Rectangle`s with `TouchArea`s,
which a screen reader sees as nothing, and it cannot be reached from the
keyboard at all: there is no Alt, no F10, no way to open File without a
mouse. Every command has a shortcut, so a sighted keyboard user can work,
but a user who cannot see the screen cannot find out what the commands are.

Slint's winit backend, which this product uses whichever renderer draws,
already publishes an accessibility tree through AccessKit on both platforms --
UI Automation on Windows, AT-SPI on Linux (`cargo tree -i accesskit_winit`).
So the work is in this product's markup, not in the toolkit.

Two audits disagreed about whether this blocks a release candidate. Nothing
had decided it, which is how it had stayed at zero.

## Decision

**In the release candidate** -- the part no screen reader can work around:

- **The menu bar is reachable from the keyboard.** Alt or F10 focuses it, the
  arrows move between menus and rows, Enter runs a row, Esc backs out -- as
  Notepad does.
- **Controls say what they are.** `accessible-role` and `accessible-label` on
  the menu bar, its menus and rows, the tabs, the find and replace inputs and
  Go To Line. A button a screen reader announces as "button" is not
  accessible; one it announces as "Replace All, button" is.

**For 1.0:**

- **A pass with NVDA on Windows and Orca on Linux**, recorded in the manual
  checklist. For the release candidate it is an *observation*, written down,
  and not a gate: the first pass will find things, and the point of it is to
  find them.
- **A high-contrast palette**, and a test that fails when a theme's text and
  background fall below WCAG AA contrast. Four themes are four chances to get
  it wrong, and only a test checks all four every time.

## Verification (W4-02)

The Xvfb harness can drive the keyboard half: Alt, Right, Down, Enter on a
row whose effect shows up in the saved file, which is the marker technique
[ADR-0080](ADR-0080.md) introduced. The labels need a person with a screen
reader, and the manual checklist says so.

## What building it found

**F10, not a bare Alt.** The decision said "Alt or F10"; only F10 is built,
and the reason is in winit rather than in taste. On X11, a window losing the
keyboard is sent a synthetic release for every key still down -- *before*
`Focused(false)` (`winit-0.30.13`, `x11/event_processor.rs`,
`xinput_focus_out`) -- and Slint forwards synthetic modifier releases
(`i-slint-backend-winit` `winitwindowadapter.rs`). So `Alt+Tab` away arrives
as `Alt` pressed and released alone, and a bare-Alt trigger would open File
in a window the user has just left. Telling the two apart needs winit's
window events, which Slint exposes only behind `unstable-winit-030`
([ADR-0081](ADR-0081.md)). If D19 turns that feature on, this can be
revisited; until then a bare Alt is a trigger that misfires on every window
switch. *Test:* bind a `capture-key-released` on `Key.Alt` and Alt+Tab away
under a window manager on X11.

**A popup does not get the keyboard by opening, and cannot be handed it.**
Slint's `show_popup` takes the focus away from the editor and gives it to
nothing, so before this every key but Escape went nowhere while a menu was
open. The window cannot call into a `PopupWindow` to fix that ("Cannot access
property or callback inside of a Window from enclosing component"), and the
popup cannot take it in `init`, which runs before `show_popup` takes the
focus. Each menu takes it one tick after it opens, with a `Timer` -- the
answer [R011](../../prompts/rosettas/R011_WIRE_CAPABILITY_INTO_SHELL.md) trap
9 already gave the bars.

**Slint 1.18 has no menu roles for markup.** Its own `MenuBar` element maps to
native menus; a hand-built one gets `button`, `list` and `list-item`. So a
menu title is a button with an expanded state, a menu is a list named for its
title, and a row is a list item whose description is its shortcut. The list's
focus is delegated to the highlighted row
(`accessible-delegate-focus`), so a reader announces the row each arrow lands
on rather than the list once.

**AccessKit 0.19 drops two states on Linux.** Its AT-SPI mapping publishes no
expanded state at all, and reports every list item Enabled and Sensitive
whatever it is told. UI Automation gets both. So on Linux a menu title does
not say whether it is open -- nothing in this product can fix that -- and a
greyed row says "unavailable" in words, which works on both.

**Reading the tree needed no screen reader.** `at-spi2-core` and
`python3-pyatspi` in the container, a private session bus, and
`scripts/atspi-tree.py` print exactly what Orca would be handed. Reading it
found four things the markup review had not: the gutter read out as every
line number before the first word; each status readout beginning "vertical
line"; every named control's own text exposed a second time; and the message
dialog focusing the window rather than the button Enter would press.
`--editor-view` also exposed a hidden 20-character ruler as the first text
in the document.

## Verification

- `scripts/drive-menus-xvfb.sh`, on both surfaces: F10, Left and Right with
  wrapping, Up, Down, Home, End, Enter, Escape; letters typed into an open
  menu staying out of the document; a menu opened a second time, and one
  opened with the mouse, both taking the keyboard; Return on a greyed row
  doing nothing. Every case ends in Edit > Select All and a letter, so the
  evidence is the saved file.
- `scripts/check-accessibility-xvfb.sh`: 30 assertions on the AT-SPI tree --
  every name the Decision lists, the focused row and dialog button, a greyed
  row's "unavailable", the absence of the four defects above, and a menu
  closing after a row is activated the way a reader activates it. That last
  one was review's find: the row's accessible action ran the command and left
  the menu up, holding the keyboard, because only a click and Enter closed it.
- A short window, photographed: End and Home keep the highlighted row in view
  in a menu that scrolls.

**Not verified:** anything spoken. NVDA and Orca have not been run, which is
the 1.0 half of this decision and stays open. Windows has not been driven by
hand; the expanded state reaching UI Automation is AccessKit's code, read,
not observed.

## Consequences

**"Accessible" is not claimed anywhere until 1.0's pass has happened.** The
release candidate is keyboard-reachable and labelled, and it says exactly
that.
