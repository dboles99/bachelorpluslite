# ADR-0088: The Release Candidate Is Reachable By Keyboard And Names Its Controls; 1.0 Is Tested With A Screen Reader

**Status:** Accepted -- not yet built (W4-02)
**Date:** 2026-09-25
**Answers:** D26
**Related:** [ADR-0001](ADR-0001.md), [ADR-0080](ADR-0080.md)

## Context

The release-candidate audit counted **zero** `accessible-*` properties in
the `.slint` sources. The menu bar is a row of `Rectangle`s with `TouchArea`s,
which a screen reader sees as nothing, and it cannot be reached from the
keyboard at all: there is no Alt, no F10, no way to open File without a
mouse. Every command has a shortcut, so a sighted keyboard user can work,
but a user who cannot see the screen cannot find out what the commands are.

Slint's winit backend, which this product uses whichever renderer draws,
already publishes an accessibility tree through AccessKit on both platforms --
UI Automation on Windows, AT-SPI on Linux (`cargo tree -i accesskit_winit`).
So the work is in this product's markup, not in the toolkit.

Two audits disagreed about whether this blocks a release candidate. Nothing
had decided it, which is how it had stayed at zero.

## Decision

**In the release candidate** -- the part no screen reader can work around:

- **The menu bar is reachable from the keyboard.** Alt or F10 focuses it, the
  arrows move between menus and rows, Enter runs a row, Esc backs out -- as
  Notepad does.
- **Controls say what they are.** `accessible-role` and `accessible-label` on
  the menu bar, its menus and rows, the tabs, the find and replace inputs and
  Go To Line. A button a screen reader announces as "button" is not
  accessible; one it announces as "Replace All, button" is.

**For 1.0:**

- **A pass with NVDA on Windows and Orca on Linux**, recorded in the manual
  checklist. For the release candidate it is an *observation*, written down,
  and not a gate: the first pass will find things, and the point of it is to
  find them.
- **A high-contrast palette**, and a test that fails when a theme's text and
  background fall below WCAG AA contrast. Four themes are four chances to get
  it wrong, and only a test checks all four every time.

## Verification (W4-02)

The Xvfb harness can drive the keyboard half: Alt, Right, Down, Enter on a
row whose effect shows up in the saved file, which is the marker technique
[ADR-0080](ADR-0080.md) introduced. The labels need a person with a screen
reader, and the manual checklist says so.

## Consequences

**"Accessible" is not claimed anywhere until 1.0's pass has happened.** The
release candidate is keyboard-reachable and labelled, and it says exactly
that.
