# ADR-0070: State Written By A Feature That Has Gone Is Left Where It Is, And Named

**Status:** Accepted
**Date:** 2026-08-30
**Depends on:** [ADR-0064](ADR-0064.md), [ADR-0032](ADR-0032.md)

## Context

This session removed ten crates' worth of features. Removing the code that
*writes* a file is a compile-time act with a test behind it. **Removing the
file it already wrote is not**, and nothing in this repository had said what
happens to it.

The question stopped being hypothetical on the machine this was developed on:

| Path | State |
| --- | --- |
| `%LOCALAPPDATA%\bachelorpad\state\recent.toml` | live |
| `%LOCALAPPDATA%\bachelorpad\data\organize.sqlite` | live |
| `%APPDATA%\bachelorpad\recent.toml` | **dead** -- an earlier location |
| `%APPDATA%\bachelorpad\security-history.log` | **dead** -- ADR-0064 removed the audit log |

**`%APPDATA%\bachelorpad` itself is live**, and the first draft of this ADR
said otherwise. It is [`DirKind::Config`](../architecture/ARCHITECTURE.md), and
it holds `config.toml` the moment configuration is saved. The directory is not
orphaned; two files inside it are. That distinction is the whole difference
between "remove a folder" and "do not remove a folder", and it took one `grep`
for `DirKind::Config` to find -- the same `grep` this session has now leaned on
six times.

## The half that was already decided, in the wrong place

`recent.rs` has said this since the list moved out of the config directory:

> Nothing migrates the old file. It is a convenience list of at most ten paths
> and it rebuilds itself the first time anything is opened, so carrying code
> forward to find it would cost more than it saves.

That is a correct decision and it is **a decision living in a module header**,
which this repository's own table says is not where decisions live. It is
adopted here so it has one home, and `recent.rs` links rather than restates.

## Decision

**Nothing is deleted, moved or rewritten in a user's profile on their behalf.
Leftover state stays where it is.**

Three reasons, in order of weight:

1. **It is the rule this product already follows everywhere else.** File
   renames and moves need explicit approval; [ADR-0012](ADR-0012.md) will not
   seize a file association and hands the user a `.reg` to read instead. A
   product that will not silently claim `.txt` but *will* silently delete a
   file out of `%APPDATA%` is not being careful, it is being inconsistent.
2. **A deletion pass is a new failure mode on a path nothing else touches.**
   It would run at start-up, against paths derived from environment variables,
   on a directory the user may have put other things in. The upside is a few
   kilobytes.
3. **The files are inert.** Nothing reads them. They cost disk and nothing
   else.

### `security-history.log` is the interesting one, and it still stays

It differs from the stale `recent.toml` in a way worth writing down rather
than waving past: **`recent.toml` rebuilds and this does not.** It is a frozen
security record -- every profile change the product made while the audit log
existed -- and a frozen security record is exactly the shape of thing that
misleads, because it looks maintained. Trap 3, in a file rather than a
comment.

The argument for deleting it is therefore real, and it loses to reason 1
anyway. **It is the user's record of their own machine, and this product does
not get to decide it is worthless.** Somebody may want it precisely *because*
the feature is gone.

What the product owes instead is to stop the file being read as current, and
the honest way to do that is to say so where somebody looking will find it --
which is this ADR and `README.md`, not a deletion.

### What a second machine gets

**Nothing.** This is state on one developer's machine, written by builds that
no longer exist. A fresh install writes only what today's code writes, so
there is no leftover to migrate anywhere and no compatibility surface here at
all. That is worth stating because "migration" was the word the question
arrived in, and there is nothing to migrate -- only something to leave alone.

## Consequences

**`%APPDATA%\bachelorpad\security-history.log` and the stale `recent.toml`
beside it will sit on this machine until somebody deletes them by hand**, and
that is the intended outcome rather than a loose end.

**No start-up work is added**, which matters more than it sounds: the
alternative put filesystem calls on the path between launch and a window, for
a feature whose entire benefit is tidiness.

**If this is ever revisited, it is a Help ▸ Diagnostics *readout*, not a
sweep** -- naming what was found and leaving the act to the user, which is the
shape ADR-0012 already established for the one other place this product tells
the operating system about itself.

## The lesson

> **Deleting the code that writes a file does not delete the file, and the
> record has to say which of those two happened.**

A removal ADR naturally describes the code, because the code is what the
commit touched and what the tests cover. The bytes already on somebody's disk
are the part with no compiler and no test -- so they are the part that goes
unmentioned, and the part a user actually meets.

**The check is one question asked at the end of every removal: what did this
feature leave behind, and where?** For nine of ADR-0064's ten features the
answer was nothing. It only takes one to be worth asking.
