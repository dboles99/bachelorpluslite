# ADR-0056: All Three Embedding Sources, And The Axis For Them Already Existed

**Status:** Accepted
**Date:** 2026-08-23

## Context

D16 was described as the largest unasked question in the project for two
sessions: **phase 10 needs embeddings, nothing here computes one, and
computing one reaches [ADR-0033](ADR-0033.md) and [ADR-0006](ADR-0006.md).**
It was put as three options -- a local model, an opt-in network service, or
dropping phase 10.

Answered by Daniel on 2026-08-23: **all three, as choices.**

**And then looking found that the choice already exists.**
`bp_security::Embeddings` has carried exactly three values since
[ADR-0020](ADR-0020.md):

```rust
pub enum Embeddings { Cloud, Local, None }
```

with a doc comment that says *"Phase 10 reads this"*, and a per-profile
mapping already decided:

| Profile | `embeddings` | `network` |
| --- | --- | --- |
| Standard | `Local` | `Allowed` |
| Private | `Local` | `Denied` |
| Confidential | `None` | `Denied` |
| Maximum | `None` | `Denied` |

So D16 was not a question about what the product should permit. That was
settled three sessions before it was asked. **This is trap 6 again in its
other form**: not a stale premise, but a question whose answer was already in
the repository, unread. The tell was the same -- nobody could say what would
change if it were answered either way, because for four of the seven axes
nothing would.

What was genuinely undecided is smaller and sharper, and it is what this ADR
settles.

## Decision

### 1. The profile is a ceiling. The user chooses at or below it

`Policy::embeddings` says what a profile **permits**, not what happens. A
preference chooses within that, and the effective value is the more
restrictive of the two -- which is already how `Override` works in the same
crate ("a session-wide override that can only ever tighten"), so this is the
existing pattern applied to one more axis rather than a new mechanism.

The enum is ordered `Cloud < Local < None`, so "more restrictive" is `max`,
and `Policy::at_least_as_restrictive` already reads it that way.

### 2. `None` is the default, and the product is complete at `None`

**Nothing computes an embedding unless somebody asks for it.** That is
ADR-0006 held exactly as written: core editing, and everything this product
does today, works with embeddings switched off, because that is the only
state that has ever existed. Semantic search is an *addition* to the lexical
search that already ships, never a replacement -- so a user at `None` loses a
feature they never had rather than gaining a degraded one.

### 3. `Cloud` is not reachable by choosing it alone

Two things gate it, and both already exist:

- **The profile must permit it.** No named profile sets `Cloud` today --
  Standard is `Local`. So `Cloud` requires an explicit `Policy`, which is a
  deliberate act and not a menu default. **That stays true**; this ADR does
  not add `Cloud` to a named profile.
- **Every send needs a per-use gesture.** ADR-0033 permits the network
  "opt-in per use, never automatic", and `UserGesture` in `bp-execution` is
  already this product's primitive for exactly that -- a token that cannot be
  constructed except from a real user action, neither `Clone` nor `Default`,
  with compile-fail doctests proving both. Cloud embedding uses it. **A
  preference set to `Cloud` is permission to be asked, not permission to
  send.**

  **There are two `UserGesture` types today**, one in `bp-execution` and one
  in `bp-notebook`, and `bp-execution`'s own doc comment says whether they
  should be one type is "a call for whoever wires `bp-execution` into
  `bp-notebook`/`bp-ui`, with both definitions in front of them". A third
  copy is where that stops being optional: two independent tokens with the
  same rule is a defensible boundary, three is a pattern nobody owns.
  Whoever builds `Cloud` unifies them or says why not.

`Network::Denied` forbids it independently, so a profile cannot permit
`Cloud` embeddings while denying network -- and a test should say so, because
today nothing does.

### 4. `Local` needs a model, and that is its own dependency ADR

A local embedding model is a large dependency and possibly a downloaded file,
which `CLAUDE.md` makes ADR material on its own. **This ADR does not choose
one.** It says only that `Local` is the value a chooser will most often land
on, and that whatever implements it must:

- ship or fetch its weights explicitly, never silently on first use;
- work offline once present, because `Local` that phones home is `Cloud`
  wearing a different name;
- degrade to `None` with a notice rather than an error when the model is
  absent -- the same rule `bp-config` applies to a broken config file.

### 5. No setting is added today, and that is on purpose

The obvious next move is a `bp-config` setting so a user can pick. **It is
not being made**, and the argument against it is already written in the crate
this would touch:

> *"Seven axes, and every one has a named reader -- an axis nothing consults
> reads as a guarantee while being decoration, which is worse than its
> absence."*

A preference that selects between three sources, two of which compute
nothing, is that decoration. The setting lands in the same change as the
first thing that computes an embedding, and not before.

## Consequences

- **Phase 10 is sizeable now, and it is three items rather than a phase.**
  They are in `WORK_QUEUE.md`: the store column and the query that reads it,
  a `Local` provider with its own dependency ADR, and the `Cloud` provider
  behind `UserGesture`. The first is decision-free and does not need either
  provider to exist.
- **`Embeddings::Cloud` stops being unreachable.** It has been a value no
  named profile produces since ADR-0020 -- correct then, and now it has a
  route: an explicit policy plus a gesture per send.
- **The `Network`/`Embeddings` agreement is currently unenforced.** Nothing
  stops a hand-built `Policy` with `embeddings: Cloud, network: Denied`,
  which is a contradiction the type system permits and no test catches. That
  is a small item and it belongs with the first provider.
- **ADR-0033 is unchanged and unextended.** It authorises OpenAI's API,
  opt-in per use. Whether an embedding endpoint is the same authorisation or
  a new one is a question for whoever builds `Cloud`, and stating it here is
  cheaper than discovering it there.

## The lesson

> **A question can be answered in the repository and open in the queue at the
> same time.** D16 sat as "the largest unasked question in the project" while
> `bp_security::Embeddings` carried its three answers, a per-profile mapping
> for each, and a doc comment saying *"Phase 10 reads this"*. Two sessions
> described it as unscoped without opening the file that scoped it.
>
> The habit that would have caught it is the one trap 6 already names, pointed
> the other way: before asking a question, **grep for its answer.** A
> decision recorded in a type is still a decision, and it is the kind least
> likely to be re-read -- because nothing about a queue of questions suggests
> looking in `src/`.
