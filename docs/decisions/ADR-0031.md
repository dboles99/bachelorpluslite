# ADR-0031: A Signing Key Lives In A Sealed Key File, Not A Protected One

**Status:** Accepted
**Date:** 2026-08-20

## Context

`bp_integrity::sign_file` exists, is tested, and writes the very sidecar
Security ▸ Verify Signature already reads. The row is greyed with the reason
on it rather than marked `planned`, because it exists and cannot act: an
Ed25519 signing key has to be kept somewhere, and this product has no key
store.

ADR-0026 did the hard part of the analysis and stopped exactly where the
decision starts. Its finding, restated because it is the whole of this ADR's
context:

> **Windows: `InheritedFromDirectory`, and `is_confirmed_private()` is
> `false`.** This crate narrows nothing. It cannot: `std::fs::Permissions` on
> Windows exposes exactly one bit, the read-only attribute [...] Narrowing the
> DACL properly means `SetNamedSecurityInfo` or a `SECURITY_ATTRIBUTES` on
> create, both Win32 calls, and this crate is `#![forbid(unsafe_code)]`.

So on one of the two first-class platforms, a key file's protection is
whatever the directory happened to grant — usually the user, `SYSTEM` and
every local administrator, and far wider under a shared, network or
synchronised folder. `is_confirmed_private()` reports `false`, which is honest
and is not a solution.

specs.md §15 asks for three routes: a key store, the platform keyring, and a
key file. The question was which one a signing key gets *first*, because
whichever it is, that is where keys will exist.

## Decision

**The signing key is stored sealed, in a `.bpadx` envelope, under a passphrase
the user chooses.**

The key file is an ordinary file whose *contents* are protected rather than a
file whose *permissions* are. It goes in the state directory beside the rest
of this machine's own state (`DirKind::State`, and see ADR-0030's neighbour
work), and its confidentiality does not depend on the filesystem, the
directory's ACL, or the platform.

Concretely: the 32 raw seed bytes ADR-0026 specifies are the plaintext, and
`bp_crypto::seal` with `SealOptions::default()` produces the file. Nothing new
is designed — this is the envelope ADR-0021 already ships, already fuzzes, and
already uses for encrypted documents and for the sealed recovery journal
(ADR-0022).

### Why not the plain key file with permissions where possible

It is what ADR-0026 measured, and the measurement is the argument against it.
`0600` on Linux and nothing on Windows is not a policy, it is an asymmetry —
and the asymmetry falls on the platform this product names first. A user
signing a document on Windows would be told, correctly, that the protection
of their signing key is unknown. Shipping a key store whose honest status
indicator reads "unknown" on half the supported platforms is shipping the
problem.

### Why not the platform keyring

DPAPI and Secret Service give the best protection available and specs.md §15
asks for them. Two things put them second rather than first. They are a real
dependency and a platform-specific one, and ADR-0001 warns specifically
against code that only one leg of CI ever compiles — this repository has been
caught three times by a *judgement* taking a platform while some operation
underneath it did not. And they are phase 18 work, while Sign Document is
phase 16 and otherwise finished.

This decision does not close that door. A sealed key file and a keyring-backed
key differ in where the *unsealing secret* comes from, not in what is stored,
so the keyring becomes a second source for the passphrase rather than a second
key format.

### What this costs, honestly

- **A passphrase prompt per signing session.** The same shape as an encrypted
  document's, and `bp-ui` already has the bar for it. Holding the unsealed key
  for the session is the same trade `passphrases` on `AppState` already makes,
  for the same reason: prompting on every Ctrl+S trains a user to type a
  passphrase reflexively, which is worse than holding it.
- **Argon2id per unseal.** ~45 ms at the OWASP baseline, once per session.
  D7's derive-once question is about `bp-audit` sealing one envelope per line;
  one key file is one derivation and is not affected.
- **A forgotten passphrase is a lost key**, and a lost signing key means every
  document signed with it can still be verified and no new one can join them.
  That is a property of the decision and has to be said at the point the key
  is created, not discovered later.
- **Everything ADR-0026 says about a key in memory still holds.** It is in
  `bp-crypto`'s zeroizing types and wiped on drop, and pinning it out of the
  page file needs `mlock`/`VirtualLock` and therefore `unsafe`. Sealing the
  file changes what is on the disk, not what is in RAM.
- **A replaced key file is still not shredded.** Unchanged from ADR-0026, and
  now less consequential: the blocks that may outlive a rotation hold
  ciphertext.

## Consequences

- D5 leaves `project/DECISIONS_NEEDED.md`, and Security ▸ Sign Document stops
  being blocked on a decision. It is now blocked only on the work.
- `KeyFileProtection` from ADR-0026 does not go away and does not become
  decorative. It still describes a key file this product did not write — one
  restored from a tar archive or checked out of a repository — and the
  product's own key is now protected by something it does not have to ask the
  filesystem about.
- The Windows/Linux asymmetry in key protection is closed, not documented.
  That is the point: `is_confirmed_private()` was honest about a gap, and the
  answer to an honest gap is to remove it rather than to keep reporting it
  well.
- Nothing new is designed, reviewed or fuzzed. If D4 is ever answered — an
  outside review of the `.bpadx` envelope — that review covers the key store
  too, because it is the same envelope.
