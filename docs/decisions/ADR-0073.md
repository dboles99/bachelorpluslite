# ADR-0073: Hosted CI Is Restored, Because ADR-0016's Premise Was Never Re-checked

**Status:** Accepted
**Date:** 2026-09-10
**Amends:** [ADR-0016](ADR-0016.md)
**Depends on:** [ADR-0072](ADR-0072.md)

## Context

[ADR-0016](ADR-0016.md) opens: *GitHub Actions is not available to this
project.* Everything else in it follows from that sentence -- the local gate
being authoritative, the workflow file kept dormant at `workflow_dispatch`,
and Actions disabled at the repository level so that no branch could queue a
run that could not execute.

The reasoning was sound and the mechanism was well built. **The premise is
false, and one call disproves it:**

```
GET /repos/dboles99/bachelorpluslite/actions/permissions
{"enabled": true, "allowed_actions": "all", "sha_pinning_required": false}
```

Actions is enabled. The account is on GitHub Pro. And the repository is about
to become public, which makes Actions minutes free and unmetered on Linux and
Windows runners.

**This is trap 6, and it is the second time.** D13 sat for five sessions on
*111 commits live on the branch; main has none of them*, a claim one
`git merge-base` disproved. The habit that catches it -- check a premise
before acting on it again -- was installed for questions in
`DECISIONS_NEEDED.md` and not for premises inside accepted ADRs, which is
where this one was living.

Worth stating precisely: ADR-0016 was almost certainly **true when written**.
Nothing about it was careless. It became false silently, and a decision
document has no mechanism that would ever tell anybody.

## Decision

**Hosted CI is restored, and the local gate stays authoritative for
development.** They are two gates with two jobs, and ADR-0016's warning that
two gates which disagree are worse than one is honoured by making the hosted
one run the same stages under the same names.

| | Runs on | Is the gate for |
| --- | --- | --- |
| `scripts/Invoke-LocalCI.ps1` | pre-commit (`-Quick`), pre-push, and by hand (`-Linux`) | Everything before a push. Unchanged |
| `.github/workflows/ci.yml` | push and pull request, Windows and Linux | What a contributor's pull request is judged by |
| `.github/workflows/release.yml` | a `v*` tag | Building and publishing the archives |
| `.github/workflows/docs.yml` | changes under `docs/` | That the generated documentation is not stale ([ADR-0075](ADR-0075.md)) |

### What hosted CI is *for*, which is not checking Daniel's work

The local gate already does that, on this machine, in about seven minutes,
before a push can happen. Restoring Actions is not a vote of no confidence in
it.

It is about three things a local gate structurally cannot do:

1. **Judge a pull request from somebody who is not Daniel.** A public
   repository will receive them, and *run this on your machine and tell me it
   passed* is not a gate.
2. **Build a release on a clean machine.** Every archive shipped so far was
   built on the one workstation that has been developing the product for a
   month. That is trap 7's shape exactly -- a round trip through one build
   says nothing about another build. A release built on a bare runner is the
   first evidence this product builds anywhere else at all.
3. **Run the advisory database.** The local `licences` stage deliberately runs
   `cargo deny check licenses` only, because RustSec needs a network and a
   gate that fails on a train is a gate people learn to skip. CI has a network
   as a promise rather than a hope, so it runs `cargo deny check` whole.

### What is deliberately not changed

**The hooks still run the local gate**, and pre-push still runs it in full.
Waiting on a runner to be told about a formatting error is worse than seven
minutes.

**`Invoke-LocalCI.ps1` remains the definition of the gate.** The workflow
mirrors its stages and names them identically, so a red stage is looked up in
one place. When the two drift, the local one is right.

**The Linux leg still goes through WSL locally** and through a real
`ubuntu-latest` runner in CI. Those answer different questions -- *does this
build under the distro on this machine* and *does this build on a clean
Ubuntu* -- and both are worth having.

## Consequences

**There is nothing to undo at the repository level**, and that is the half
that would otherwise have been missed. ADR-0016 disabled Actions on the
repository precisely because editing a trigger only protects branches carrying
the edit. It is already `enabled: true` -- which is exactly why nobody
noticed the premise had moved.

**`docs/governance/LOCAL_CI.md` gains the second gate** rather than being
replaced by it.

**Two targets, not three.** [ADR-0072](ADR-0072.md) declined macOS, so the
matrix is `windows-latest` and `ubuntu-latest` -- the same two the local gate
covers.

**The first hosted run failed twice, and both were real.** That is the
evidence for this ADR rather than an embarrassment, so it is recorded here:

1. **Three RustSec advisories** the local gate had never been in a position
   to see, because it deliberately runs `cargo deny check licenses` only.
   [ADR-0078](ADR-0078.md) accepts them by name.
2. **A clippy lint that does not exist on the developer's machine.**
   `clippy::chunks_exact_to_as_chunks` fired in `bp-files`, and the local
   toolchain is 1.97.1 while `dtolnay/rust-toolchain@stable` takes the latest
   stable. **This is a fourth thing a local gate structurally cannot do**, and
   it was not in the list above: *notice that the toolchain has moved*. A gate
   pinned to one developer's `rustup` is a gate that ages with them.

**A release becomes a tag.** `New-Release.ps1` stays exactly as it is and
stays the way a release is built by hand; the workflow does the same work on a
clean runner and attaches the archives, the checksums and the notices to a
GitHub Release.

## The lesson

> **A decision document records why something was decided. It records nothing
> about whether the world it described still exists.**

`DECISIONS.md` is the record and it is a good one. But an Accepted ADR reads
as settled, and *settled* is how a false premise survives -- nobody re-reads
an accepted decision looking for something to disprove.

The check is cheap and specific: **an ADR whose reasoning rests on an external
fact should name the command that would test it.** ADR-0016 rested on *Actions
is not available*, and the command is one `gh api` call. It took five sessions
and a request to publish before anybody ran it.
