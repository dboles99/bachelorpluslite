# ADR-0080: The Insert Key Overtypes, And Two Surfaces Stop Mishandling Named Keys

**Status:** Accepted
**Date:** 2026-09-25
**Related:** [ADR-0018](ADR-0018.md), [ADR-0049](ADR-0049.md), [ADR-0052](ADR-0052.md)

## Context

Daniel reported that the cursor keys, Insert, Home, End, Page Up and Page
Down need to work in the application. The report did not say which surface
or which platform, so the first job was finding out which of the six were
actually broken, and in which of the two editor surfaces
([ADR-0018](ADR-0018.md)).

That was answered by driving the real window rather than by reading the code.
This session ran on Linux, with no person at a keyboard, so the window ran
under Xvfb and `xdotool` pressed the keys. **Each key was followed by a marker
letter, and then Ctrl+S**, so where every marker landed in the saved file says
where the caret went -- evidence in bytes, not a screenshot to be interpreted.

| Key | Default surface (`TextInput`) | `--editor-view` |
| --- | --- | --- |
| Arrows, Home, End, Ctrl+Home | works | works |
| **Page Up, Page Down** | **did nothing** | works |
| **Insert** | **did nothing** | **typed U+F727 into the document** |
| **F1--F12, and every other named key without a name here** | ignored | **typed a private-use character into the document** |

## Three defects

**Page Up and Page Down did nothing in the default surface.** Slint's
`TextInput` pages by its `page-height` property and refuses to move when that
is not taller than a line:

```rust
let offset = self.page_height().get() - font_height;
if offset <= 0 as Coord { return false; }
```

`page-height` defaults to zero and nothing in `app.slint` set it. Slint's own
`TextEdit` sets it to its scroll view's visible height; this product wraps a
bare `TextInput` in a `Flickable` and never inherited that line. It is now
`page-height: editor-scroll.height` -- the visible height, not the widget's,
because inside a `Flickable` the widget is as tall as the whole document and
would page to the end.

**Named keys typed garbage into the custom surface.** Slint reports a named
key as a private-use character -- F5 is U+F708, Insert U+F727 -- and
`translate_key` mapped the ones it knew and let every other one fall through
as `Key::Char`. `command_for` inserts any character that is not a control
character, so **pressing F5 wrote U+F708 into the document**, and the saved
file had it. The test beside `translate_key` said, in its own comment, that a
mismatch here means keys "would type invisible glyphs into the document" --
and then checked only the keys already on the list. That is
[trap 3](../../DECISIONS.md) exactly: the comment named the failure, and
nothing asked the question of the keys that were *not* listed.

`translate_key` now returns `None` for anything in U+F700--U+F8FF, the Apple
function-key block Slint borrows, and the test sweeps the whole block rather
than naming keys. It was watched failing first, on U+F704 (F1).

**Insert had no meaning in either surface**, which is the third defect and the
reason for the rest of this ADR.

## Decision: overtype

**Insert toggles overtype, as it does in Notepad.** While it is on, a typed
character replaces the one after the caret.

The rule lives in `bp-editor`, as R011 requires --
`bp_editor::overtype_span` decides what a keystroke replaces and
`Editor::overtype` does it -- and both surfaces ask it:

- **The end of a line is never overtyped.** Typing past it adds to the line.
  Overtyping the line break would pull the next line up one keystroke at a
  time, which no editor with the mode does and no user means. `\r\n` counts
  as an end as well as `\n`.
- **A selection is replaced whole**, in either mode -- that is what typing
  over a selection already means.
- **Enter splits the line** rather than eating the character after the caret.
- **A run of overtyping is one undo step** in the custom surface, like a run
  of typing. It could not reuse typing's merge, which extends one `Insert` in
  place: every overtyped character also *removed* one, and an undo that put
  back the typing without what it replaced would lose text. So the run keeps
  every op in order, and `undo` already inverts a transaction back to front.
- **The mode is the window's, not a document's, and it is never saved.**
  Notepad keeps it across tabs, and a mode that survives a restart is one the
  user has forgotten switching on.
- **Ctrl+Insert and Shift+Insert are copy and paste**, which Notepad still
  honours. Only a bare Insert changes the mode: a Shift+Insert that flipped it
  instead of pasting would change what every later keystroke does, silently.

**It shows.** The status bar says **Overtype** while it is on, in the accent,
on the same argument as the security label: insert is the ordinary case, and
a mode that changes every keystroke is the one thing a reader must be able to
see. The custom surface draws the caret as an underline one character wide;
`TextInput` draws a heavier bar, because its caret is drawn in the text colour
and a block would hide the character it is about to replace.

### How `TextInput` overtypes, when it has no such mode

`TextInput` calls its `key-pressed` handler before its own, and a handler that
rejects lets the key through. So in overtype mode the handler asks Rust how
far to select -- `overtype_span` over the rope, which is kept equal to the
widget's text on every edit -- selects it, and rejects. The widget's own
insertion then replaces the selection, which it already does correctly.

Reading the rope rather than the widget's `text` keeps the document off the
typing path (R011, trap 5). Slint reports the caret in UTF-8 bytes and this
workspace counts characters, so `Buffer` gained `byte_to_char` and
`char_to_byte`.

## Conceded

- **In the default surface each overtyped character takes two Ctrl+Z.**
  `TextInput` records replacing a selection as a removal and an insertion and
  never merges them. Nothing is lost -- four presses restore two overtyped
  characters exactly, which was checked at the window -- it is only slower.
  Fixing it would mean taking the undo stack away from the widget, which is
  the whole of what `--editor-view` is.
- **The caret offsets are properties Slint marks internal.**
  `cursor-position-byte-offset` and `anchor-position-byte-offset` carry the
  comment *"Internal, undocumented property, only exposed for tests"* in
  Slint 1.17.1's `builtins.slint`, and `state.rs` has avoided them for the
  status bar for exactly that reason. They are used here because there is no
  other way to know where the caret is. **If an upgrade removes them, the
  failure is loud** -- `slint-build` refuses to compile `app.slint` -- which
  is why this was acceptable where a silent change would not have been.
- **The arrows, Home and End were not reproduced as broken.** All of them
  worked in both surfaces on Linux, and a test now pins what each maps to. If
  they fail for Daniel it is either Windows-specific or it was Page Up and
  Page Down being reported with them. **That needs a person on Windows**, and
  it is the first thing to check at the next manual pass.

## Consequences

**A default of zero is a feature switched off, and nothing reports it.** A
refusal that returns `false` from inside a toolkit looks exactly like a key
the product never claimed. The only way it was going to be found was pressing
the key -- which five manual passes had not done, because nobody lists Page
Down as a thing to check.

**Driving the window no longer needs Windows.** `Drive-Window.ps1` is
Windows-only, and `project/NEXT_SESSION.md` treated window-driving as either
that script or a person. Xvfb plus `xdotool` drove the Linux build from a
cloud container with no display, and the marker-then-save technique makes
the result a diff rather than a judgement. It is
`scripts/drive-window-xvfb.sh` now, so nobody re-derives it. Its one trap: with no window
manager, the first input after the window maps is sometimes lost, and a run
where *nothing* changed is the harness, not the product. Rerun it before
believing it.

**And "suspect the pass before the product" was re-proved.** The first undo
probe typed a marker after undoing, and the result said overtype lost text.
It had not: Slint re-selects what an undo restores, and the marker replaced
the restored character. Moving the marker to the end of the line made the
defect disappear, because it had never been one.
