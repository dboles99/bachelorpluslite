# ADR-0077: Reporting A Problem Composes A Document, Because This Product Cannot Open A Browser

**Status:** Accepted
**Date:** 2026-09-10
**Depends on:** [ADR-0006](ADR-0006.md), [ADR-0012](ADR-0012.md), [ADR-0057](ADR-0057.md), [ADR-0075](ADR-0075.md)

## Context

A public release needs a route from "this is broken" to an issue somebody can
act on. The request was for in-app feedback that reaches GitHub.

The two obvious implementations are both closed to this product, and not for
technical reasons:

1. **Open the browser at a pre-filled issue URL.** That is launching a
   program. `bp-platform`'s own header refuses it in as many words: *a library
   that spawns processes on the user's behalf is a library that can be talked
   into spawning a different one.* [ADR-0057](ADR-0057.md) removed the last
   thing in this product that ran anything.
2. **POST to the GitHub API.** That is network access, which
   [ADR-0006](ADR-0006.md) forbids, and the website's central claim is that
   the program never makes a connection. A feedback button would make that
   claim false in the one place a privacy-minded user would look first.

**The interesting part is that neither refusal costs anything here**, because
the thing that actually makes a bug report useful is not the transport.

## What actually makes a report fixable

`.github/ISSUE_TEMPLATE/bug_report.yml` asks for the version, the renderer,
every resolved directory, the platform, and which of the two editor surfaces
was in use. It asks for those because reports without them cannot be acted on.

**All of it is already in Help > Diagnostics**, and a person filing an issue
in a browser has to go back to the program, find that menu row, copy it, and
paste it. Most will not.

So a browser button would deliver a *worse* report than the thing this product
is allowed to do.

## Decision

**Help > Report a Problem composes a complete, pre-filled bug report as a
document in a new tab.**

It is the same shape as File > Set as Default Editor
([ADR-0012](ADR-0012.md)): this product will not do the outward-facing act for
you, so it prepares the artefact and names the step.

The document contains:

- the issue template's questions, as headings with blanks to fill in;
- **the diagnostics already filled in** -- version, renderer, platform, and
  every directory as resolved on this machine;
- the URL to paste it into, written out as text.

And the URL goes on the clipboard, because that is the one part the user would
otherwise have to type from a dialog.

**Nothing is sent, nothing is launched, and nothing is opened but a tab in the
editor the user is already looking at.** It works with the network cable out.

### Why a document and not a dialog

A dialog cannot be edited, and the point is that the user *adds* to it: what
they did, what they expected. A dialog would mean composing the report
somewhere else and copying the diagnostics into it, which is the friction this
row exists to remove.

It is also [ADR-0075](ADR-0075.md)'s reasoning applied a second time. The help
opens as a document for the same reason, and the same sentence covers both:
**the product is a text editor, so the thing it should reach for is a
document.**

## Consequences

**The reports this project receives get better rather than merely easier**,
which is the opposite of what a browser button would have achieved. The
template's required fields arrive filled in.

**One more menu row that produces an artefact and names a step.** That is now
three: default-editor registration, the user guide, and this. The pattern is
worth naming as a pattern, because a fourth is likely.

**Nothing about the offline claim changes**, and the website can go on saying
so without an asterisk. That was the constraint that shaped the design, and it
produced a better feature than the unconstrained version would have.

**The clipboard is written without being asked twice.** `arboard` is already a
dependency and the clipboard already carries document text on copy, so this
adds no new capability -- but it is a write the user did not explicitly
request, so the row says it has happened.

## The lesson

> **A constraint that forecloses the obvious implementation is worth reading
> as a design brief rather than as an obstacle.**

"In-app feedback" almost always means a button that opens a browser. Two
existing decisions made that impossible here, and the natural response is to
record the feature as blocked.

What the constraint actually forced was the question *what makes a bug report
useful?* -- and the answer, the diagnostics, was already a menu row away and
was going to be omitted by most people using the browser version.

**The check is to ask what the feature is for, once its usual shape is
unavailable.** Here the usual shape was the worse one, and only the refusal
made anybody look.
