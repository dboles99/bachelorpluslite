# ADR-0041: Research Mode's Data Is `bp-storage`'s, Not A New Store

**Status:** Accepted
**Date:** 2026-08-21

## Context

D12 answered one half of research mode's foundation question: not
`bp-research`'s bibliography model (BibTeX, DOIs, citation styles), which
stays exactly what it is, untouched. It did not answer what research mode's
data model *is* -- only what it is not. `project/DECISIONS_NEEDED.md` carried
that gap forward as the still-open half: "what 'gathered data' means
concretely."

**The gap closed itself the moment ADR-0037 wired `bp-storage` in.** D12's
decision was never that research mode needed *no* relationship to any
existing store -- only that the scholarly citation crate was the wrong one.
`bp-storage`'s schema (`documents`, `tags`, the join between them) is generic:
a document's path, its extracted title, and whatever tags describe it. It is
not bibliography-shaped at all, and reusing it does not reopen D12 -- D12
ruled out one specific crate for one specific reason (citation infrastructure
answering a different question than design synthesis does), not every
existing store in the workspace.

By the time this ADR is written, `bp-storage` is no longer a passive schema
with 21 tests and nothing calling it: ADR-0037's Related Notes and Duplicate
Detection populate it with real titles and real tags (via `bp_semantic`
keyword extraction) every time a document is saved. That is exactly
"gathered data" in the sense ADR-0039 used the phrase -- material the user
has already produced, sitting in one place, ready to be read rather than
re-collected.

## Decision

**Research mode reads `bp-storage`; it does not get a store of its own.**
No new schema, no new persistence, no new crate holding rows. What it adds
is a synthesis layer -- pure functions over what `bp-storage` already
returns -- that turn a flat list of documents and tags into the kind of
thing ADR-0039 promised: insights, options, and recommendations.

### What a first "insight" concretely is

Four shapes, each derivable from the schema `bp-storage` already has, none
needing anything new from it beyond the query functions ADR-0037 added
(`related_to`, `documents_tagged`) plus one more, described below:

1. **Dominant themes** -- the most frequent tags across every recorded
   document, which describes what the user has actually been writing about
   over time, not what they intended to.
2. **Stale clusters** -- a tag whose documents have not been touched
   (`last_seen`) in a long time, surfaced as "these N notes about X have not
   moved" rather than silently forgotten.
3. **Under-connected documents** -- a document with no shared tags to
   anything else in the store, which is either genuinely novel or a note
   that never got tagged usefully; the report says which questions to ask,
   not which answer is right.
4. **Consolidation candidates** -- several documents sharing the same tag in
   large numbers, worded as a recommendation ("consider consolidating") the
   way ADR-0039's decision described, rather than as a bare statistic.

`bp-storage` needs one more read function for these to be built on real
data rather than guesswork: something like `tag_frequency(&self) -> Vec<(String, usize)>`
and `stale_documents(&self, tagged: &str, before: i64) -> Vec<DocumentRecord>` --
exact shape is implementation, decided when this is built, not fixed here.

### What this explicitly is not

Not a recommendation engine with a model behind it, not fuzzy, not scored.
Every "insight" above is a plain aggregate query with a fixed, inspectable
rule -- the same honesty this codebase already holds `bp-storage`'s
`possible_duplicates` to (ADR-0037: "a simple, honest v1... say so in the
doc comment"). If a future session wants genuinely generated
recommendations -- prose synthesised rather than arranged -- that reaches
for ADR-0033's OpenAI policy, opt-in, and is a separate decision layered on
top of this one, not a reason to delay shipping the plain version now.

## Consequences

- D12 is now closed in full: not `bp-research`, and concretely, `bp-storage`
  read through a new synthesis layer with no schema of its own.
- **Not yet implemented.** This ADR settles the data model; the crate or
  module holding the four insight functions, the `bp-storage` read function
  they need, and the Research menu row that surfaces a report through it are
  separate work, the same as every other ADR from this session that closes a
  design question without writing the code.
- `bp-research` (the bibliography crate) is completely unaffected -- nothing
  here reads it, extends it, or depends on it existing.
- The four insight shapes above are a *starting* set, not an exhaustive
  design. Nothing prevents a later session adding a fifth once this one
  ships and it becomes clear what is actually useful to see, the same way
  `bp-storage`'s own schema was built to grow with the phases that need more
  of it.
