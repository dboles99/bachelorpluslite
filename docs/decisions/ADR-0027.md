# ADR-0027: The Large-File Engine

**Status:** Accepted
**Date:** 2026-08-19

## Context

specs.md section 5 asks for large-file detection, read-only initial handling
for very large files, chunked loading, streaming search and a memory-mapped
read-only mode. Section 22 says multi-GB files must be "usable in large-file
mode", and gives the budget everything else here is measured against: 150 ms
to window, 250 ms to first interaction, 50 MB idle.

Nothing in `bp-buffer` distinguished a 4 KB note from a 2 GB log. The
ordinary path reads the file, validates it as UTF-8 and builds a rope, and
the question is where that stops being affordable — twice, because "warn and
defer the expensive work" and "do not load this at all" are different answers
to different problems.

Both thresholds are measured on the benchmark corpus in
`benches/large_file.rs` (72-byte lines, the shape of prose and source alike).
The numbers below are from a Windows 10 x86-64 workstation, release build,
rustc 1.97.1, 2026-08-19; re-running the bench reproduces them or re-derives
them on other hardware.

| File | cold read | UTF-8 check | build rope | **total cold** | resident |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 6 MiB | 65.5 ms | 0.4 ms | 8.8 ms | **74.6 ms** | 7.2 MiB |
| 8 MiB | 77.3 ms | 0.5 ms | 12.1 ms | **90.0 ms** | 9.5 MiB |
| 10 MiB | 89.6 ms | 0.8 ms | 15.3 ms | **105.7 ms** | 11.8 MiB |
| 12 MiB | 108.0 ms | 1.1 ms | 19.2 ms | **128.3 ms** | 14.1 MiB |
| 16 MiB | 142.2 ms | 1.7 ms | 25.5 ms | **169.4 ms** | 18.7 MiB |
| 192 MiB | 319.1 ms | 24.3 ms | 378.2 ms | **721.6 ms** | 222.9 MiB |
| 224 MiB | 342.1 ms | 28.0 ms | 384.0 ms | **754.1 ms** | 260.0 MiB |

## Decision

### `LARGE_FILE_BYTES` is 8 MiB, and it falls out of the top of that table

Section 22's 150 ms to window and 250 ms to first interaction leave about
100 ms for getting content on screen. A cold open of 8 MiB costs 90.0 ms —
the last size that fits. 10 MiB costs 105.7 ms, which is the budget gone
before anything is drawn.

So the ordinary path stops at 8 MiB: a measured ceiling that happens to be
round, not a round number assumed to be a ceiling. The comparison is strict,
because the measurement said 8 MiB fits — a file of exactly that size is
still `SizeClass::Normal`. An off-by-one here moves the class of every file
sitting on the threshold, so the direction is stated rather than inferred.

### `HUGE_FILE_BYTES` is 192 MiB, and it falls out of the bottom of it

The rope costs a measured 1.16x the file on the heap, and that multiplier
holds to three digits across every size in the table, so a ceiling on
resident memory is a ceiling on file size. 256 MiB resident is as much as a
text editor has any business spending on one document — section 22 budgets
50 MB idle — and 1.16x puts that at about 220 MiB of file. 192 MiB is the
largest 64 MiB step under it, measured at 222.9 MiB resident; 224 MiB is the
first step over, at 260.0 MiB. Past 192 MiB the document is not loaded at
all: it is served from disk in chunks and opened read-only.

Three size classes rather than a boolean, because the two thresholds say
different things to the caller: one says "warn and defer the whole-document
work", the other says "do not load this".

`Access` keeps the two read-only *reasons* apart for the same kind of reason.
A file that is read-only on disk becomes editable when its permissions
change, and Save As is the way out. A document read-only because it is 2 GB
stays read-only however the permissions change, and the way out is a
different tool or a smaller slice. Size wins when both apply, because size is
why edits are refused *while typing*, which is what the user meets first.

What the chunked path costs instead, on a 255 MiB file from the same run:
opening it 0.19 ms, the first sixty lines 0.35 ms, indexing all 4,067,204
lines 181 ms (1.38 GiB/s), and streaming every byte past a matcher 373 ms
with a 2,056 KiB peak. Opening is `metadata`; the first frame is one seek and
one chunk; neither grows with the file.

### The line index is sparse, with a doubling stride

The obvious line index is a `Vec<u64>` with one entry per line. On the 2 GB
file section 5 asks us to open, that is 25 million entries and 200 MB of
index — more than the memory budget for the whole document, to answer a
question the user asks about forty lines at a time.

So the index keeps the start of every `stride`-th line and doubles `stride`,
discarding every other anchor, whenever it would outgrow its cap. The cap is
`MAX_ANCHORS` = 65,536 anchors, which is 512 KiB of `u64` — a rounding error
against the streaming budget, while still giving exact answers at stride 1
for any file under about 65,000 lines, which is most of what anyone actually
opens.

"Where does line N start" becomes "here is a known offset at most `stride`
lines before it, scan from there". A bounded scan is the price of a bounded
index, and it is the right trade: the scan is sequential I/O over a few
kilobytes, and the alternative is an index larger than the memory bound it
was supposed to protect. Halving is done in place, so the `Vec`'s capacity —
which is what the bound is stated against — never grows past the cap.

The index is also incremental: `push` takes consecutive chunks in file order,
so indexing spreads across frames rather than blocking the first one, and
every question is answered against the prefix indexed so far. Chunks must
arrive in order and without gaps, because the index tracks absolute offsets
and cannot detect a skipped region — a caller that seeks between calls gets a
plausible-looking index that is wrong everywhere after the seek.

Chunk boundaries are the defect to hunt, and one fact makes half of it safe:
`\n` is `0x0A`, and no byte of a multi-byte UTF-8 sequence is ever below
`0x80`. A newline cannot hide inside a character, so counting newlines over
raw bytes cannot be confused by a chunk that splits one. Decoding is a
different matter, and belongs to the streaming reader.

### `locate` distinguishes "not yet indexed" from "past the end"

Four answers, not `Option<u64>`: `At`, `After`, `NotYetIndexed`, `PastEnd`.

"I have not looked that far yet" and "there is no such line" lead to opposite
actions — index more, or tell the user — and collapsing them into `None` is
how a viewport ends up permanently blank at the bottom of a file. The index
refuses to say `PastEnd` until `finish` has been called, because before that
the honest answer is `NotYetIndexed`.

For the same reason `exact_range` returns `None` rather than guessing
whenever either end needs a scan. A range that is sometimes exact and
sometimes approximate is a range nobody can safely use.

### The memory bounds are functions with no file length in them

That is the whole claim, and it is stated as arithmetic so it can be
asserted rather than believed.

`LargeFile::memory_bound_bytes()` is the index cap, plus one 256 KiB scan
buffer, plus the longest line the viewport will materialise
(`MAX_DISPLAY_LINE_BYTES` = 64 KiB), plus the largest result one
`display_lines` call can return (`MAX_DISPLAY_BYTES` = 1 MiB), plus headers
for `MAX_DISPLAY_LINES` = 4,096 lines allowing for a `Vec` that doubled once.
The three display caps are not decoration: without them a caller asking for a
million lines makes the bound false, and a line cap alone is not a bound
either — 4,096 lines of 64 KiB is a quarter of a gigabyte, which is worse
than the file the caller was avoiding loading. A generated file can hold a
single 400 MB line; it is cut, and `DisplayLine::truncated` says so rather
than the UI silently showing a prefix.

`WindowReader::memory_bound_bytes()` is the read buffer, plus the largest
carry the line-alignment trim can leave (half a window plus up to three bytes
of a split character), plus the repeated prefix, plus the one window handed
out. The two bounds are reported separately rather than summed, because they
are configured separately and adding them would hide which one moved.

Streaming's constants come from the same reasoning: a 1 MiB window is two
orders of magnitude larger than any pattern anyone types and two orders
smaller than the files this exists for; a 4 KiB minimum overlap means no
match a person types can fall between two windows, and is 0.4% of the window,
which is what makes the repeated scanning free.

### Memory mapping is declined

specs.md section 5 lists a memory-mapped read-only mode. This does chunked
`read` instead, and the decision is written down rather than silently taken:

1. **It cannot be done without `unsafe`.** Every mapping crate's entry point
   (`memmap2::Mmap::map` and equivalents) is an `unsafe fn`, and `bp-buffer`
   is `#![forbid(unsafe_code)]`. Every editing path in the application goes
   through this crate; trading that guarantee away for one feature is not a
   trade one agent should make alone.
2. **The unsoundness is not theoretical here.** A mapping is undefined
   behaviour if the file is truncated underneath it — the next touched page
   raises `SIGBUS` on Linux and `EXCEPTION_IN_PAGE_ERROR` on Windows, neither
   catchable in safe Rust. This editor already assumes files change
   underneath it: `bp-files::watch` exists precisely to detect that, and
   ADR-0007 makes external-change detection a v1 requirement. A network share
   or a removable volume disappearing does the same thing. The hazard is one
   the product design has already conceded is real.
3. **ADR-0002 already counts mapping as attack surface**, alongside parsers
   over untrusted files.
4. **The measured benefit is the smaller half.** Mapping removes a copy from
   the read, and the read is not where the time goes: at 192 MiB the cold read
   is 319.1 ms against 378.2 ms to build the rope and 24.3 ms to validate, and
   warm sequential reads here run at 1.7 GiB/s — already faster than any
   consumer of the bytes. Chunked reads sustain 1.38 GiB/s through the line
   indexer over a 255 MiB file, the same order, and they keep the property
   that actually matters: opening a 2 GB file touches kilobytes rather than
   gigabytes, measured at 0.19 ms whatever the size.

**What mapping would buy, so a human can reverse this**: roughly the read
half of a cold whole-file scan, and simpler random access for the line-start
scan. **What it would cost**: `unsafe` in the crate every edit passes
through, an unsound-by-construction failure mode on external truncation that
would need its own mitigation (copy-on-open, or a platform-specific `SIGBUS`
handler, neither of which is small), a new third-party dependency, and
ADR-0002 revisited. Left as a stated decision for a human, not taken here.

## Consequences

- The thresholds are hardware-dependent and the numbers above are one
  machine's. They are constants in the source with the measurement beside
  them, so re-deriving them is re-running a bench rather than an argument.
- Indexing takes a byte budget, not a deadline. A deadline needs a clock and
  this crate reads none, which is what lets `bp-buffer` be tested without a
  window. `INDEX_BUDGET_BYTES` is 4 MiB: newline scanning runs at over
  1 GiB/s in release, so that is a small fraction of a 16 ms frame — enough
  that a 2 GB file indexes in a few seconds of background work, little enough
  that no single call is visible as a stutter.
- A file above `HUGE_FILE_BYTES` is read-only and stays read-only. specs.md's
  large-file mode is a viewer, and nothing here makes it an editor.
- Streaming reports byte offsets and line numbers, never absolute *character*
  offsets, because a character offset cannot be known without decoding every
  byte before it — the exact walk streaming exists to avoid.
- Windows begin and end on line breaks wherever the text allows, so a line
  number computed inside a window is a line number in the file. A file that is
  one enormous line forbids making that a guarantee, which is why
  `StreamWindow::starts_mid_line` exists rather than being assumed away.
- Deduplicating matches across windows tests *end* past the overlap, not
  start. A match wholly inside the repeated prefix was seen whole last time; a
  match that starts in the prefix and runs past it was truncated last time and
  never matched at all. Testing `start` silently drops exactly the matches the
  overlap exists to catch.
- Invalid UTF-8 is reported with the offset of the first bad byte rather than
  decoded lossily, for the reason `bp-files` gives: a lossy decode lets
  someone edit and save mangled text over their original.
