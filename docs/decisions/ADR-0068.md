# ADR-0068: The Icon Ships Beside The Executable, Because There Is No Installer

**Status:** Accepted
**Date:** 2026-08-30
**Closes:** `project/WORK_QUEUE.md`'s P2
**Depends on:** [ADR-0067](ADR-0067.md)
**Amends:** [ADR-0012](ADR-0012.md)

## Context

P2 was queued as *"an application icon, and the `.desktop` file
`bp_platform::editor::desktop` already knows how to write"*, and sized with a
warning: **"Windows takes it from the executable, which needs a build-time
resource — a new dependency, so an ADR."**

That was true of the design as it stood, and the design changed under it.
Taking the inventory first — as this session has now had cause to do six
times — found something else.

## What the inventory found

**Both halves of ADR-0012's registration already named an icon that does not
exist.**

- **Windows.** `editor/windows.rs` wrote `DefaultIcon` as `"<exe>",0` — icon
  index 0 of the executable's own resources. **The executable has never had an
  icon resource.** Every file type registered through File ▸ Set as Default
  Editor rendered as a blank page in Explorer.
- **Linux.** `editor/desktop.rs` wrote `Icon=io.github.dboles99.BachelorPadPlus`
  — a theme name, resolved against `hicolor`. **Nothing has ever installed a
  file there**, so the entry named nothing.

So P2 was not a polish item. It was a defect in a shipped feature, and the
row that described it as an icon *asset* problem was describing the smaller
half.

## Decision

**The icon ships in the archive, beside the executable, and everything points
at it there.**

`bp_platform::editor::icon_file_name` names it per platform —
`bachelorpad.ico` and `io.github.dboles99.BachelorPadPlus.png` — and
`icon_beside` resolves it from wherever the executable turned out to be.

### This removes the dependency rather than adding one

[ADR-0067](ADR-0067.md) decided there is no installer, and that decision
**settles this one**. An installer is the usual thing that places an icon into
a system icon theme; with none, the icon has to travel in the archive and be
referenced where it lands.

Which means the Windows registry does not need the icon *inside* the
executable at all. `DefaultIcon` takes any path, so it takes the `.ico`
already sitting beside the binary — **and the build-time resource compiler
that P2 was sized around is not needed.** The file the archive was going to
carry anyway does the job.

The same reasoning fixes Linux for free: `Icon=` accepts an absolute path as
well as a theme name, so it gets one. The theme name stays as the fallback,
which is what a *packaged* build would want and costs nothing to keep.

### The artwork

Drawn from the **Green palette in `bp-theme`** rather than chosen: a light
page with a folded corner and three rules, on the shell colour, with the
accent on the crease and the last rule.

Two things about it are decisions rather than taste:

- **The page is `ink`, not `panel`.** Panel and shell differ by about five
  values per channel — ample inside a window, where borders and area do the
  separating, and *invisible* at 16px where the mark itself is all the
  separation there is. The first draft used `panel` and disappeared into a
  dark square. **An icon is not a small screenshot.**
- **Below 32px the mark simplifies**: two thick bars instead of three thin
  ones, and a larger fold. Three rules at 256 are 0.75px at 16 and turn to
  mush. That is what an ICO's size list is *for*, and shipping the same
  geometry at every size wastes it.

It is a real icon rather than a placeholder, and it is also easy to replace:
one PNG and one ICO in `assets/`, with tests that will fail if a replacement
is the wrong format or size.

### The window icon is the PNG on both platforms

Slint 1.17 has no Rust setter for a window icon, so `AppWindow` gains an
`in property <image> window-icon` and Rust loads a PNG into it. **Not
`@image-url`**, which would embed a copy at compile time and leave an icon to
keep in step with the one registration points at.

It fails silently. A missing or unreadable icon gives the toolkit's default,
which is a cosmetic loss; refusing to start over it would turn a cosmetic loss
into an outage.

**And the silence hid a defect for an hour.** The first version pointed the
window icon at whatever registration named, which on Windows is the `.ico` --
and **Slint 1.17 builds the `image` crate with `png` and `jpeg` only.** There
is no ICO decoder, so the load failed, and by design nothing said so.

It was caught by building an archive, extracting it, and reading the file
list. Not by a test, not by running the app, and not by review: the code was
correct-looking, the app started, and the window simply had the toolkit's
icon.

So the two are separate functions with separate names. `icon_file_name` is
what *Explorer and the desktop* read; `window_icon_file_name` is what *Slint*
reads, and is the PNG always. The Windows archive carries both, which costs
1.3 KB and removes the class of question. `window_icon_file_name` writes its
value out rather than calling `icon_file_name(Platform::Linux)` — the two are
equal today and for unrelated reasons, and a caller reading one for the other
would be right by accident.

A test asserts the window icon's name ends in `.png` on every platform, and
that `New-Release.ps1` stages it. **A silent failure needs a louder test than
a loud one**, and gets one less often — which is the same lesson `recent.toml`
taught under ADR-0050.

## Consequences

**`bp_platform::paths::parent` is new, and it is at the platform seam for
trap 2's reason.** `std::path` must not answer "what directory is this file
in" for a function that takes a `Platform`: a backslash path has a parent on
Windows and is a single filename on Linux, and a `std::path` answer is only
ever right on the host that ran it. Both legs of the gate check the same code,
and its doctest asserts both answers.

**Three tests, and each guards a different way this can rot.**

- The asset a plan *names* must exist, **and the release scripts must mention
  it**. Those scripts are PowerShell and shell; nothing type-checks them
  against this crate, so the agreement is asserted by reading them. Without
  it, an archive could ship with registration pointing at a file that is not
  in it — which is precisely the state this ADR found.
- The path must follow the executable and the platform, including the case
  with no parent, where guessing would write a dead path into a `.desktop`.
- **The assets must be the format their names claim.** `is_file()` is
  satisfied by an empty file, which is what a mangled copy leaves behind — and
  since the window icon fails silently by design, nothing at runtime would
  report it. The PNG's signature and IHDR dimensions are checked, and the
  ICO's header, size count, and that every directory entry points inside the
  file.

**Both release scripts now fail loudly if the asset is missing**, rather than
producing an archive whose registration points at nothing.

## The lesson

> **A queue row describes the work somebody expected, not the work that is
> there.**

P2's row named a dependency decision — *"Windows takes it from the
executable"* — and that sentence was true when it was written and had stopped
being the constraint by the time anyone took it. What changed it was not new
information about icons. It was **ADR-0067**, decided an hour earlier, which
removed the installer and therefore the reason the icon had to be inside
anything.

This is [ADR-0067](ADR-0067.md)'s own lesson pointed the other way. There, a
decision was already made by the decisions around it. Here, an *estimate* was
already invalidated by them — and the row still read as authoritative because
it was written down in a table.
