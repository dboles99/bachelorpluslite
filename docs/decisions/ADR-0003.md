# ADR-0003: Semantic Filename Grammar

**Status:** Accepted
**Date:** 2026-08-16
**Amended:** 2026-08-17 (component ordering)

## Context

specs.md section 2 fixes the shape of a default filename and requires both a
revision suffix and a collision suffix, but does not say where each sits
relative to the date. An implementation has to choose, and the choice has to
be stable because it determines what old filenames parse as.

## Decision

The grammar is:

```text
<Title>[_v<N>]_<DDMMMYYYY>[_<NN>].<ext>
```

- The date is the creation date (ADR-0004), formatted `16AUG2026`: two-digit
  day, uppercase three-letter English month, four-digit year.
- The revision suffix `_v2`, `_v3` sits with the title, because it is part of
  what the document *is* -- a deliberate new version the user asked for.
- The collision suffix `_02`, `_03` sits last, because it is a mechanical
  disambiguator applied at write time and carries no meaning.
- Numbering for both starts at 2; `_v1` and `_01` are never emitted.
- Invalid filesystem characters are sanitised; Windows reserved device names
  are defused. The union of Windows and Linux rules applies on both.
- Semantic rename and physical move always require explicit user approval.

## Consequences

- The date is a fixed-width anchor with at most one numeric segment after it,
  so parsing is unambiguous without a separate index.
- A title that itself ends in `_v2` is indistinguishable from a revision
  suffix. This is accepted and documented in `bp-naming`; it is inherent to a
  suffix grammar over free-form titles.
- Only canonical suffixes parse, so a render/parse round trip never silently
  rewrites a user's filename.
- Implemented in `crates/bp-naming`.
