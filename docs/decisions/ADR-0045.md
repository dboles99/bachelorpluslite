# ADR-0045: A Markdown File Is A Notebook, And The Panel That Lists Things Is One Component

**Status:** Accepted
**Date:** 2026-08-21

## Context

[ADR-0043](ADR-0043.md) named the next step and declined to take it:

> **Markdown fences are the obvious next step and are not in this change.**
> The same purpose — a README whose examples are verified — wants
> ```` ```python ```` blocks in an ordinary `.md` file to be runnable too.
> That needs a fence parser and a decision about what names a block.

[ADR-0044](ADR-0044.md) left a different question open, in the same area:

> A results panel with clickable rows would be better for jumping to each
> hit, and it is deliberately not built here: it would be a third near-copy
> of `results_panel.slint` … **Whether those three should become one
> component is a question worth answering once, not a thing to prejudge by
> adding a fourth.**

Both come due here, because the thing that wants a panel is the thing the
fence parser makes possible.

## Decision

### A Markdown document is read as a `Notebook`, not as a new model

`bp_notebook::Notebook` already models an ordered sequence of prose and code
where each piece knows its own language. A README with fenced blocks *is*
that. So `markdown::parse` produces one, and **everything built on `Notebook`
works on a `.md` file without knowing it came from one** — including
`request_run`, which means consent, the refusal of a prose cell, and the
`UserGesture` requirement all carry over untouched rather than being
re-implemented for a second kind of document.

That is the whole reason this change is small. The Run menu, the run panel,
the timer and the one consent site are unchanged; what was added is a parser
and one `match` arm choosing it.

### What names a block: the fence's info string, through the existing table

`CellKind::from_language_name` is the function a `.ipynb`'s kernelspec
already goes through. Sending fences through it too means ` ```python `,
` ```py `, ` ```bash ` and a notebook whose kernel is `python3` all arrive as
the same kind, and there is no second spelling table to drift from the first.

**A fence naming no language, or one this build does not recognise, becomes
`CellKind::Raw`** — carried verbatim, never run. Identical to what `ipynb`
does with a code cell it cannot identify, and for the reason that crate
gives: "keep the bytes and do nothing" is the only safe answer to text whose
language we would otherwise be guessing at. An unlabelled block is not an
error; it is a block this product declines to guess about.

**Indented code blocks stay in the prose.** Four spaces makes something code
in CommonMark, but it names no language, so it could never be run — lifting
it out would produce a `Raw` cell saying nothing the prose did not.

### A row is named by its line, not by a cell number

A `.ipynb` has cells in order and a reader can count them. **A `.md` has no
cells written in it at all** — they are this product's reading of the file —
so "Cell 3" would name something the reader cannot find. A line number they
can go to.

`MarkdownDocument::line_of` carries it, shaped like `Import`: the useful
thing plus the context needed to say something honest about it.

The converse is recorded rather than papered over: **a `.ipynb` cell has no
line**, because the line a reader would scroll to is the line of a `"source"`
array inside JSON, which `bp-notebook` has no reason to record.
`Source::line_of` returns `None` there, and a click on such a row leaves the
reader where they are rather than scrolling somewhere arbitrary.

### One `ListPanel`, and the answer to ADR-0044's question is "yes"

`results_panel.slint` and `organize_panel.slint` were **structurally
identical**. Running `diff` over them with the names normalised showed
differences in their comments and nothing else — not one element, property or
binding apart.

So they become one `ListPanel`, with the single thing they disagreed about as
a property: how wide the label column is, because a file path needs more room
than `Line 42 · Python`. Three uses now: cross-file search results, Organize ▸
Related Notes, and the outline below.

### Notebook ▸ Cell Outline is an outline, not a runner

It lists **every** cell, prose included, which is exactly where it differs
from the Run menu: the menu offers what can run, and an outline is a map of
the whole document. A reader of a runbook wants the prose headings between
the examples — that is most of what makes it a runbook rather than a script.
A marker on each row says which ones the Run menu would offer, so the two
agree in front of the reader rather than only in the code.

**Clicking a row goes to the cell. It does not run it.** A click is a
perfectly good gesture and consent would be satisfied — but there is exactly
one place in this product where `UserGesture::from_user_command()` is called,
and keeping it that way is worth more than saving a trip to the menu. A
second site is how "run on click" ends up somewhere nobody meant it to be.

## Consequences

- `bp-notebook` gains a Markdown reader and stays pure: no clock, no
  filesystem, no configuration, and `parse` returns no `Result` because
  Markdown has no invalid form — an unclosed fence is a fence that reaches
  the end.
- Two `.slint` files are deleted and one is added. `docs/architecture/
  ARCHITECTURE.md`'s file list changes with them.
- The Run menu's "nothing to run here" row now names both kinds of document,
  and its unnamed-language row says something different for each: a notebook
  needs a kernelspec, a fence needs a word after its backticks. Same
  situation, different fix, and a single message would have been wrong for
  one of them.
- **A `.md` is now a document with two readings** — text in the editor, cells
  in the Run menu and the outline — and nothing forces them to agree except
  that both are computed from the same bytes on every refresh. That is why
  neither parse is cached.
- Rendering Markdown as *formatted* prose remains blocked on what it always
  was: Slint has no HTML view. This change makes a `.md` more useful without
  touching that, which is worth noting because it is easy to read "Markdown
  support" into a menu that has none of it.
