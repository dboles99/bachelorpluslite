# ADR-0079: The Fuzz Harness Silences The Panic Hook, Because The Budget Was Timing It

**Status:** Accepted
**Date:** 2026-09-10
**Depends on:** [ADR-0073](ADR-0073.md), [ADR-0074](ADR-0074.md)

## Context

The second hosted run failed on the Windows leg, in the fuzz stage, on the
harness testing itself:

```
test tests::a_panic_is_caught_and_its_message_kept ... FAILED
  left: Some(Hang { budget: 20s })
 right: Some(Panic { message: "the message" })
```

The body of that probe is `panic!("the message")`. It cannot hang. The Linux
leg passed, and so did the local gate on both legs -- twice, either side of
the failure.

## What actually happened

`Probe::run` spawns a thread, the thread runs `catch_unwind` around the body,
and sends the result back down a channel. The parent waits with
`recv_timeout(budget)` and calls the input a hang if that expires.

**`catch_unwind` does not return until the panic hook has finished.** The hook
runs during the unwind, before the payload reaches the caller, so everything
the hook does is inside the window the parent is timing. `ci.yml` sets
`RUST_BACKTRACE=1`, so the hook was the default one, symbolising a backtrace.

On Windows that means dbghelp loading the PDBs for the test binary, which
links `bp-files`, `bp-formats`, `bp-security` and `proptest` in a debug
profile. The first backtrace in a process pays for all of it, and this was
the first panic in that process -- the two tests before it do not panic.

**It took more than twenty seconds, and that number is not an estimate.**
`Hang` is produced in exactly one place, when `recv_timeout` expires; the only
work between the spawn and the send is the `catch_unwind`; the budget was
twenty seconds.

So the harness was not measuring the input. It was measuring itself reporting
on the input, and attributing the result to the input.

## The decision

**Install a panic hook, once, that stays quiet for threads the harness
spawned, and delegates to the previous hook for every other thread.**

Probe threads are named with `PROBE_THREAD_PREFIX`, and the hook keys on that
prefix. The harness already recovers the message from the payload and reports
it with the input name, so for those threads the default hook was printing a
second copy of something the harness prints anyway -- and charging the input
for it.

Every other thread keeps the hook it had, including the test thread when an
assertion inside this crate fails. Going quiet everywhere would have made the
harness harder to debug in exchange for nothing.

## What this costs

The automatic backtrace on a real finding.

That is a genuine loss and it is still the right trade. A panic misreported as
a hang has thrown the message away for good, and the message is the reason
`catch_unwind` is there at all. A backtrace, by contrast, can be had again on
demand: the corpus entry is checked in, its name is in the failure, and one
`cargo test` with the hook removed reproduces it.

## Alternatives that were rejected

**Raise `DEFAULT_BUDGET`.** It would have turned the run green, which is
exactly the problem -- the defect is not that twenty seconds is too short, it
is that the budget measures the wrong thing. A larger number moves the
threshold without changing what is being timed, and a genuinely wedged parser
would then hold the gate for as long as the new number says.

**Unset `RUST_BACKTRACE` in `ci.yml`.** It fixes the symptom on one machine
and leaves the harness charging hook time to inputs everywhere else, including
for anyone who sets the variable themselves while debugging -- which is
precisely when they are most likely to hit a real panic.

**Take and restore the hook around each probe.** `set_hook` is process-wide,
probes run in parallel under libtest, and two of them swapping hooks race.

## What now fails if this regresses

Two tests, because one was not enough.

`a_panic_is_reported_as_a_panic_on_a_budget_that_leaves_no_room_to_print`
runs the same instant panic under a 500 ms budget. That is ample for a thread
spawn and a channel send on any machine that can run the suite, and nowhere
near enough for a hook doing real work. Had it existed, the hosted run would
have failed on a Windows laptop long before a runner saw it.

`a_probe_thread_carries_the_prefix_the_panic_hook_keys_on` ties the naming
site to the reading site. The hook decides by thread name; if the two stopped
agreeing the hook would go quiet for nothing, the budget would start timing
backtraces again, and **every other test in the file would still pass.** This
is [ADR-0074](ADR-0074.md)'s lesson applied before it costs anything rather
than after.

## The lesson

**A timeout measures everything inside it, including the code that reports
the result.** The comment on `DEFAULT_BUDGET` said "a slow machine under a
cold cache is not a defect. Anything past this is not slow, it is stuck" --
and it was wrong in a way no reading would have caught, because the sentence
is about the input and the budget was not.

This is trap 3 with a stopwatch. *What would fail if this stopped being
true?* Nothing did, for as long as every machine that ran it happened to have
warm PDBs.

And the second half: **the local gate is not the hosted gate, and this is the
second time in one day that the difference was the point.**
[ADR-0078](ADR-0078.md) was the first. ADR-0073 restored hosted CI to check
things the local gate cannot; it is now doing that, and the finding is the
argument.
