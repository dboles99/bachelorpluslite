# ADR-0011: Security Architecture

**Status:** Accepted
**Date:** 2026-08-16

## Context

specs.md section 15 requires encrypted `.bpadx` documents, passphrase
protection, per-document security profiles, privacy mode, secret scanning,
hashing, signatures, redaction and audit history. Section 24 lists the threat
categories these answer.

## Decision

- Protected documents use established KDF and AEAD implementations. **No
  custom cryptography**, which means no hand-written ciphers, KDFs or MACs:
  every primitive comes from a vetted crate.

  Clarified 2026-08-19: this does *not* forbid designing the `.bpadx`
  envelope itself. Its layout, its version scheme and how it frames AEAD
  segments are ours to specify, because no off-the-shelf format supplies
  them and phase 15 cannot proceed without one. The line is between
  *composing* vetted primitives, which is unavoidable, and *implementing*
  them, which is not permitted. Both were once read as "custom
  cryptography"; only the second is.
- The `.bpadx` envelope is versioned and platform-neutral; a document written
  on Windows opens on Linux.
- Platform key protection (DPAPI, Windows Hello, Linux Secret Service) is an
  optional convenience layer over the passphrase, never a replacement that
  would make the document unopenable elsewhere.
- Security policy propagates from the document to every derived artefact:
  autosave, recovery journal, revision history, clipboard persistence,
  semantic metadata, embeddings, temporary files, audit events and network
  eligibility.
- Notebook code never auto-runs -- not on open, not on paste, not on restore.

## Consequences

- A feature that persists anything derived from a document must consult the
  document's security profile first; "it only went to a temp file" is not an
  exemption.
- Wrong-passphrase, corrupted-ciphertext and authentication-failure paths are
  required tests, not edge cases.
