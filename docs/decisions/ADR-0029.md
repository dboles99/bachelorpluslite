# ADR-0029: One Definition of a Line

**Status:** Accepted
**Date:** 2026-08-20

## Context

This product has two answers to "what is a line", and a user can see both at
once.

`bp_search::Offsets` finds line starts by looking for `'\n'` and nothing else.
`bp_buffer::Buffer` is a `ropey::Rope` built with ropey's default features,
which include `unicode_lines` — so the rope also breaks on a bare `\r`,
`\x0B`, `\x0C`, U+0085, U+2028 and U+2029. For a document containing any of
those, a find reports one line number and the caret reports another: the
results panel scrolls to the wrong line, and "go to line 12" from a search
result lands somewhere else.

A bare `\r` is not exotic. It is what a file written on a classic Mac
contains, and what a program that drew a progress bar leaves behind.

**The disagreement is not only between crates.** `bp-buffer` has two public
answers of its own: the free `line_count` counts `'\n'`, and
`Buffer::len_lines` asks the rope. `bp-ui`'s status bar uses the first under
one editor view and the second under the other, so the same document reports
two different line counts depending on which view is showing it. That is
visible today, without a search.

### The rest of the product already decided this

The question looks open and is not. Four places have already committed to
LF and CRLF, and only the rope has not:

| Where | What it says |
| --- | --- |
| `bp_core::LineEnding` | exactly two variants, `Lf` and `CrLf` |
| `bp_files::encode` | "a bare carriage return is data, not a break, and is never rewritten" |
| `bp_buffer::line_count` | counts `b'\n'` |
| `bp_buffer::line_len` | "strip the line break, CRLF or LF" |
| `bp_editor::view::content` | strips a trailing `'\n'`, then a trailing `'\r'` |
| `bp_search::Offsets` | counts `'\n'` |

`ropey`'s `unicode_lines` is the only voice for the wider set, and it was
never chosen — it is the crate's default, inherited by writing `ropey = "1"`.

## Decision

**Build the rope without `unicode_lines`, so that a line break in this
product is `\n` or `\r\n` and nothing else.**

Precisely: `ropey = { version = "1", default-features = false, features =
["simd"] }`. Dropping `unicode_lines` alone would not be enough, because ropey
declares `unicode_lines = ["cr_lines"]`, and `cr_lines` still breaks on a bare
`\r` — the very character `bp-files` calls data. `simd` is kept: it is a
performance feature with nothing to say about lines.

### Why not the other direction

The alternative is to teach `bp-search` ropey's break set. It is a smaller
diff in one sense — one crate's line counting — but it is the wrong way round
for three reasons.

It would put the *search* and the *buffer* in agreement while leaving both
disagreeing with `bp-files`, which writes the file, and with `bp-core`, which
models its line ending. The disagreement would move rather than close.

It would make a document's line count depend on characters this product
cannot produce, preserve or convert. `LineEndingPolicy::Rewrite` converts
between LF and CRLF; it has no idea what to do with U+2028, and `LineEnding`
has no variant to describe a document that uses one.

And it would be a decision to treat a bare `\r` as a break in the *editor*
while `bp-files` treats it as data in the *file* — which is the same class of
split as the one being closed, one layer down.

### What this costs, honestly

A document that genuinely uses U+2028 or a bare `\r` as its separator will
show as one long line rather than several. That is a real regression against
ropey's default for those files, and it is accepted: such a file is
unopenable-as-intended in most editors, this product cannot save it back
correctly in any case, and pretending otherwise in the line numbers while the
save path disagrees is worse than being consistently unable to help.

`\r\n` is unaffected. Ropey without `unicode_lines` still ends a line at the
`\n`, and the `\r` sits at the end of that line's content — which is exactly
what `bp_buffer::line_len` and `bp_editor::view::content` already strip.

### `line_count` and `len_lines` must agree, and a test must say so

Closing the crate-level split without closing `bp-buffer`'s internal one
would leave the status bar still reporting two numbers. The two functions
answer the same question and a property test should hold them to it, over
generated text containing every separator in the argument.

## Consequences

- One definition, in the crate that owns the storage, matching the one the
  file layer already documents.
- The `#[ignore]`d test in
  `tests/integration/tests/search_over_buffer.rs` — the last ignored test in
  the tree — runs.
- `bp-ui`'s status bar reports the same line count under both editor views.
- Find-in-files scrolls to the line the caret agrees with, for every document
  this product can save.
- A file separated by U+2028 or bare `\r` opens as one line. Recorded above
  as accepted rather than discovered later.
- **The change breaks nothing, and that is measured rather than hoped.**
  Applied as a probe on 2026-08-20 and reverted: the workspace ran 1,681
  passing and 0 failing, identical to the run before it, and the `#[ignore]`d
  test passed. Not one behaviour anywhere was relying on ropey's Unicode line
  breaking — which is what a default nobody chose usually looks like from the
  inside.
