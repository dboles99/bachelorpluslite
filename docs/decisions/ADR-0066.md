# ADR-0066: Read-Only Is The Save Refusing, And The Type That Claimed Otherwise Never Ran

**Status:** Accepted
**Date:** 2026-08-30
**Closes:** `project/WORK_QUEUE.md`'s R1
**Supersedes:** the read-only half of [ADR-0054](ADR-0054.md)
**Amends:** [ADR-0063](ADR-0063.md)

## Context

`WORK_QUEUE.md` has carried R1 — *"`--readonly`, or rather what it should be
instead"* — since [ADR-0054](ADR-0054.md) declined it as a **flag** and
explicitly did not decline the **capability**. It was sized as a design pass,
and the pass was one question: **are these three the same thing?**

- the huge-document viewer, read-only because a 2 GB file has no rope;
- Security ▸ Lock Document;
- `bp_buffer::Access`, a property on the buffer itself.

**Two of the three no longer exist.** [ADR-0063](ADR-0063.md) removed the
viewer and [ADR-0064](ADR-0064.md) removed Lock Document. So the design pass
had one candidate left, and taking the inventory before the estimate — as
[ADR-0048](ADR-0048.md) recommends and this session has now had cause to
repeat five times — turned that candidate over.

## What the inventory found

**`bp_buffer::Access` has never been set by anything.**

```text
producers of Access, outside bp-buffer's own tests ...... 0
consumers of Access, outside bp-buffer's own tests ...... 0
```

And it was not the reduction that did it. At `f238b67`, the commit before any
of this began, `Access::of` had exactly **one** production call site:
`LargeFile::open`. A huge document got a `HugeView` and **no `Editor`**, so no
rope, so **no `Buffer`** — the `Access` it computed lived on the `LargeFile`
and was read for a status-bar notice.

So `Buffer::access` — the field on the rope, guarding `insert` and `remove` —
**has never once been read as anything but `Editable`, and those guards have
never fired.** The type's own doc comment made the argument for its existence:

> Carried on the buffer rather than checked by every caller because
> "read-only" enforced at the call sites is read-only until somebody adds a
> call site. The rope is the one place every edit passes through.

That argument is correct and was never taken up. Nobody added the call site
that sets it.

## Decision

### 1. `Access` is deleted

The enum, `Buffer::{access, is_read_only, set_access, with_access}`, the
guards in `insert` and `remove`, and their tests.

[ADR-0063](ADR-0063.md) kept it deliberately, "waiting for" this design pass,
and said so — that was the right call on what was known then, and this is the
pass it was waiting for. **The answer is that there was nothing to unify**: a
type with no producer is not one of three implementations of read-only, it is
a claim about the product that nothing keeps.

### 2. Read-only is the save refusing, and the refusal now knows

**This is what the capability always actually was.** Type into a read-only
file and the save fails; there is no other mechanism and, per §1, there never
was.

**That is also the correct behaviour for this product.** Windows Notepad lets
you edit a read-only file and refuses at save. A buffer that went inert at the
first keystroke would be a different and worse editor, and it is not what
ADR-0054 was asking for.

What was wrong is that the refusal *guessed*:

> cannot replace `notes.txt` -- it may be read-only, open in another program,
> or in a directory that no longer exists: Access is denied. (os error 5)

Three candidate causes and a hedge. Honest when the cause is unknown, and
needlessly vague when it is not: **at the moment a replace fails, the file can
be stat'ed.** `SaveError::ReadOnlyFile` now says so and names the way out:

> cannot save `notes.txt` -- the file is marked read-only. Use Save As to
> write a copy somewhere else, or clear the read-only attribute and try again

**Only where the attribute is actually set.** On Unix
`Permissions::readonly()` answers "no write bit for anyone", which is a
different question from "may this process write it" — a file owned by somebody
else with mode 644 answers `false` and still refuses us. That case keeps
`Replace`'s hedge, because there the hedge is true.

The check runs **only on the failure path**, so an ordinary save pays nothing
for it, and it stats the target *then* rather than remembering an answer from
the open — the attribute can be set while a document is open, which is exactly
the case a remembered answer would get wrong.

## Consequences

**The platforms genuinely differ here and the test asserts both**, without a
`cfg`. On Windows, replacing a read-only file fails and the new refusal fires.
On Linux the rename does not open the file at all, so a read-only file in a
writable directory **is replaced successfully** — the save works, and the test
asserts that outcome rather than skipping. *"It succeeded" and "the test did
not run" look the same in a green log.*

**`bp-buffer` is a rope and nothing else now.** After [ADR-0063](ADR-0063.md)
took the large-file engine and this takes `Access`, the crate is 360 lines of
buffer, character indices and line/column maths.

**R1 leaves the queue answered rather than built.** ADR-0054 declined the flag
and left the capability open; the capability turns out to have existed all
along in the only place it could, and the work was making it *say* something.

## The lesson

> **A type with no producer is not an implementation. It is a claim.**

This is the third time in one sequence, and the three are worth reading
together because the shape is identical and the hiding places are not:

- **Four of `Policy`'s seven axes** are computed, stored, and printed by an
  inspector as *the policy in force*, and consulted by nothing
  ([ADR-0059](ADR-0059.md)).
- **`Format::has_data_operations`** answered a question whose only asker was a
  menu that had left ([ADR-0062](ADR-0062.md)).
- **`bp_buffer::Access`** guarded every edit against a condition nothing could
  set.

None of the three would fail a build, a test, or a review of the file it lives
in. All three fall out of one question asked of the whole workspace rather
than of one file: **who produces this, and who reads it?** That is a `grep`,
and it is the same `grep` that would have caught both of this session's own
trap-6 mistakes.
