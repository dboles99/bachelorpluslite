# ADR-0062: The Data Menu Leaves, And `sniff` Loses The Thing That Could Contradict It

**Status:** Accepted
**Date:** 2026-08-29
**Implements:** [ADR-0059](ADR-0059.md) R3
**Supersedes:** [ADR-0023](ADR-0023.md)
**Amends:** [ADR-0008](ADR-0008.md), [ADR-0048](ADR-0048.md)

## Context

[ADR-0059](ADR-0059.md) put `bp-data` third: 2,002 lines, one dependant, and
the eight-row Data menu. Validate, format, minify and convert for JSON, JSON
Lines, TOML, YAML and delimited text. Windows Notepad has none of it.

R2 had already removed the coupling that made this less obvious than it looks:
`apply_transform` routed two paste transformations through
`bp_data::json_format` and `json_minify`, so until
[ADR-0061](ADR-0061.md) the crate had two callers rather than one.

## Decision

**Remove `bp-data`, the Data menu, and everything that existed only to serve
them.**

Deleted: the crate, `bp-ui`'s `state/data.rs`, the Data menu builder, both
action-id blocks (70--79 and 210--211), the dispatch arm, the two
range-dispatch windows, the `Data` menu bar label and popup in `app.slint`,
and the `data-items` property.

Also deleted, and each one is a decision rather than a consequence:

- **`Format::has_data_operations`**, in `bp-formats`. Its only caller outside
  its own tests was the Data menu; a predicate nobody asks is a claim nothing
  keeps.
- **`fuzz/tests/yaml.rs` and `fuzz/corpus/yaml/`.** The harness targeted
  `bp-data`'s YAML entry points and nothing else. The corpus went with it --
  see below, because that one is not obvious.
- **`tests/integration/tests/format_detection_and_parsing.rs`**, in full.
  See "What is genuinely lost".

**`bp-formats` stays**, as ADR-0059 said it would. It identifies a file type,
and two kept things need that: `.ipynb` recognition, which
[ADR-0057](ADR-0057.md) deliberately preserved, and `bp-platform`'s
registration table, which a test holds in agreement with it. It is now a
smaller crate with the same job -- **named here so nobody deletes it later as
vestigial**, which was ADR-0059's specific worry.

## What is genuinely lost, and it is not the menu

**`sniff` no longer has a consumer that can disagree with it.**

`bp_formats::sniff` guesses a document's format from its first kilobyte. It
runs on every file the editor opens. Until this change, whatever it guessed,
`bp-data` then had to parse the document *as that* -- and
`format_detection_and_parsing.rs` asserted the two agreed, across every format
and a proptest over generated documents.

**That test found a real defect** and its comment records it: `sniff` counted
lines beginning with `{` or `[`, called two or more of them JSON Lines, and so
classified a pretty-printed array of objects -- the single most common shape
of JSON anybody has -- as a format its own parser would reject. The fix was
`bp-formats` asking instead whether the first line is a complete value with
something after it.

Every test in that file routes through `bp_data_accepts`. With no parser there
is no question to ask, so the file is deleted rather than hollowed out.

**What this changes about the risk, precisely.** `sniff`'s answer now reaches
a status-bar label and a syntax profile. A wrong answer is cosmetic rather
than a syntax error on a valid file, so the *stakes* fell. But it is also
**unfalsifiable**: nothing in the workspace can now demonstrate that `sniff`
is wrong about a document, because nothing else acts on the classification.

> **Removing a caller does not only remove work. It can remove the only thing
> that could contradict a claim.** The Data menu was the consumer; the
> cross-crate test was the contradiction; deleting the first silently deleted
> the second's subject.

`fuzz/tests/data.rs` is therefore **narrowed rather than deleted**, and its
header says all of the above. It keeps `sniff` and `detect` over the same
corpus, and gains one property that is not survival: **appending text past the
first kilobyte must not change the verdict.** That is the property the status
bar depends on, it is checkable without a parser, and it is the most this can
honestly assert now.

The file keeps its name. `data` names the corpus it reads -- `corpus/data/` is
still JSON, JSON Lines, TOML and delimited text -- rather than the crate it
exercises, and renaming a file needs approval a sweep should not assume.

## Consequences

**ADR-0023 is superseded, and its caps were load-bearing for a reason that has
gone.** That ADR chose `saphyr`, capped YAML nesting at 128 to match
`serde_json`'s limit so both formats refuse at the same depth, and refused
alias bombs before expanding them. The reasoning was good and the
implementation held under every probe. **All of it existed to let this product
parse a YAML file safely, and it no longer parses one.**

The YAML corpus went with it, which is worth stating plainly because it
reverses a decision from earlier the same day. Commit `9e2d0c0` found that
`fuzz/corpus/yaml/` crash-loops any language server that parses workspace
YAML -- `billion-laughs.yaml` is 570 bytes of alias expansion -- and concluded
**the corpus is untouched and the listing is narrowed instead**, because the
corpus was evidence about a parser this product shipped. It is not evidence
about anything now, and a known editor hazard kept for no remaining subject is
not a trade worth making. The workspace excludes that commit added are
harmless and are left alone.

**Three of five fuzz harnesses remain**, down from five before ADR-0057:
`data.rs` (now `sniff`), `files.rs` and `envelope.rs`. The fuzz suite is 26
tests, one `#[ignore]`d for cost.

**The menu bar is eleven menus.** File, Edit, View, Insert, Format, Note,
Organize, Research, Security, Tools, Help.

**Ids 70--79 and 210--211 are free**, along with 300--599 from ADR-0061. Four
range-dispatch windows remain and `no_two_range_dispatch_windows_overlap`
still guards them; as with R2, removing a window is the safe direction, and
the freed blocks should not be reused casually.

**One thing did not need doing, which is worth recording.** `bp-formats`'
`Profile::StructuredData` and `is_data_class` survive untouched: they classify
a format for the status bar and the syntax profile, which is a different
question from "can anything parse this". ADR-0008 drew that distinction and
`has_data_operations` existed *because* of it -- the predicate that goes is
the one that named a capability, and the one that stays names a kind. **The
distinction ADR-0008 made is what let half of this be deleted cleanly.**
