# ADR-0042: Find In A Document Served From Disk Is Resumable, Not Threaded

**Status:** Accepted
**Date:** 2026-08-21

## Context

ADR-0030 shipped the viewer for a document the rope does not hold and named
what it deliberately left out. One of the three is Find:

> **Find, in a document served from disk.** `LargeFile::windows` exists for
> exactly this and `bp-search` decides what a match is, so the pieces are
> there. It is a feature rather than wiring and it is not in this change.

Both halves really do exist, and each was built with the other in mind.
`bp_buffer::stream` produces `StreamWindow`s that "between them cover the
file exactly once, each small enough to hand to a matcher", carries an
overlap so a match straddling a boundary is not lost, and exposes
`is_new_match` whose argument is documented as "in characters, as
`bp_search::Match::range` gives it". `bp_search` owns what a match *is* and
duplicates none of the reading. Neither crate depends on the other.

What has not been decided is the three things in between: **which crate
joins them**, **what happens to the window while two gigabytes are scanned**,
and **what a hit has to be for a viewer with no caret to act on it**.

## Decision

### `bp-search` depends on `bp-buffer`, and not the other way round

The dependency has to go one way or a third place has to own the join.
`bp-search` is the right end, for a reason already written down in the other
crate: `bp_buffer::stream`'s own documentation says "`bp-search` owns what a
match *is* -- and nothing here duplicates a byte of it", and `windows()` says
"`bp-search` decides what a match is; this decides what it gets to look at".
That is a description of a dependency direction; this ADR only declares it.

It also puts the feature beside its sibling. `bp_search::files` already
searches files this product cannot hold whole -- by *skipping* them:
`MAX_FILE_BYTES` is 5 MiB and anything larger is passed over. Searching a
file too large to read at once is the same crate's next sentence, not a new
subject.

Rejected: joining them in `bp-ui`, which is where `bp-secrets` and
`bp-redaction` meet. That precedent is a real one, but it exists because
neither of those crates should know the other -- a scanner that knew about
redaction would be a scanner that could be asked to hold a secret. Nothing
of the kind is true here, and the cost of the shell owning it is that the
dedupe rule, the line arithmetic and the caps would live in the crate with
no way to test them without a window.

### The search is resumable, and the shell drives it. No thread

**A search does a bounded amount of work per call and returns.**
`StreamSearch::advance(windows)` scans at most that many windows and comes
back; the caller decides when to ask again. A scan of 2 GB is a few thousand
of those calls, and between any two of them the window redraws, the user
types, and the search can simply not be asked again.

**That is what makes it interruptible**, and it is the whole reason for the
shape. Cancelling is not a flag another thread has to notice -- it is the
absence of the next call. There is no channel to drain, no handle to join,
no question about what happens to a half-finished scan when the tab closes:
the `StreamSearch` is dropped and the file handle with it.

This was available rather than invented. `WindowReader::next_window` says in
as many words that it exists "so a caller driving this from a background task
can ask for exactly one window per tick without wrapping the iterator".

Rejected: a background thread with a channel and an `AtomicBool`. It buys
throughput this feature does not need -- the budget below already scans
faster than a disk delivers -- and it costs the things this repository has
been most careful about: a second place where the document's state can be
observed mid-change, a cancellation that is a request rather than a fact, and
tests that have to synchronise before they can assert. The one honest
argument for it is that a single `advance` call still blocks the UI for its
duration, and the answer is that the budget is what bounds that duration,
measured in a window at a time rather than a file at a time.

**The budget is windows, not milliseconds.** A time budget makes the amount
of work done depend on the machine, which makes every test of it either
flaky or a tautology. A window is 1 MiB and the count is the caller's.

### A hit is a line and a column in it, because that is what a viewer can act on

`HugeView` scrolls by line and draws by line. It has no caret and no
selection -- both are positions in a rope, and there is no rope -- so a hit
reported as a character offset in the document would be a number nothing
could use, and computing one would need the whole file walked, which is the
cost this viewer exists to avoid.

```rust
pub struct StreamHit {
    pub line: usize,                    // 0-based, as `DisplayLine::line`
    pub column: Option<Range<usize>>,   // chars within that line
}
```

**The `Option` is not defensive.** A window can begin in the middle of a line
-- only when a single line is longer than the window, which is a minified
bundle or a one-line log dump, but those are exactly the files that reach
this viewer. When it does, the line's start was never in the window, so the
column cannot be computed from it, and the two dishonest options are to guess
one or to drop the hit. It reports the line it can prove and says the column
is unknown; the shell scrolls there and highlights nothing.

**No preview string.** `FileHit` carries one because a cross-file result list
has nothing else to show. Here the viewer re-reads the line from disk to draw
it anyway, so a preview would be a second copy of a line the caller can
already get correctly -- and a copy that is silently truncated whenever the
line runs past the end of the window that found the match.

### Capped at `MAX_HITS`, and the truncation is reported

The same 500 as `search_dir`, and the same contract: "500 results" and "at
least 500 results" mean different things to someone deciding whether to
refine their query. A scan that reaches the cap stops there rather than
reading the rest of the file to build a list nobody scrolls through.

### What this does not do

- **No replace.** The document is `Access::ReadOnlyBySize`. `ReplacePlan`
  builds a new `String` from the old one, which for these documents is the
  one thing ADR-0027 exists to prevent.
- **No total match count before the scan finishes.** `find_all` can say
  "1 of 27" immediately because it has seen the whole document. This cannot,
  and saying so is the honest readout: a count that grows is a count that was
  never a total.
- **A match longer than the overlap can still be lost.** 4 KiB, from
  `DEFAULT_OVERLAP_BYTES`, and stated rather than hidden -- `bp-buffer`
  exposes `windows_with` for a caller that needs more. Nothing typed into a
  find box comes near it; a regex written to match a whole paragraph could.

## Consequences

- `bp-search` gains its first path dependency. Its other half stays pure:
  `find_all`, `count` and the replace planner still take a `&str` and know
  nothing about files.
- `Query::compile` is called once per search rather than once per window.
  Over a 2 GB file that is two thousand regex compilations avoided, and it
  also moves a bad pattern's error to `start` -- which is where a find box
  wants it, before any of the file has been read.
- The shell acquires a piece of state a document can be in that it did not
  have: *searching*. It has to be started, driven, reported, and abandoned
  when the query changes, the tab changes or the bar closes.
- `SearchError` is untouched. Streaming has its own error type because
  `LargeFileError` carries an `std::io::Error`, and `SearchError` derives
  `PartialEq` -- widening it would cost every existing caller's ability to
  compare one.

## Built, and watched working rather than asserted

Shipped 2026-08-21, engine and shell in two commits. Driven against a
**213.5 MiB** log of 4.8 million lines, in the release build:

| Asked | What happened |
| --- | --- |
| `ZEBRA`, which occurs once, in the last line of the file | `searching 86%` while it ran, then `1 of 1`, and the viewport moved from line 1 to **line 4,800,001** with `ZEBRA` highlighted on exactly its own characters |
| `column`, which occurs on every line | `1 of 500+` almost at once -- the cap, reported as a cap |
| Enter, three times | `4 of 500+`, the highlight following the step |

The mid-scan readout is the part worth having a screenshot of: **`searching
86%`, with no total**, while the window was still drawing. That is the
resumable design working -- the scan had read 180 MiB in ticks small enough
that the rest of the shell never noticed.

### It was unreachable, and finding out cost a defect fix

**Ctrl+F is the only route to Find in a document served from disk** -- there
is no Find menu row -- and in a huge document it did nothing at all. Nor did
Ctrl+S, Ctrl+O, Ctrl+N, or any other shortcut.

`apply_editor_command` sends every key in a viewer to `scroll_for_command`,
which returned `true` -- "handled" -- for everything it was given, including
the `Command::Ignore` that `bp_editor::keys::command_for` produces for
exactly the keys it says "belong to the window". `EditorSurface`'s
`FocusScope` accepts whatever that reports as handled, and an accepted key
never bubbles to the `KeyBinding` that wanted it. So the shell's entire
keyboard was dead in any document past `HUGE_FILE_BYTES`, and had been since
ADR-0030 shipped.

Fixed with the feature, because a capability reachable by nothing is not
shipped: `Command::Ignore` now returns `false` from the viewer's path too.
The swallowing below it stays, and is a different statement -- an *editing*
command has no meaning in a document with no caret, and a Delete that bubbled
to the window would be worse than one that did nothing.
