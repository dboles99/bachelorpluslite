# ADR-0051: The Run Menu Denied There Was Anything To Run While Offering To Run It

**Status:** Accepted
**Date:** 2026-08-22

## Context

`project/NEXT_SESSION.md` §3b lists what `scripts/Drive-Window.ps1` had never
been pointed at: a document taller than the window, and Run ▸ Run Document on
a real `.py`. Both are things a script *can* do — they open no `rfd` modal —
and both had been waiting on the half of the manual pass that needs a person.

Pointing it at them took an hour and found four things. Two are in the
application, two are in the tooling that was supposed to find them, and the
pattern across all four is the same one ADR-0049 recorded and did not finish
learning: **a claim about verification is not a property of the verifier.**

## What was confirmed working, because that is a result too

Recorded so the next session does not re-check them:

- **Go to Line, in a 601-line document.** Ctrl+G, `555`, Enter: it scrolled,
  landed, and highlighted the target line. The fixtures that had been used
  before all fitted on one screen, which cannot test anything about scrolling.
- **Find, in the same document.** The query went into the Find box and not
  into the document — the defect a previous pass found — the view scrolled to
  the only match near the bottom, the match was highlighted, the count read
  "1 of 1", and the document was still 601 lines and still unmodified.
- **Run ▸ Run Document on a real `.py`.** A fresh subprocess ran, and the panel
  showed `runme.py — finished in 0.2s` over the script's actual output,
  including an arithmetic result that was correct. It is a panel, not a
  dialog, so a script can read it.

## Decision

### 1. The Run menu's readout must not make a claim about a row it does not own

Opening Run on a `.py` produced this, and the contradiction is three rows tall:

```text
Nothing to run: open an .ipynb, or …     (greyed)
Stop                                      (greyed)
Run Document                              (enabled -- and it works)
Interpreters
```

The first row heads the *cell list*; Run Document is the *whole file*. They
answer different questions, and nothing made the first one say so. As written
it is a flat denial that anything runs, sitting directly above a row that runs
the file correctly.

**A readout that contradicts a working row three lines below it is worse than
no readout**, because a user believes it and stops looking. `run()` already
receives `document_runnable`, so the information needed to tell the truth was
in scope the whole time and unused.

Two readouts now, both true and both short:

| State | Row |
| --- | --- |
| Not a notebook, whole file runs | `No cells here: use Run Document` |
| Not a notebook, nothing runs | `Nothing to run: try an .ipynb` |

`the_run_menu_never_says_nothing_runs_while_offering_to_run_the_document`
asserts the pairing rather than the wording — it checks that no row starts
"Nothing to run" in a state where Run Document is offered and enabled, so a
future rewording cannot reintroduce the contradiction.

### 2. Three Run-menu labels were over a budget that already existed

The old label is **52 characters**. `LABEL_BUDGET` is 42, and
`no_row_label_is_too_long_for_the_popup_to_show` has enforced it since
ADR-0048. Two more were worse: the `NoKnownLanguage` arms ran to around 70,
and both are *reasons* — the text ADR-0049 identified as the worst thing on
screen to lose, because explaining is its whole job.

The window confirmed it: `Nothing to run: open an .ipynb, or …`. Eliding was
working exactly as ADR-0049 built it to. **What ADR-0049 got wrong was the
sentence after the fix** — "the reasons are short enough not to need it" — a
claim about three labels that had never been measured.

All three are shortened to fit. The hints go; the reasons stay. The popup was
throwing the hints away already, and silently.

### 3. `every_menu()` never contained the Run menu

This is the finding that explains the other two, and it is worth reading its
own doc comment first:

> One list so a menu added later cannot quietly escape the check below -- the
> failure mode of a hand-written sweep is the menu nobody added to it.

**The comment named the failure mode and did not prevent it.** The Run menu
was absent from that list from the day it was written, so neither the readout
check nor `LABEL_BUDGET` had ever seen it — which is exactly how a menu came
to carry a 52-character readout and two around 70 while a test asserting 42
passed on every run.

It is the one menu built from the document rather than written down, which is
both why it was easy to forget and why it most needed the sweep. It now
appears **six times**, once per state worth checking: the two `NotANotebook`
branches, unreadable, no cells, and both `NoKnownLanguage` shapes. A menu
whose rows depend on a value is not covered by building it one way — Tier 1
learned that once already, in `WORK_QUEUE.md`'s "a menu builder whose rows
depend on a value must be handed it".

The guard was checked by putting the old label back: it fails with
`Run (inert) ▸ "Nothing to run: open an .ipynb, or a .md with fences" is 52
characters and will be elided by the popup`. A guard nobody has seen fire is
indistinguishable from one that cannot.

### 4. `Drive-Window.ps1` photographed the wrong window again

The first capture of the session came back **1x1** — the precise failure
ADR-0049 says it was written to prevent, on the first run after it was
written.

ADR-0049 got the diagnosis right and the fix half right. It knew
`MainWindowHandle` was untrustworthy and added an enumeration that takes the
visible top-level window of class `Window Class` with a title. But it still
**waited** on `MainWindowHandle -eq 0` — and that condition is satisfied while
the handle still names the 0x0 `Winit Thread Event Target` and the real
window has no title yet. The enumeration then found nothing titled, fell back
to `MainWindowHandle`, and photographed exactly the window the enumeration
existed to avoid.

**The wait condition and the selection rule have to be the same question.** A
window is usable when it is winit's, visible, titled, and has a client area
with area in it; anything else is a window that is not ready, whatever any
handle says. The poll now asks that question to a deadline, and there is **no
fallback**: a capture of the wrong window is worse than no capture, because it
reads as "the row did nothing", which is the one conclusion a capture must
never invite by accident.

### 5. `-Keys` takes a list, because a bar cannot be driven by one send

`prompts/rosettas/R011` rule 9 says a bar takes the caret a tick after the row
that opened it. `SendKeys` waits for nothing, so `-Keys "^g555{ENTER}"` types
the line number into the document — the exact defect a previous manual pass
found in Find, arrived at from the other direction.

`-Keys` now takes a list and sends each element with its own settle and
capture, the shape `-Click` already had: `-Keys "^g","555{ENTER}"`.

While correcting its documentation: **`-Click`'s said "may be given more than
once"**, which PowerShell refuses outright — it needs comma-separated array
syntax. A usage example nobody had run.

## Consequences

- Three of the four defects were in the record's *claims about verification*
  rather than in the application: "the reasons are short enough", "the window
  is found correctly", "one list so no menu escapes". Each was written by
  somebody who had just fixed the underlying thing, and each was true of the
  fix and not of everything the fix claimed to cover.
- **The Run menu's remaining variable label is `Unreadable(reason)`**, whose
  length depends on a parse error this crate does not author. The sweep
  covers it with a representative reason and cannot bound it in general.
- `project/NEXT_SESSION.md` §3b loses three of its four rows. What is left is
  the one that genuinely needs a person: Notebook ▸ Export as .ipynb opens an
  `rfd` save dialog, which no script gets past.

## The lesson

> **A guard's own comment describing its failure mode is not a defence against
> it.** `every_menu()` said in as many words that the risk was a menu nobody
> added, and the menu nobody added was already missing when the sentence was
> written. The check that would have helped is not a better comment: it is
> asking, once, whether the list is complete — and the cheapest version of
> that question is putting a known-bad value in and watching the guard fire.
