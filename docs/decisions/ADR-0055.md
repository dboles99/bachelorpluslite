# ADR-0055: Signing Is Deferred, And Everything Around It Is Built Anyway

**Status:** Accepted
**Date:** 2026-08-23

## Context

D15, opened by [ADR-0054](ADR-0054.md) when phase 20 started: does this
product buy a code-signing certificate, ship unsigned, or defer?

The question is real and it is not a technical one. On Windows, an unsigned
executable downloaded from the internet meets SmartScreen, which tells the
user the publisher is unknown and offers "Don't run" as the default button.
The three ways out cost differently:

| | What it gets | What it costs |
| --- | --- | --- |
| **OV certificate** | A named publisher; SmartScreen reputation accrues over downloads | A few hundred a year, plus an identity check |
| **EV certificate** | SmartScreen reputation *immediately* | More, and a hardware token that has to be present to sign |

> **Amended 2026-09-25 ([ADR-0086](ADR-0086.md)).** The EV row was false when
> this was written: Microsoft removed the EV bypass in 2024, and EV-signed
> files now build reputation exactly as OV ones do. The deferral stands; the
> route to 1.0 is SignPath Foundation or the Store, and EV is off the table.
| **Self-signed** | **Nothing.** | It is worse than unsigned: the user must install a certificate they have no reason to trust, which teaches exactly the habit that makes signing worth having |

Linux is unaffected. A detached signature and a published checksum need no
authority at all -- they answer "is this the file the author published?",
which is a different question from "who is the author?", and it is the one an
individual can actually answer.

## Decision

**Defer.** Answered by Daniel on 2026-08-23.

Nothing about a certificate is bought, and nothing about the release is built
in a way that assumes one will not be. Concretely:

### What gets built now

- **The archive**, produced by a script, for both targets.
- **A SHA-256 for each archive**, published beside it. This is the whole of
  what an individual publisher can honestly offer on Windows today, and it is
  not nothing: it answers tampering-in-transit, which is the threat a
  certificate answers *worst*.
- **A signing step that is one command away.** The staging directory, the
  archive name and the checksum file are all produced before any signature
  would be applied, so adding `signtool sign` later touches one function and
  changes no layout.

### What is deliberately not claimed

**The release will say it is unsigned, in the same words every time.** A
release that stays quiet about it is asking the user to discover the
SmartScreen warning themselves, and the moment they do, the honest thing
would have been cheaper.

### Self-signing is refused, not deferred

This is the part worth writing down, because it looks like the cheap option
and is the expensive one. A self-signed Authenticode certificate does not
satisfy SmartScreen; it satisfies it only after the user installs the
certificate into their trusted root store. **Teaching a user to install a
root certificate in order to run a text editor is a worse outcome than the
warning**, and it is not undone by uninstalling the editor.

`bp-crypto::sign` and `bp-integrity` can produce an Ed25519 detached
signature over the archive, and that is genuinely useful **on Linux** and as
a trust-on-first-use record anywhere. It is not Authenticode and this ADR does
not let it be described as though it were.

## Consequences

- **`WORK_QUEUE.md`'s P1 is unblocked and unchanged.** That was the point of
  the default: the artefact work never depended on the answer, only the
  sentence describing the result did.
- **Re-ask when either of two things changes**: this product acquires a legal
  entity that can hold an OV certificate, or somebody is about to hand the
  binary to a person who is not the author. The second is the real trigger and
  it has not happened yet.
- **Phase 20 can complete without it.** "Packaging, signing, release and
  upgrade testing" has four nouns and only one of them is blocked; treating
  the phase as blocked because a quarter of it is would be the estimate
  measuring the question again ([ADR-0046](ADR-0046.md)).

## The lesson

> **A deferred decision and a blocked one look identical until you ask what
> actually stops.** D15 read like a gate on phase 20 and gated one sentence
> in a README. The test that separates them is the same one trap 6 installs:
> name the thing that cannot proceed. If nothing can be named, the answer is
> "build it and leave the step", and the question was about *describing* the
> result rather than producing it.
