# ADR-0025: The Notebook Cell Model and `.ipynb`

**Status:** Accepted
**Date:** 2026-08-19

## Context

specs.md section 12 asks for two separable things — a notebook document and a
way to run it — and names eight cell kinds *and* mixed-language notebooks.
`bp-notebook` is only the first half: no interpreter, no process, no channel,
no thread. That split is not tidiness. It is what lets a notebook be opened,
edited, exported and tested on a machine with no Python, no kernel and no
network.

Interchange is where the model stops lining up with the world. Jupyter has
three cell types — `code`, `markdown`, `raw` — and states the language once
for the whole file, in `metadata.kernelspec` and `metadata.language_info`.
Eight kinds and per-cell languages do not fit into that, and no amount of
cleverness makes them.

The security rule cuts across both halves. specs.md section 15: **never
auto-run an opened or pasted notebook or cell.** A crate that cannot run
anything satisfies that by accident, and an accident is not a guarantee — the
crate that *can* run things will take its instructions from here.

## Decision

### `cell_type` carries what it can, `metadata.bachelorpad` carries the rest

Three ways out were available. Encoding the language in a `%%` cell magic
would alter the user's source, which is the one thing an interchange format
must never do. One file per language stops being interchange. What is done is
the third:

| our kind | `cell_type` | `metadata.bachelorpad.kind` |
|---|---|---|
| Markdown | `markdown` | `markdown` |
| plain text | `raw` | `plain_text` |
| Raw | `raw` | `raw` |
| Python, Rust, PowerShell, SQL, Shell | `code` | the language |

Unknown cell metadata is *required* to survive a round trip by the nbformat
schema, so this is the escape hatch the format itself provides rather than a
private extension bolted on. A notebook we wrote opens in Jupyter as an
ordinary notebook; a notebook Jupyter wrote opens here with its languages
read from, in order: our key, `metadata.vscode.languageId`, then the
notebook's own kernelspec.

**When the two disagree, `cell_type` wins**, on the grounds that it is what
the other tool last acted on. The import says so with
`ImportWarning::StaleKindMetadata` rather than resolving it silently.

When even the fallbacks fail — a `code` cell in a language we cannot name —
the cell becomes `Raw`, with `ImportWarning::UnknownCodeLanguage`. Raw and
not plain text, because Raw is the kind carried verbatim and never run, which
is the right treatment for code we cannot identify.

nbformat 4.5 is written: version 4 has been current since 2015 and is what
every tool in use emits, and 4.5 is the minor version that gives cells a
stable `id`, which is what lets our identities survive a round trip.

### What the format cannot carry is enumerated, not discovered

A silent loss is the failure mode of every interchange format, so the list is
written down and each item produces an `ImportWarning` where there is a
specific cell to blame:

* **our eight kinds, if the metadata is stripped.** A notebook edited by a
  tool that discards unknown cell metadata returns as Markdown and Raw.
  Nothing can be done from this side, and it is why the kind is cross-checked
  against `cell_type` at all;
* **outputs on a cell that is not code.** Jupyter has nowhere to put them.
  `Cell::set_outputs` refuses to create that state, so it can only arrive
  from a foreign file, and it is dropped;
* **`Output::Table` and `Output::File`.** No native representation exists, so
  both travel as custom vendor MIME bundles inside a `display_data` output.
  Jupyter preserves them and cannot render them; we read them back exactly;
* **execution counts and every other piece of execution state.** Discarded on
  import, always, with `ImportWarning::DiscardedExecutionState` when there
  was any. Not tidiness — see below;
* **`attachments` on Markdown cells, output-level `metadata`, and outputs
  whose type or MIME bundle we do not model.** Dropped, each with a warning;
* **the `bachelorpad` metadata key** at notebook and cell level. It is ours;
  export overwrites it and import removes it.

Everything else round-trips exactly, and that is a property test over
arbitrary notebooks rather than a handful of examples: export then import
returns an equal `Notebook` and an empty warning list.

Only failures that stop us producing *any* notebook are errors. Everything
survivable is a warning on a notebook the user still gets to see, because a
notebook with one unreadable output is far more useful than a refusal.

### We never synthesise a kernelspec

A kernelspec we did not write is preserved verbatim in `Notebook::metadata`
and written straight back out. One is never invented. A mixed-language
notebook has no single kernel, and claiming one we cannot honour would send
the user to a kernel that fails on two thirds of their cells.

### "Never auto-run" lives in the type system

The rule is put where the compiler keeps it, in three places:

1. `import_ipynb` returns an `Import` — a report — not a `Notebook`. Getting
   the notebook out is a second call the caller has to write.
2. `RunRequest` is the only description of work this crate produces, its
   fields are private, and the only way to obtain one is a `request_run*`
   method on a notebook.
3. Every one of those methods takes a `UserGesture` **by value**, and
   `UserGesture` is not `Deserialize`, not `Default` and not `Clone`. It has
   exactly one constructor, `from_user_command`. No parsed file can produce
   one at any depth, no `..Default::default()` can conjure one, and one
   gesture cannot be duplicated into a second run. **An import path that
   tried to start a run would not compile.**

`Cell` has no `auto_run`, no `run_on_open` and no execution state at all. The
absence of those fields is the design, and it is why a Jupyter
`execution_count` is discarded rather than kept "for information".

What this does *not* claim: it cannot stop a caller from calling
`from_user_command` in the wrong place. Nothing in a type system can. What it
does is make that call the single, greppable, obviously-named line where
consent is asserted, instead of a `run: bool` somewhere in a struct that a
`serde` derive will happily fill in from a downloaded file. Both halves of
the claim are pinned by `compile_fail` doctests, alongside a passing one that
proves the failures are failing for the stated reason rather than because
`serde` was out of scope.

### Split and merge are exact inverses, and that shapes both

A stronger promise than either operation needs alone, taken deliberately
because it is the property that catches errors a pair of hand-written
examples never would. It forces three things:

* **merge joins with no separator.** Jupyter inserts a newline; doing so
  would make every split-merge pair grow the document by a byte. A caller
  wanting a blank line adds it before merging, where the user can see it.
* **split keeps the outputs on the upper half** rather than discarding both,
  which also means a user who splits a cell after a long run does not lose
  the result of it.
* **merge refuses two cells of different kinds.** Adopting the first cell's
  language would file a Shell cell's text as Python source, and the next "run
  cell" would hand exactly that to a Python interpreter. There is no safe
  default, so there is no default.

Splitting at `0` or at `source.len()` is allowed and yields an empty half.
That is a strange cell to have, but it is what the user asked for, and
refusing would mean a caret at the top of a cell has no split.

## Consequences

- The `CellId` allocator is derived — `max(existing) + 1` — not stored. A
  stored counter would be extra state every saved file has to carry, and
  would make two notebooks with identical contents unequal, which is what
  would reduce the round-trip property from equality to a vaguer
  "equivalent". The price, stated plainly: after a merge removes the
  highest-numbered cell that number is handed out again, so a `CellId` held
  across an edit is stale rather than merely dead. Every operation takes the
  id by value and re-resolves it, and nothing caches an index.
- A notebook edited by a tool that strips unknown cell metadata comes back
  degraded and there is no recovery path. The warning is the whole mitigation.
- `bp-execution` inherits the rule rather than re-deciding it: a `RunRequest`
  is inert data with no handle, no callback and no environment, so "prepare a
  run" stays separable from "run", and a caller may discard one.
- The crate is pure — no clock, no filesystem, no configuration — so every
  behaviour is a function of its arguments and testable as one.
- The raw JSON view shows the `.ipynb` form, because that is the thing a user
  might want to hand-edit, and it round-trips through the same code path as
  import and export rather than a second one.
