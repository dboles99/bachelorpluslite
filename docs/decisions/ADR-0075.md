# ADR-0075: One Documentation Source, Four Destinations, And Nothing Retyped

**Status:** Accepted
**Date:** 2026-09-10
**Depends on:** [ADR-0047](ADR-0047.md), [ADR-0057](ADR-0057.md), [ADR-0071](ADR-0071.md)

## Context

A public release needs documentation a stranger can read: how to install it,
how to use it, what the keys do, what differs between Windows and Linux, and
how to build it if they want to contribute. This repository has a great deal
of writing and almost none of it is that. `README.md`, `specs.md`,
`ROADMAP.md`, `DECISIONS.md`, seventy-four ADRs and `docs/architecture/` are
written for somebody working *on* the product, not somebody using it.

Four destinations were asked for: a documentation website, in-app help, a
GitHub Wiki, and exportable manuals.

**Four destinations is the entire risk.** `CLAUDE.md` opens its table with
*one home per kind of fact*, and the reason is stated in the next sentence: a
fact repeated in four files is a fact that will be updated in three. Four
copies of *how Find and Replace works* is the exact failure that table exists
to prevent, and building the pipeline the obvious way would install it
deliberately.

## Decision

**One Markdown source under `docs/`, and every other destination is
generated.** Nothing is hand-maintained in `app-help/`, `wiki/` or
`docs/generated/`; a `-Check` mode and a gate stage make staleness fail rather
than accumulate, the same mechanism `THIRD-PARTY-NOTICES.md` got in
[ADR-0071](ADR-0071.md).

```
docs/user/  docs/tutorials/  docs/reference/  docs/developer/
                          |
        +-----------------+-----------------+------------------+
        |                 |                 |                  |
  docs/generated/     app-help/           wiki/          site/ (ADR-0076)
   one-file manual   in-app help       GitHub Wiki       the website
```

### And the source is not the whole story either

This is the half that makes the design fit the repository rather than fight
it. **Several of the facts a user manual needs already have a home**, and that
home is not prose:

| Fact | Its one home | What `docs/` does |
| --- | --- | --- |
| Every flag the binary accepts | `bp_config::cli::FLAGS` -- *the list is the documentation*, in its own words | Generated from `--help` |
| Every keyboard shortcut | `dispatch.rs::SHORTCUTS` | Generated from the constant |
| Every menu row and its state | `docs/product/MENU_MAP.md` | Generated from that table |
| Crates, modules, sizes, seams | `docs/architecture/ARCHITECTURE.md` | Linked, never restated |
| Every decision, and every lesson | `DECISIONS.md` and the ADRs | Linked, never restated |

So `docs/` is the source for **user-facing prose that has no other home** --
what a tab is for, why a filename has a date in it, what a privacy profile
governs -- and a generator for everything that does. A shortcut table typed
into a user guide would be a sixth spelling of a fact the product already
holds, and it would be wrong within a session.

### In-app help does not open a browser

The obvious in-app help is a menu row that opens the documentation website.
This product will not do that, and the reason is already written down:
`bp-platform` executes nothing, and says why in its own header -- *a library
that spawns processes on the user's behalf is a library that can be talked
into spawning a different one*. [ADR-0057](ADR-0057.md) removed the last thing
in this product that ran anything, and a Help menu is a poor reason to put one
back.

**So `app-help/` ships as Markdown beside the executable, and Help opens it as
a document in a new tab.** The product is a text editor; its help is text; it
already knows how to show text. No browser, no process, no network, and the
help works on a machine with none of those.

It is also the honest test of the product: help that is unpleasant to read in
this editor is a fact about the editor worth knowing.

## What is built

| Script | Produces | Checked by |
| --- | --- | --- |
| `scripts/Build-Docs.ps1` | `docs/generated/` -- one-file manual, and the HTML the website and any PDF export are made from | `-Check`, gate stage `docs` |
| `scripts/Build-AppHelp.ps1` | `app-help/` -- the in-app pages, and the index Help reads | `-Check`, same stage |
| `scripts/Sync-GitHubWiki.ps1` | `wiki/`, and pushes it to the repository wiki | `-Check` for drift; the push is explicit |

`.github/workflows/docs.yml` runs the same `-Check` on every change under
`docs/`, so a pull request that edits a page and forgets to regenerate is
caught by the gate rather than by a reader.

## Consequences

**`app-help/` and `wiki/` are committed generated artefacts**, which is
normally a smell. They are committed for one reason each: `app-help/` is
shipped in the release archives, so it must exist without a build step; and
`wiki/` is what the wiki push mirrors, so a diff of it is the review of what
strangers will read. The staleness check is what makes committing them safe.

**`README.md` keeps its job and loses some text.** It owns *what works today,
for a reader who has never seen the project* and now links to the guide
instead of gesturing at features.

**`specs.md` is not the user manual and does not become one.** It is a
specification, written before most of the product existed, and several of its
sections describe things five ADRs have since removed.

**The archives grow by the size of `app-help/`** -- some tens of kilobytes
against a 21 MB binary.

## The lesson

> **The way to keep four copies in step is to have one copy and three
> renderers, and the interesting half is that the source is not always
> Markdown.**

The first design of this had a `docs/reference/shortcuts.md` in it, and it was
wrong in the way this repository is most practised at spotting: a table of
keyboard shortcuts typed out beside a constant that already holds them, with
nothing to make the two agree. It would have been correct on the day it was
written.

**The question that catches it is the one trap 3 always asks, pointed at
documentation: if this page and the code disagreed, what would fail?** For a
page describing what a tab is for -- nothing, and prose is the right home. For
a page listing the flags -- nothing either, which is precisely why that page
has to be generated instead.
