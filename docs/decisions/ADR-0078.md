# ADR-0078: Three Unmaintained Dependencies Are Accepted By Name, Never As A Category

**Status:** Accepted
**Date:** 2026-09-10
**Depends on:** [ADR-0071](ADR-0071.md), [ADR-0073](ADR-0073.md)

## Context

[ADR-0073](ADR-0073.md) restored hosted CI, and argued for it on three
grounds. The third was that CI can run the RustSec advisory database, which
the local gate is not allowed to assume a network for:

> a gate that fails on a train is a gate people learn to skip

**The first hosted run failed on that stage**, on three advisories the local
gate had never been in a position to see. The argument was made on a
Wednesday and demonstrated on the same day, which is worth recording because
it is rarer than it sounds.

| Advisory | Crate | Reaches us through |
| --- | --- | --- |
| [RUSTSEC-2024-0436](https://rustsec.org/advisories/RUSTSEC-2024-0436) | `paste` | `i-slint-compiler` → `image` → `exr` → `pulp` |
| [RUSTSEC-2026-0206](https://rustsec.org/advisories/RUSTSEC-2026-0206) | `rustybuzz` | `i-slint-core` → `resvg` → `usvg` |
| [RUSTSEC-2026-0192](https://rustsec.org/advisories/RUSTSEC-2026-0192) | `ttf-parser` | the same path, plus font loading |

## What these advisories are, and are not

**All three are `unmaintained`. None is a `vulnerability`.** There is no known
defect in any of them. Each is a crate whose author has said, in as many
words, that they will not be maintaining it further.

That distinction is the whole of this decision, and it is easy to lose:
`cargo deny` reports both as `error`, in the same red, with the same shape.
Treating them identically would mean either shipping with a known
vulnerability one day, or refusing to ship over a crate that works perfectly
and simply has nobody watching it.

**All three arrive through Slint**, which draws every glyph in this product.
There is no version of "upgrade away from them" that does not mean leaving the
toolkit. This project cannot fix these and neither can it route around them.

## Decision

**The three are ignored by id, with a reason each, in `deny.toml`. The
`unmaintained` category stays an error.**

```toml
ignore = [
    { id = "RUSTSEC-2024-0436", reason = "..." },
    { id = "RUSTSEC-2026-0206", reason = "..." },
    { id = "RUSTSEC-2026-0192", reason = "..." },
]
```

The alternative — `unmaintained = "warn"` — is one line shorter and much
worse. **It would silence the next one too**, and the next one is by
definition the one nobody has looked at yet. A blanket setting turns a
decision made once about three known crates into a standing policy about
crates that do not exist yet.

Enumerating the exception keeps the category enforcing. A fourth unmaintained
dependency still fails the build, which is the behaviour worth having.

### `ttf-parser` is the one to watch, and the file says so

Two of the three have no runtime surface worth worrying about: `paste` is a
proc-macro that pastes identifiers together at compile time, and `rustybuzz`
shapes text in SVG rendering.

**`ttf-parser` parses fonts, and a font is untrusted input.** It is exactly
the shape of dependency where "unmaintained" becomes serious the moment
somebody looks. That is written into `deny.toml` beside its entry rather than
left for a reader to work out, because the three entries otherwise look
interchangeable and they are not.

## Consequences

**The re-ask condition is a command**, per ADR-0073's own lesson about ADRs
resting on external facts:

```sh
cargo deny check advisories
```

Any of these three turning into a `vulnerability` advisory, or Slint moving
off them, changes the answer. Nothing else does.

**CI runs `cargo deny check` whole and the gate runs `check licenses`.** That
split stands, and this is the evidence for it: the licence half needs no
network and catches a licence change immediately; the advisory half needs a
network and catches the world changing underneath a dependency graph that has
not moved.

## The lesson

> **Two failures in the same red are not the same failure.**

`unmaintained` and `vulnerability` arrive from the same tool, in the same
format, with the same exit code. The temptation is to handle them the same
way, and both symmetric answers are wrong: treat them all as blocking and you
cannot ship over a crate with nobody watching it; treat them all as noise and
you ship over a real one.

The check is to ask **what would have to be true for this to hurt somebody**,
and to answer it per item rather than per category. Two of these three cannot
hurt anybody. The third parses untrusted input, and the file says so.

**And the smaller, more repeatable lesson:** when a tool offers to silence a
category, prefer enumerating the instances. The category setting is a
statement about things you have not seen yet, and you have no grounds for one.
