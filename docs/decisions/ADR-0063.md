# ADR-0063: Huge-File Mode Leaves, And D11 Stops Being A Question

**Status:** Accepted
**Date:** 2026-08-30
**Implements:** [ADR-0059](ADR-0059.md) R4
**Supersedes:** [ADR-0027](ADR-0027.md), [ADR-0030](ADR-0030.md), [ADR-0042](ADR-0042.md)
**Amends:** [ADR-0018](ADR-0018.md), [ADR-0017](ADR-0017.md)

## Context

[ADR-0059](ADR-0059.md) put huge-file mode fourth and called it **the first
removal with no directory to delete** -- a capability spread across three
crates and the shell rather than one that can be `git rm`'d. That was the
reason to take it before R5: the sweep technique had only ever been tested on
things with their own `Cargo.toml`.

What it was: a document past `HUGE_FILE_BYTES` never reached the rope. It got
a `HugeView` and no `Editor`, was served from disk a window at a time, was
read-only, drew in the custom surface whichever flag the build was started
with, and was searched by a resumable scan rather than by asking a rope that
did not exist. Measured at 213.5 MiB and at 2 GB; a 192 MiB log cost 0.8 MiB
more than a small note.

**It worked, and it was the most technically interesting thing in the
product.** Windows Notepad opens a large file by loading it.

## Decision

**Remove huge-file mode entirely.**

Deleted: `bp-buffer`'s `large.rs`, `line_index.rs` and `stream.rs` (2,391 of
its 2,854 lines) and `benches/large_file.rs`; `bp-search`'s `stream.rs` and
the `StreamSearch` API; `bp-ui`'s `viewer.rs`, the `viewers` map,
`open_viewer`, `is_viewer`, `active_viewer_mut`, `active_is_viewer`,
`refuse_on_viewer`, `is_too_large_to_load`, `size_label`, `drawn_rows`,
`draw_viewer`, `viewer_rows`, `scroll_for_command`, the whole scan half of
`state/find.rs`, the scan timer and its two Slint properties, and the size
class from Tools ▸ File Analysis.

**`bp-buffer` keeps its rope and `bp-search` keeps find and replace.** Neither
crate goes; both lose the half that existed for a document nothing holds.

## Three things survive that look like they should not

### 1. `Access` stays, minus one variant

`Access` lived in `large.rs` and is *about* read-only rather than about size.
It had three variants -- `Editable`, `ReadOnlyFile`, `ReadOnlyBySize` -- and
its doc comment argued that collapsing them to a `bool` would lose the
difference a user needs: a file read-only on disk becomes editable when
permissions change, and Save As is the way out; a document read-only because
it is 2 GB stays that way however permissions change.

**`ReadOnlyBySize` was the variant that made it an enum, and it is gone.** One
non-editable reason remains, so `bool` would now fit.

**It is kept as an enum anyway**, and that is a decision rather than an
oversight. `project/WORK_QUEUE.md`'s R1 is a design pass asking whether the
huge-document viewer, Security ▸ Lock Document and a read-only property are
the same thing. Two of those three still exist. Collapsing to a `bool` today
would have to be undone to answer that question, and the enum costs nothing
while it waits.

The test `a_read_only_buffer_refuses_every_edit_whatever_the_reason` is
likewise kept as a loop over one element, with a clippy allow and the reason
on it. **Its subject was never the count**: it is that a reason which only
changes the *message* must never quietly become one that changes whether the
edit lands.

### 2. `uses_custom_surface` keeps its name and loses its second term

It was `self.editor_view || self.active_is_viewer()`. It is now
`self.editor_view`.

### 3. The test that asserted the *other* branch

`an_ordinary_document_still_follows_the_flag` existed because ADR-0030 made
`uses_custom_surface` a two-branch function, and something had to hold the
branch ADR-0030 did *not* change. With one branch left it is renamed
`every_document_follows_the_flag` and is **worth more, not less**: it is now
the whole of that function, and a flag that started claiming every document
would retire `TextInput` by accident -- and with it input-method composition,
which is the only reason the fork exists.

## Consequences

**D11 stops being a question, and the way it stops is the interesting part.**
[ADR-0030](ADR-0030.md) answered *"may a huge document be viewable only under
`--editor-view`?"* with **no** -- it opens read-only in *every* build, because
the flag is about editing and the reason it is opt-in (input-method
composition) has nothing to say about a read-only view. That reasoning was
right and is now inert: there is no such document, so the flag decides alone
again.

**This weakens the case for the `--editor-view` fork and does not settle it.**
[ADR-0018](ADR-0018.md), re-affirmed as D2 on 2026-08-22, keeps the fork
because composition is impossible on Slint 1.17.1 and *"the tax fell from five
features to four"*. **The tax has now fallen again** -- the custom surface's
unique burden is smaller with the viewer gone. ADR-0059 deliberately left the
fork undecided and this ADR does not decide it either; it records that D2's
own metric moved, which is D2's stated re-ask condition.

**ADR-0042's find-in-a-huge-document goes whole**, including the defect it
found: *a huge document had no keyboard shortcuts at all*, because
`scroll_for_command` reported `Command::Ignore` as handled and an accepted key
never bubbles to the `KeyBinding` that wanted it. That fix is deleted with the
function. **The lesson is not**, and it is in `DECISIONS.md`: a key the editor
did not map belongs to the window.

**ADR-0017's revert condition loses half its evidence.**
`bp-editor/benches/scroll.rs` still measures per-frame row building against
document size -- 1.19x across a thousand-fold document -- and that is
untouched. What goes is `bp-buffer/benches/large_file.rs`, which measured the
chunked path against the whole-file load. Nothing now measures what a large
document costs to *open*, because there is no second path to compare against:
every document takes the one ADR-0027 called `Normal`.

**A 2 GB file now loads into a rope, or fails trying.** That is not a
regression to fix; it is the product Notepad is. The status bar's size label
is gone with it, and so is Tools ▸ File Analysis's "Size class" line -- both
described a fork that no longer exists.

**Four range-dispatch windows remain and no ids were freed**, because
huge-file mode never had any: it was a *mode*, reached by opening a file,
which is why removing it touched nine files in `bp-ui` and no id block. **That
is the shape ADR-0059 predicted and the thing worth carrying to R5**, whose
`bp-security` half is the same kind of change: not a directory, but a set of
branches in code that stays.

## The lesson

> **A capability with no directory of its own is removed by deleting
> *branches*, and the branches are where the surviving code learned to ask a
> question it no longer needs to ask.**

Every one of the nine `bp-ui` files touched here had the same shape: `if this
document is served from disk, do the other thing`. Deleting the other thing is
easy; the risk is the `if`, because a condition pinned to `false` and a
condition deleted read identically at the call site and differently to
everyone after. `writable` in the File menu is the clearest case -- it could
have been set to `true` and left, and four rows would have kept a gate that
can never close. **A gate that is always open is a gate a reader has to
check**, so it is removed rather than satisfied.
