# ADR-0054: The Command Line Is An Interface, And It Owed Its User Three Things

**Status:** Accepted
**Date:** 2026-08-23

## Context

Phase 20 -- *packaging, signing, release and upgrade testing* -- has been
*Not started* since the roadmap was written, and
[ADR-0053](ADR-0053.md) named it "the only phase still marked *Not started*
that is not blocked on a decision." Taking it began, as
[ADR-0048](ADR-0048.md) recommends, with an inventory rather than an estimate.

The inventory found four things, and they are worth separating because only
two of them are decisions.

### 1. The binary could not say what it was

`bachelorpad --version` printed nothing and opened a window. So did
`bachelorpad --help`. Nineteen phases of work, twelve flags accepted, and no
way to discover any of them from the product -- the only inventory was
`main.rs` and the middle of `bp_config::resolve`.

### 2. A mistyped flag was discarded in silence

`resolve` matched `--key=value` against six names and `continue`d past
anything else. So `--font_size=20` -- the config file's spelling, which is
the one somebody arrives at *by knowing the product* -- did nothing and said
nothing.

**The same crate already got this right on the other layer.**
`Notice::UnknownKey` exists precisely so that `font_size` misspelled in
`config.toml` is reported. One end of one precedence chain told the user; the
other swallowed it. Nobody had chosen that.

### 3. Every crate claimed a licence the repository did not contain

`[workspace.package]` says `license = "MIT OR Apache-2.0"`, and it has since
the scaffold commit. There was no `LICENSE-MIT` and no `LICENSE-APACHE`
anywhere in the tree. A release archive built today would have shipped a claim
with nothing behind it.

### 4. `specs.md` §19 advertised three flags that did not exist

```text
bachelorpad --line 427 server.log
bachelorpad --readonly huge.log
bachelorpad --large-file dataset.jsonl
```

None of the three was implemented, and worse than "not implemented": with
`--line` unrecognised and dropped, `427` fell through to the file collector
and the product tried to open **a file called `427`**.

This is the shape [ADR-0046](ADR-0046.md) named. Ask where a name came from:
all three came from the specification sweep, not from a decision that chose
them, and they have read as a specification ever since.

## Decision

### `--help` and `--version`, printed to stdout, before configuration is read

`bp_config::cli` is the one home for **what the executable accepts**: a
`FLAGS` table of twelve entries, and `help`/`version` rendered *from* it. The
list is the documentation, and a test asserts it -- a flag added to `FLAGS`
without a `--help` line is not a reachable state.

The shell answers both **before** `bp_config::load`. `--help` is what somebody
reaches for when the product is misbehaving, and a config file broken badly
enough to be the reason is not a reason to withhold it.

**Both print to stdout, as `--self-check` already did**, and the release
binary was checked rather than assumed:

| How it was launched | What happened |
| --- | --- |
| Redirected to a file (`Start-Process -RedirectStandardOutput`) | 26 bytes written, exit 0 |
| From a shell, straight to the console | The three lines of `--version`, exit 0 |
| With no console at all (`-WindowStyle Hidden`, no redirect) | Discarded, **exit 0 -- no panic** |

The third row is the one worth having measured. On Windows a release build is
a GUI-subsystem binary (`windows_subsystem = "windows"`, so no console flashes
when a document is double-clicked), which means stdout has nowhere to go when
no console is attached. Rust tolerates the invalid handle rather than
panicking, so the text is dropped and nothing else breaks. The alternative --
`AttachConsole(ATTACH_PARENT_PROCESS)` -- means `unsafe` and a Windows
dependency, to serve the case of somebody double-clicking a text editor in
Explorer in order to read its `--help`. **Conceded, deliberately, and recorded
here so the next person does not re-derive it.**

### A flag this product does not accept is reported, not dropped

Three new notices, and they travel the route the existing ones already do --
`tracing::warn!` at startup and the status bar:

| Typed | Said |
| --- | --- |
| `--font_size=20` | `unknown option '--font_size=20'; ignored. Try --help` |
| `--theme` | `'--theme' needs a value, as --theme=NAME; ignored` |
| `--editor-view=true` | `'--editor-view' takes no value; ignored` |

The third is not hypothetical padding. The shell matches `--editor-view` as a
whole argument, so `--editor-view=true` reads as though it works and does
nothing at all.

**This is why `FLAGS` lists flags `bp-config` does not act on.** Six are
settings and `resolve` applies them; `--line` belongs to `bp-ui`, and
`--self-check`, `--measure-exit` and `--latency-probe` to the shell. A table
holding only this crate's six could not tell a typo from a flag somebody else
owns -- it would have reported `--self-check` as a mistake on every gate run.

### `--line=N` is built. `--large-file` is deleted. `--readonly` is not a flag

Standing authority 3 covers the second of these, and the reasoning is the
value:

- **`--line=N` ships**, made of exactly what Ctrl+G does -- the same
  `AppState::go_to_line`, the same `dispatch::reveal`. One implementation, so
  the flag cannot drift from the row. Confirmed by driving the release binary
  under **both** editor surfaces (R011 rule 3): line 555 of a 900-line
  document at the top of the viewport, highlighted, with the custom surface's
  status bar reading `Ln 555, Col 49`.

  Spelled `--line=N` and not `--line N`, which is what §19 showed. Every other
  flag in this product carries its value with `=`, and a space-separated form
  would need the argument reader to know which flags consume the next word --
  the one piece of machinery this design does not have and does not need.

- **`--large-file` is deleted.** [ADR-0027](ADR-0027.md) and
  [ADR-0030](ADR-0030.md) made size decide how a document opens, from metadata,
  before a byte is read. A flag forcing that choice either agrees with the
  automatic answer, in which case it is a no-op, or overrides it with a worse
  one. **A decision obsoleted it and nobody went back to the sentence.**

- **`--readonly` is not deleted and is not a flag.** Read-only is a property
  of a document, not of an invocation: the huge-document viewer is already
  read-only (ADR-0030) and Security ▸ Lock Document already exists
  (ADR-0048). A flag would be a fourth answer to a question already answered
  three times. It goes to `WORK_QUEUE.md` as a design pass, not a wiring item.

### The licences exist

`LICENSE-MIT` and `LICENSE-APACHE` at the repository root, dual-licensed as
every manifest has claimed since the scaffold commit. `--version` prints
`env!("CARGO_PKG_LICENSE")` -- the workspace manifest stays the one home for
the string, and the two files are the text behind it.

### `bp_platform::{DISPLAY_NAME, DESCRIPTION}`

"BachelorPad+" and "Text editor for notes, data and logs" were literals inside
`AppInfo::bachelorpad`, which writes them into every `mimeapps.list` on the
machine. `--version` needed the same two strings. Two spellings of a product's
name is how a rename reaches two places out of three, so they are constants
now, and a test asserts `--version` names what the desktop registration names.

Deliberately **not** `APP_DIR` or `APP_ID` (ADR-0032): those two carry
compatibility promises and this one carries none. That is precisely why it
must not be typed out at each site -- it is the one that may change.

## Consequences

- **Phase 20 moves from *Not started* to *Started*.** What is done is the part
  a person meets: the binary identifies itself, refuses a typo out loud, and
  ships the licences it claims. What is not done is the artefact -- no release
  archive, no icon, no installer, no signature.
- **Signing needs a certificate, and that is a human's to obtain.** It becomes
  the first row in `DECISIONS_NEEDED.md` since it emptied on 2026-08-22. An
  agent can prepare it -- ADR-0050's lesson, that a task which cannot be
  finished can usually be prepared -- but cannot buy one.
- **`Drive-Window.ps1` gained `-Flag`.** A flag does its work at startup, so
  driving one means launching with it and photographing the first frame. There
  was no way to do that; `--line` is the first flag that needed it and will
  not be the last.
- **`specs.md` §19 stops being a second home for the flag list.** It shows the
  two invocation forms and points at `bp_config::cli::FLAGS`, which is the
  home. That is `CLAUDE.md`'s "link, do not restate" applied to the file it
  had never been applied to.
- The `--line` status is not surfaced: `--line=99999` on a 900-line document
  lands on the last line and says "there are only 900 lines" into a Go to Line
  bar that is not open. Landing somewhere sensible is the behaviour Go to Line
  already chose; only the explanation is missing, and only in the flag's case.

## The lesson

> **An interface nobody has typed at is not an interface, it is a parser.**
> Twelve flags were accepted and none was discoverable; a thirteenth spelling
> was rejected in silence; three more were documented and absent. Every one of
> those is invisible from inside the code, because from inside the code the
> arguments are just a `Vec<String>` that gets read correctly. They become
> visible the moment somebody asks what a *stranger* typing `--help` would
> see -- which is the same question packaging asks about everything, and the
> reason phase 20's inventory found four things in a product that had passed
> its gate 1,972 tests deep.
