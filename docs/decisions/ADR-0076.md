# ADR-0076: The Website Is Static, And The Only Thing It Collects Is An Email Address You Ticked A Box For

**Status:** Accepted
**Date:** 2026-09-10
**Depends on:** [ADR-0006](ADR-0006.md), [ADR-0055](ADR-0055.md), [ADR-0072](ADR-0072.md), [ADR-0075](ADR-0075.md)

## Context

`bpad.prompt-forge.dev` has two jobs: give somebody the download and the
documentation for BachelorPad+ Lite, and collect early-access signups for the
full BachelorPad+.

Those two jobs have opposite privacy shapes, and that is the whole of this
decision. The first collects nothing. The second collects an email address --
which makes it the only part of this project, on any surface, that holds
personal data at all. [ADR-0006](ADR-0006.md) says core editing never depends
on cloud or AI services; the product honours that completely. A website is not
covered by it, and a website that quietly started collecting analytics would
be a contradiction nobody had written down.

## Decision

**A static site on Azure Static Web Apps, deployed from this repository, with
no analytics, no tracking, no cookies and no third-party scripts.** Two pages:
the product, and the waitlist.

### The product page

Downloads, what it does, and the two things a visitor deserves to be told
before clicking:

- **The archives are unsigned** ([ADR-0055](ADR-0055.md)). SmartScreen will
  warn. `New-Release.ps1` prints that on every run in the same words, and a
  download page that stays quiet about it is asking the user to discover it
  themselves.
- **Windows and Linux** ([ADR-0072](ADR-0072.md)), said in the positive. A
  macOS visitor gets an answer rather than an absence.

Checksums are published beside the archives, because they are the whole of
what an unsigned publisher can honestly offer, and offering it is not nothing.

### The waitlist page

For BachelorPad+ full. **It promises features and a date, and no price.**

The feature list is not written for the page -- it is the list of what
[ADR-0057](ADR-0057.md) and [ADR-0059](ADR-0059.md) through
[ADR-0064](ADR-0064.md) removed from this product, every item of which
demonstrably worked before it was taken out. That is the difference between a
waitlist for a product and a waitlist for an intention, and it is the only
form of it this repository could write without contradicting its own rules
about claims.

> **Amended 2026-09-25 ([ADR-0089](ADR-0089.md)).** The countdown and the
> date below are withdrawn. There was no plan behind 10 October, and a missed
> public date would have stood beside every release-candidate announcement.
> The page now says BachelorPad+ is in development, with no date. The feature
> list above stands.

**The countdown marks BachelorPad+ arriving, thirty days out, on 10 October
2026.** A fixed instant in UTC, not a rolling one: a per-visitor thirty days
that resets when somebody clears their browser storage is a claim the visitor
can catch being false, and this project writes ADRs against claims that cannot
fail.

**This is now a public commitment to a date**, which the first version of this
ADR deliberately avoided by promising features and no dates. That was
reversed on request, and the reversal is recorded rather than quietly applied:
if the date moves it moves on six pages, with the reason beside it.

### What the form does with an address

**Amended 2026-09-10.** The first version of this ADR chose a hosted form
service, reasoning that holding no personal data is the safest position. That
was decided without looking at what already existed, and
`dboles99/af-site` had solved the same problem properly on the same domain
three days earlier.

**So this adopts af-site's arrangement rather than inventing a second one**:
an Azure Function at `/api/subscribe`, writing to Table Storage in Daniel's
own account, then forwarding to Kit.

The reasoning is af-site's and it is better than the original:

1. **The list is yours.** Moving between email platforms later costs an
   export rather than a migration.
2. **Storage first, Kit second.** If the forward fails the request still
   succeeds, because the address is already stored. A signup captured but not
   synced is a five-minute fix; one lost to a third-party outage is gone.
3. **The API key never reaches the browser**, which is the whole reason it
   runs server-side.
4. **Consent is obtained, not merely notified.** GDPR Art 4(11) wants a clear
   affirmative action, so there is an unticked box, and Art 7(1) puts the
   burden of demonstrating consent on the controller, so the *wording agreed
   to* is stored and versioned alongside the address.

And it makes the site's own claim stronger rather than weaker: the endpoint is
**same-origin**, so `connect-src` stays at `'self'` with no exception and the
page makes no third-party request at all. The hosted-service version would
have needed one.

**Two lists, kept apart by a tag.** The release-notes list is for the free
version; the waitlist is for BachelorPad+. The pages say that joining one does
not join the other, and the `list` field is what makes that true rather than
stated.

### Why the analytics decision does *not* follow af-site

af-site runs GA4 with Consent Mode v2 and a banner, and `site.json` records
that as a deliberate reversal of its own earlier no-analytics decision. **This
site does not, and the difference is the product rather than the principle.**

BachelorPad+ Lite's headline claim is that it has no telemetry and makes no
network connection, and that you can check this by reading the source. A
`googletagmanager.com` request on the page making that claim is the kind of
contradiction a reader finds in ten seconds and never forgets. The marketing
plan identifies *editor no telemetry* and *offline notes app* as the queries
this product actually wins; a tracker on the landing page loses the argument
before it starts.

What is measured instead: Search Console and Bing Webmaster (impressions,
clicks and queries per language, no cookies, no consent needed), GitHub
release downloads and stars, and signups. That is enough to know whether
anything is working.

**af-site selling plugins and this site giving away an editor whose selling
point is restraint are different situations, and the same answer would have
been wrong for one of them.**

## What is shared with af-site, and why that matters

Two sites on one domain, one operator. Every difference between them is a
thing to keep working twice, so the conventions are taken wholesale:

| | Shared |
| --- | --- |
| Locale directories | en-GB at the root, then `us/`, `fr/`, `de/`, `ja/`; `zh-tw/` is new here |
| Sitemaps | one per language plus an index, named by locale slug |
| `llms.txt` | one per language, written to be quoted by an assistant answering in that language |
| `robots.txt` | names GPTBot, ClaudeBot, PerplexityBot, Google-Extended, Applebot-Extended and bingbot explicitly, because several look for their own token first |
| Signups | Azure Function, Table Storage, Kit, versioned consent |
| PayPal | `paypal.me/DBoles648` with preset amounts, as links rather than the SDK |
| Deploy | `Azure/static-web-apps-deploy@v1` with `skip_app_build` |

**The one thing not shared is analytics**, for the reason above.

## Consequences

**The site is built and deployed from this repository** under `site/`, so a
release and the page describing it move together. A download link naming a
version the release workflow has not produced is the failure this prevents.

**Azure Static Web Apps, Free tier**, with `bpad.prompt-forge.dev` as a
custom domain. **The DNS is at name.com, not Azure DNS** -- there is no Azure
DNS zone in either subscription, and `prompt-forge.dev` answers from
`ns1glr.name.com` and its siblings. The CNAME is added there, exactly as
`www.prompt-forge.dev` already is. This is written down because the first
version of this ADR assumed Azure DNS and was wrong.

**No analytics means fewer numbers**, and that is accepted rather than
overlooked. Search Console and Bing give impressions, clicks and queries per
language; GitHub gives downloads and stars; the two lists give signups. What
is lost is page-level behaviour, and a static page with no scripts is a
promise that can be verified by reading its source.

**GPL-3.0-only applies to the application, and the site says which build it is
offering** -- version, commit and checksum -- so that the source it links to
is the source the archive was built from ([ADR-0071](ADR-0071.md)).

## The lesson

> **A product with a strict privacy rule acquires a website, and the rule does
> not automatically come with it.**

[ADR-0006](ADR-0006.md) is about the application. Every crate honours it and
several ADRs turn on it. A marketing site is a different artefact on different
infrastructure written in a different language, and the default for that
artefact -- the thing every template ships with -- is an analytics tag.

Nothing would have failed. No test covers a website, the gate never sees it,
and the rule it contradicts is one directory away in a file about crate
boundaries. **The check is to ask, of each new surface, which of this
project's existing rules it is now the exception to** -- and to answer in
writing before the surface exists, because afterwards it is a change rather
than a decision.

### And the one that cost more

> **Before designing a mechanism, look for the one that already exists next
> door.**

This ADR originally specified a hosted form service, with a page of reasoning
about why holding no personal data is safest. It was written without opening
`af-site`, which sits on the same domain, is owned by the same person, and had
solved the identical problem three days earlier, better, with GDPR consent
versioning this version had not thought about.

The tell was available and ignored: **the domain was already in use.**
`bpad.prompt-forge.dev` is a subdomain of a site that exists, and "what does
the parent site do?" is one question that would have produced the whole
answer -- the signup mechanism, the locale directory shape, the sitemap
naming, `llms.txt`, the PayPal handle, and the deploy configuration.

This is trap 6 wearing different clothes. That trap says a claim in the record
is not a property of the repository. This is its neighbour: **an absence in
*this* repository is not evidence that the thing does not exist.**
