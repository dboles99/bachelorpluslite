# ADR-0036: A Long Security History Stays Usable By Reading It Lazily, Not By A Faster Key

**Status:** Accepted
**Date:** 2026-08-21

## Context

`bp-audit` seals one complete `.bpadx` envelope per line (ADR-0024), and
`AuditLog::read` decrypts every line of a file in one pass into a `Vec<Record>`
before the caller sees any of it. At the OWASP baseline's ~50-100 ms per
Argon2id derivation, a few hundred lines already costs several seconds, and a
document's history only grows. D7 asked whether `bp-crypto` should expose a
derive-once API so a caller pays one derivation instead of one per line, and
this repository's own decisions queue proposed exactly that as the candidate
answer: split `derive` from `seal_with_key`.

**That candidate answer does not survive contact with why the format costs
what it does.** `crates/bp-audit/src/passphrase.rs`'s own module documentation
already argues this ground, for the write side: every `bp_crypto::seal` call
draws a *fresh random salt*, so every line's Argon2id output is a different
key even though every line shares one passphrase -- specifically so that a
`(key, nonce)` pair can never repeat across lines. The alternative it names
and rejects is a session key: cheaper to derive once, but it "would ... take
on a nonce counter to get right", and "getting a nonce counter wrong is
unrecoverable" for a counter that would have to survive process restarts,
which an append-only log deliberately does not keep state for.

A derive-once *read* API does not revisit that write-side argument -- but it
does not escape its consequence either. Because each line's salt is
independently random by design, there is no single derived key that opens
more than one line. Exposing `derive` separately from `seal_with_key` would
still require calling it once per line on the way back in, because each
line's key genuinely differs. **The API `bp-crypto` would need to expose is
not the problem; the problem is that `AuditLog::read` decrypts the whole file
before showing any of it**, which turns a per-line cost that is individually
fine into a whole-file cost that eventually is not.

## Decision

**`bp-crypto`'s API does not change.** `derive` and `Key` stay exactly as
private as ADR-0021 left them, and the fresh-salt-per-line argument in
`passphrase.rs` stands untouched.

**`AuditLog` gains a way to read incrementally instead of eagerly**, so the
security inspector shows what it has decrypted as it goes rather than
blocking until the whole history is unsealed. The shape of that -- an
iterator over records versus a paged read versus a background decrypt with a
progress readout -- is implementation, not this decision; what this ADR fixes
is that the fix lives in `bp-audit`'s consumption pattern, not in
`bp-crypto`'s key surface.

## Consequences

- D7 leaves `project/DECISIONS_NEEDED.md`, answered differently than it was
  posed: the mechanism named in the queue turned out not to work, and this
  records why, so nobody re-proposes it having to re-derive the same
  argument from scratch.
- **Not yet implemented.** `AuditLog::read`'s `Vec<Record>` return and its one
  caller in the shell's security inspector both need to change together; this
  is real, separate work, not a one-line change like ADR-0035's.
- Every line's Argon2id derivation, and the fresh-salt argument that makes
  nonce reuse structurally impossible across lines, is unchanged. A history a
  thousand lines long costs the same *total* CPU time to read as it does
  today; what changes is that the person reading it sees the first lines
  immediately instead of waiting for the last one.
- If a future session wants the total cost itself lowered rather than only
  its visibility, that is a format change to how `bp-audit` seals lines --
  weighing a durable nonce counter's failure mode against the derivation cost
  it would remove -- and it needs its own ADR, not a reopening of this one.
